# 소싱라이프 주문관리 서비스 기획

## 1. 서비스 정의

주문관리는 소싱라이프 내부에서 제공하는 마켓 주문 수집, 조회, 처리 기능이다.
기존 독립 주문관리 범위는 소싱라이프 안의 `주문관리` 메뉴로 통합한다.
주문 처리 과정에서는 소싱라이프 상품 후보 검색, 구매대행 신청/결제, 국내송장 확보 결과를 주문 단위로 연결한다.

현재 저장소는 PostgreSQL·로그인·스마트스토어 주문/클레임 수집·명령 코어와 실원장 화면을 함께 갖춘 전환 단계다. 실제 판매자 계정 UAT와 소싱라이프 구매 연동 전이므로 실서비스 완료로 보지 않는다.
mock data와 브라우저 상태는 API 자격증명 없이 UI 정상·예외 경로를 확인하는 명시적 데모 모드에만 사용한다.

## 2. 핵심 목표

1. 모든 판매처의 주문을 한 화면에서 통합 조회한다.
2. 마켓별 주문 상태를 주문관리 내부 상태로 통일한다.
3. 운영자는 소싱라이프 주문관리에서 주문확인, 소싱 진행상태 확인, 국내송장 확인, 배송중 처리를 진행한다.
4. 주문관리는 소싱라이프 내부 기능이며, 주문 처리 중 소싱라이프 결제와 국내송장 결과만 연결한다.
5. 스마트스토어, 쿠팡을 먼저 연동하고 11번가, G마켓, 옥션으로 확장한다.
6. 화면 기준의 MVP에서는 실제 API 호출보다 운영 흐름, 상태 전환, 화면 구성, 사용자 판단 기준을 먼저 확정한다.

## 3. 연동 우선순위

최종 연동 대상은 스마트스토어, 쿠팡, 11번가, G마켓, 옥션이다.
화면 프로토타입에서는 5개 마켓 모두 등록 대상으로 제공한다.
실제 API 안정화와 운영 우선순위는 스마트스토어, 쿠팡을 먼저 검증하고 11번가, G마켓, 옥션 순서로 확장한다.

| 우선순위 | 판매처 | 연동 기준 |
|---|---|---|
| 1 | 스마트스토어 | 커머스API |
| 2 | 쿠팡 | 쿠팡 Open API |
| 3 | 11번가 | 11번가 Open API |
| 4 | G마켓 | ESM PLUS API |
| 5 | 옥션 | ESM PLUS API |

## 3-1. 판매처 계정 등록 정책

- 주문관리는 마켓별 다중 계정 등록을 지원한다. 최종적으로 사용자는 스마트스토어, 쿠팡, 11번가, G마켓, 옥션에서 운영 중인 판매자 계정 또는 스토어를 개수 제한 없이 등록할 수 있다.
- 주문수집은 활성화된 모든 마켓 계정과 스토어를 대상으로 실행하며, 특정 판매처만 수집하거나 특정 스토어만 수집하는 기능은 초기 범위에 포함하지 않는다.
- 주문 목록에는 판매처뿐 아니라 어떤 스토어에서 수집된 주문인지 함께 표시한다.
- 여러 개의 스토어가 등록된 경우 주문수집 화면에서 마켓별, 스토어별, 기간별, 검색어 기준으로 주문 목록을 조회할 수 있어야 한다.
- 주문 목록에는 주문이 수집된 마켓과 스토어명을 별도 정보로 표시한다.
- 주문 테이블과 행 확장 자세히 보기는 주문 처리에 필요한 정보와 현재 상태에서 가능한 다음 단계 액션을 제공한다.
- 마켓별/스토어별 필터는 주문 조회용 필터이며, 주문수집 실행 범위를 제한하는 기능은 아니다.
- 현재 마켓연동 화면은 마켓, 스토어명, 연동상태, 활성, 관리 중심으로 제공한다. 수집 성공/실패 상태와 마지막 수집 시각은 추후 API 연동 또는 운영 진단 정보로 분리한다.

## 4. 전체 주문 처리 흐름

```text
마켓 결제완료 주문
→ 소싱라이프 주문관리 주문수집
→ 신규주문
→ 주문확인 또는 소싱하기(소싱라이프 후보/옵션 매칭 + 주문확인)
→ 상품준비
→ 소싱하기(소싱라이프 후보 확인, 옵션 선택, 배대지 선택, 결제) 또는 직접구매 국내송장 등록
→ 결제완료 후 선택 배송대행지 사이트 열기와 주문서 자동입력
→ 접수대기/접수신청(동일 단계) 실행
→ 국내송장 즉시 발급과 택배사·송장번호 저장
→ 자동 배송중 처리 ON이면 마켓 발송 후 배송중
→ OFF이거나 자동 발송 실패이면 발송대기
→ 운영자 배송중 처리
→ 배송중
→ 배송완료
```

마켓 직접전달 예외 흐름:

```text
상품준비
→ 마켓 직접전달 실행
→ 네이버·쿠팡 직접전달 API 성공
→ 마켓 상태만 배송중으로 변경
→ 내부 작업 단계는 상품준비 유지
→ 소싱라이프 또는 외부 구매 완료 + 국내송장 저장
→ 내부 배송중으로 이동
```

주문은 다음 두 상태를 분리해 관리한다.

| 구분 | 역할 | 예시 |
|---|---|---|
| 내부 작업 단계 | 운영자가 다음으로 처리할 업무를 정함 | 신규주문, 상품준비, 발송대기, 배송중, 배송완료 |
| 마켓 상태 | 마켓 API에 반영된 구매자 노출 상태 | 결제완료, 배송중, 배송완료 |

마켓 직접전달 API가 성공해도 소싱라이프 결제가 남아 있으면 내부 작업 단계는 `상품준비`에 유지한다.
직접전달 이후에도 구매 방식은 반드시 소싱라이프 구매 또는 외부 구매 중 하나여야 한다. `구매 안 함` 상태는 제공하지 않으며, 구매 완료 전 직접전달 주문은 국내송장 없이 상품준비에 유지한다.
소싱라이프 실제 국내송장이 배송완료되면 내부 주문은 `배송완료`로 이동한다. 직접전달 주문의 마켓 상태가 배송중으로 남아 있어도 내부 배송완료를 지연하지 않는다.

## 5. 소싱라이프 관계 정의

- 주문관리는 소싱라이프 내부 기능이다.
- 주문관리는 마켓에서 수집된 주문을 기준으로 소싱라이프 주문 생성 여부, 소싱라이프 결제 여부, 국내송장 확보 여부를 주문 단위로 관리한다.
- 소싱라이프에서 직접 생성하거나 주문한 내역은 주문관리의 주문수집 목록에 넣지 않는다.
- 소싱라이프 주문번호는 마켓 주문을 소싱라이프 결제 흐름으로 넘긴 뒤 생성된 주문서 식별값으로 저장하며, 소싱라이프 결제 완료 여부와 별도로 관리한다.
- 소싱라이프 내부의 구매, 검수, 입고, 물류 상세 처리는 소싱라이프 기존 기능에서 진행한다.
- 주문관리의 책임은 소싱라이프 결제/송장 처리 결과를 마켓 주문 상태에 반영하고, 국내송장을 기준으로 배송중 처리를 할 수 있도록 관리하는 것이다.
- 소싱 후보가 적합하지 않은 경우 운영자는 모달 안에서 키워드 또는 타오바오/소싱라이프 상품 URL로 후보를 추가로 찾는다.
- 개인통관부호가 일치하지 않는 주문은 상품준비에서 소싱라이프 결제를 진행할 수 없다. 통관부호를 수정해 일치 상태가 된 뒤 소싱한다.
- 키워드 찾기는 검색 후보 20개를 기존 이미지 매칭 후보 목록 상단에 추가하고, URL 찾기는 해당 상품 1개를 기존 후보 목록 상단에 추가한다.
- 현재 MVP는 타오바오 직접 결제, 내부 배대지/창고 관리, 소싱라이프 기존 물류 상세 운영 기능을 주문관리 안으로 가져오지 않는다.

## 6. 주요 메뉴

| 메뉴 | 역할 |
|---|---|
| 주문관리 > 주문수집 | 일반 주문의 신규주문, 상품준비, 발송대기, 배송중, 배송완료 상태별 통합 조회 |
| 주문관리 > 취소/반품/교환 | 마켓에서 수집된 취소, 반품, 교환 클레임 조회 |
| 주문관리 > 문의관리 | 마켓 문의 확인 및 응대 |
| 주문관리 > 마켓연동 | 판매처별 API 인증 정보와 스토어명 관리 |

## 7. 주요 화면 흐름

| 화면 | 핵심 기준 |
|---|---|
| 사이드바 | 소싱라이프 타오바오 메뉴 안에 `주문관리`를 두고 하위 메뉴로 주문수집, 취소/반품/교환, 문의관리, 마켓연동을 제공 |
| 주문수집 화면 | 본문 상단 탭에서 신규주문, 상품준비, 발송대기, 배송중, 배송완료를 선택하고 검색/필터 + 주문 테이블을 구성 |
| 신규주문 | 선택된 주문에만 `주문확인`, `주문취소` 전역 액션 제공, 행별 `주문확인`, `소싱하기`, `주문취소` 노출 |
| 상품준비 | `소싱하기` 액션으로 소싱라이프 상품 매칭, 옵션 선택, 결제 진행. 네이버·쿠팡 주문은 예외적으로 마켓 직접전달 가능 |
| 상품준비 직접구매 | 소싱라이프에서 결제하지 않고 직접 구매한 주문은 자세히 보기의 `처리하기` 섹션에서 `국내송장 등록`을 실행해 택배사와 국내송장번호를 필수 입력한다. 자동 배송중 처리 OFF는 발송대기, ON은 마켓 발송 성공 후 배송중으로 이동 |
| 발송대기 | 목록 처리하기에는 고빈도 액션 `배송중 처리`만 제공한다. 자세히 보기의 `처리하기` 섹션에는 `배송중 처리`, `결제완료 보기`, `주문취소`를 제공한다. |
| 배송중/배송완료 | 상태 확인 목적 조회 화면, 개별 액션은 기본적으로 비활성 |
| 취소/반품/교환 | 일반 주문과 별도 클레임 그룹으로 노출하고 주문별 `취소처리`, `반품처리`, `교환처리` 액션 제공 |
| 소싱하기 모달 | 신규주문에서는 `주문확인` 아래 `주문취소`를 제공하고, 상품준비에서는 매칭 후보·옵션·수량 확인, 저장된 배대지 수령 프로필 선택, 구매대행 신청, 결제대기·채팅, 별도 결제 흐름을 제공 |

구매대행 신청은 결제 완료와 분리한다. 신청 직후 주문은 `결제대기`에서 멈추며, 운영자는 문의가 있으면 같은 화면의 채팅을 사용한 뒤 `결제하기`로 결제 단계를 다시 시작한다. 여기서 배대지 선택은 소싱라이프에 저장된 수령 프로필을 고르는 기능이며 주문팡팡이 배대지·창고 운영을 직접 관리한다는 의미가 아니다.
결제완료 시 선택한 배송대행지 사이트를 열고 주문서를 자동입력한다. 연결 대상은 접수 시 국내송장을 즉시 발급하는 배송대행지로 제한하며 `접수대기`와 `접수신청`은 같은 접수 단계다. 접수 응답의 택배사·국내송장번호를 주문에 저장한 뒤 결제완료 조회 화면으로 전환한다. 현재 프로토타입은 외부 사이트 열기·자동입력·접수 화면을 생략하고 결제완료 클릭 시 더미 송장을 즉시 생성해 결과만 시연한다.
발송대기와 배송중은 소싱라이프 결제완료 또는 외부구매 완료가 선행된 주문만 진입할 수 있다. 미결제 상태가 발견되면 `결제하기`를 노출하지 않고 `결제상태 불일치`로 표시한다.
| 마켓연동 | 우측 상단 `마켓 추가`, 마켓별 인증정보 입력, 테스트, 설정/삭제, 활성 스위치 제공 |

## 7-1. 검색/필터 기준

- 기간 필터는 `오늘`, `3일`, `7일`, `30일`, `직접 입력`을 제공한다.
- `직접 입력`은 시작날짜와 끝나는날짜를 선택하는 작은 팝오버로 처리한다.
- 검색어는 상품명, 주문번호, 주문자, 수령인 기준으로 주문 목록을 좁힌다.
- 마켓/스토어 필터는 중복 선택을 지원한다.
- 마켓을 선택하면 해당 마켓에 속하지 않은 스토어는 숨기지 않고 비활성화한다.
- 모든 일반 주문 단계에 `판매처`, `상태` 드롭다운을 제공한다.
- 상태 드롭다운은 현재 주문 존재 여부와 관계없이 단계별 고정 상태값을 제공하며, 배송완료 단계는 `전체`, `배송완료`, `구매확정`을 제공한다.
- 배송완료 주문은 모두 목록 상태 `배송완료`를 가지며, `marketOrderStatus`가 `PURCHASE_DECIDED`이면 목록 상태 `구매확정`을 추가로 가진다.
- 필터는 조회 조건이며 주문수집 실행 대상 마켓 계정과 스토어를 제한하지 않는다.

## 8. 초기버전 주문 테이블 기준

- 주문 목록은 처리에 필요한 핵심 컬럼만 우선 노출한다.
- 주문 행을 클릭하면 행 아래에 자세히 보기를 펼쳐 목록에 없는 주문 관련 정보를 확인한다.
- 하나의 컬럼은 하나의 업무 목적 또는 하나의 기능 단위를 담당한다.
- 같은 업무 목적의 값과 상태 표시는 한 컬럼에 함께 표시할 수 있다.
- 서로 다른 업무 목적의 상품정보, 구매자정보, 수령인정보, 소싱정보, 송장정보, 처리버튼을 한 컬럼에 섞어 표시하지 않는다.
- 마켓별 수수료율을 사용자가 직접 설정하는 화면은 현 주문수집 MVP 범위에서 제외한다. 마진 분석은 주문 결제 금액을 기준으로 수집된 판매 수수료와 소싱 상품 금액·소싱처 이용료·환전 수수료·예상 배대지 운임을 각각 직접 차감한다.
- 주문수집 화면에서는 주문 처리에 필요한 핵심 정보와 액션을 우선 표시하고, 수수료 상세값은 장부/정산 기능에서 중심적으로 다룬다.
- 처리이력은 초기버전 주문관리 화면 범위에서 제외한다.

초기 주문 테이블 컬럼 순서는 다음 기준을 따른다.

1. 선택
2. 진행상태
3. 처리하기
4. 주문일시
5. 상품정보
6. 택배정보
7. 배송정보
8. 판매처

진행상태 컬럼은 소싱 진행 상태와 중요한 마켓 예외·완료 결과를 함께 표시한다. 소싱 상태는 `소싱필요`, `소싱완료`, `결제대기`, `결제완료`, `중국배송중`, `통관 중`, `국내 배송중`, `배송완료`이며, 마켓 보조 상태는 `마켓 취소요청`, `구매확정`만 표시한다. 외부 구매 완료도 진행상태에서는 `결제완료`로 통합하고 구매경로 `외부구매`는 자세히 보기의 소싱상품 영역에서 표시한다. `마켓 배송중`, `마켓 배송완료`는 원천 상태값만 유지하고 배지로 표시하지 않는다.
`구매확정`은 내부 주문 단계가 아니라 배송완료 주문의 마켓 동기화 결과에서 파생되는 추가 목록 상태값이다.
진행상태가 `결제완료`일 때는 자세히 보기의 `처리하기` 섹션에서 `결제완료 보기`로 결제정보와 채팅을 다시 확인할 수 있다. 발송대기 목록에서는 고빈도 액션인 `배송중 처리`만 표시한다. `중국배송 보기`, `통관 보기`, `국내배송 보기` 버튼과 모달은 제공하지 않으며 해당 단계는 진행상태 배지로만 확인한다.
소싱 진행 단계는 마켓 주문상태와 독립된 판매자/소싱라이프 관점의 실제 진행 상태다.
국내 택배번호를 마켓에 등록해 마켓에는 배송중으로 보이더라도, 실제 소싱 단계는 중국 내 배송 전/중일 수 있다.
마켓 또는 내부 주문이 배송완료로 확정된 경우 소싱 단계도 `배송완료`로 맞춘다.

행 확장 자세히 보기의 정보 순서는 `주문상품`, `구매자`, `배송정보`, `택배정보`, 하단의 `처리하기`와 `소싱상품`이다. 하단은 처리하기 1, 소싱상품 2 비율로 배치한다.
배송정보는 목록과 자세히 보기에서 모두 수정할 수 있다.

## 8-1. 국내송장 처리 기준

- 상품준비에서 소싱라이프 결제가 완료되면 선택 배송대행지 주문서 접수를 실행하고, 접수 응답으로 발급된 소싱라이프 주문번호·소싱금액·국내송장을 함께 반영한다.
- 연결된 배송대행지는 접수와 동시에 실제 국내송장을 발급한다. 송장이 없으면 결제 성공은 보존하되 접수 결과 오류로 처리하고 발송 단계로 이동하지 않는다.
- 마켓 직접전달을 먼저 처리한 주문에도 같은 규칙을 적용한다. 직접전달 + 소싱라이프 구매 완료 + 국내송장 없음 조합은 생성하지 않으며, 구매 완료와 내부 상태 변경을 모두 차단한다.
- 국내송장이 있더라도 `자동 배송중 처리`가 OFF이면 송장번호가 입력된 상태로 발송대기에 남긴다.
- 국내송장이 있고 해당 토글이 ON이면 마켓 발송 API를 자동 호출한다. 성공 시 마켓 주문을 배송중으로 변경하고 내부 주문도 배송중으로 함께 이동한다.
- 자동 발송 API가 실패하면 마켓과 내부 상태를 배송중으로 변경하지 않고, 송장이 있는 발송대기에 남겨 재처리할 수 있어야 한다.
- 발송대기 상태는 구매와 국내송장 확보가 끝났지만 마켓 택배 발송 처리가 남은 상태다.
- 국내송장은 소싱라이프 구매 완료 결과로 반영되거나 외부 구매 완료 시 운영자가 필수 입력한다.
- 직접전달 주문도 택배정보에 실제 국내 택배사·송장번호를 표시하고, 그 아래에 `직접전달` 배지를 표시한다.
- 마켓 직접전달이 완료되고 구매도 완료된 주문이 실제 국내송장을 받으면 내부 주문은 `배송중`으로 이동한다.
- 직접전달 주문은 실제 국내송장 배송완료 시 내부 주문을 배송완료로 이동한다. 직접전달 여부는 택배정보의 `직접전달` 배지로 확인하며, 진행상태 컬럼에는 `마켓 배송중 · 직접전달` 배지를 표시하지 않는다.
- 발송대기 상태에서는 소싱라이프 송장 자동 수집 토글을 제공하지 않는다.
- 발송대기 상태에서는 별도 `소싱라이프 송장 수집` 버튼을 제공하지 않는다.
- 수동 입력은 운영자가 국내 택배사와 국내송장번호를 직접 입력하는 기능이다.
- 자동 배송중 처리 ON은 구매 완료와 국내송장 확보 직후 마켓 발송을 시도하고 성공 시 배송중으로 넘기는 기능이다.
- 자동 배송중 처리 OFF일 때는 국내송장이 입력되어도 운영자가 발송대기의 `배송중 처리`를 실행해야 국내송장이 마켓에 전송되고 배송중으로 이동한다.
- 배송중 처리는 국내송장이 있는 발송대기 주문만 대상으로 한다.
- 배송중 처리가 성공하면 주문 상태는 배송중으로 변경된다.
- 상품준비에서 직접 구매한 주문은 `국내송장 등록`을 사용하며 택배사와 국내송장번호를 필수 입력해야 한다. 송장번호가 없으면 등록과 상태 이동을 허용하지 않는다.
- 마켓 직접전달을 먼저 처리한 외부 구매 주문도 예외가 아니다. 직접전달 + 외부 구매 완료 + 국내송장 없음 조합은 생성하지 않으며, 완료와 내부 배송중 전환을 모두 차단한다.
- 국내송장 등록 후 주문은 진행상태를 `결제완료`로 표시하되 구매경로 `외부구매`는 유지한다. 자세히 보기의 소싱상품 영역에는 외부 구매처 결제완료 안내를 표시하고 소싱라이프 주문번호는 연결하지 않는다.
- 직접구매 국내송장 등록도 소싱라이프 구매 완료와 동일하게 `자동 배송중 처리` 설정을 적용한다. OFF이면 송장만 저장하고 발송대기에 남으며, ON이면 마켓 발송 API 성공 후 마켓과 내부 주문을 배송중으로 변경한다.
- 상품준비와 발송대기의 `자동 배송중 처리` 토글은 동일한 설정값을 공유하며 한 화면에서 변경하면 다른 화면에도 그대로 적용한다.
- 마켓 직접전달 주문에는 판매자 `주문취소` 액션을 노출하지 않는다.
- 배송중 상태에서는 마켓 API로 송장 변경을 자동 전송하지 않으며, 변경된 송장번호 항목도 목록/상세에 표시하지 않는다.

## 9. 단계별 처리 건수 표시

- 주문수집 본문 상단 탭에는 단계별 주문 건수를 표시한다.
- 일반 주문 표시 대상은 신규주문, 상품준비, 발송대기, 배송중, 배송완료다.
- `전체` 탭은 처리보류를 포함한 일반 주문을 조회하고 `처리보류` 상태 필터를 제공한다.
- 클레임 처리 건수는 취소/반품/교환 화면에서 별도로 표시한다.
- 배송완료 상태는 마켓 배송완료와 구매확정 주문을 포함하는 조회 상태이며, 구매확정 여부는 별도 속성으로 저장할 수 있다.
- 배송완료 필터는 구매확정 주문을 포함한 전체 배송완료 주문을 조회하고, 구매확정 필터는 그중 구매확정 배지가 있는 주문만 조회한다.

## 10. 현재 데이터/기술 전제

- PostgreSQL tenant/account/order/item/recipient/sync/command/claim/audit 원장과 RLS, 브라우저 세션, 스마트스토어 수집 worker가 현재 실서비스 코드 경로다.
- `/orders` 기본 진입 화면은 신규주문 탭이다.
- 주문 목록은 `/api/orders` 실원장을 우선 표시하고, 연결 실패·0건 시 별도 원장 안내 문구 없이 데모 주문을 표시한다. 클레임 작업함도 데이터 원천을 설명하는 상단 안내 문구를 표시하지 않는다.
- 소싱라이프 후보는 `lib/mock-data/sourcing-life.ts`의 더미 데이터를 기준으로 표시한다.
- 실주문 매핑·국내송장은 서버 원장/API를 사용한다. 소싱 결제와 demo 주문 처리 결과만 브라우저 저장소로 화면 동작을 검증한다.
- 브라우저 저장소 초기화는 demo 상태만 삭제하며 PostgreSQL 실원장을 변경하지 않는다.
- 사용 중인 저장소 키는 `jumunpangpang.syncedInvoices`, `jumunpangpang.sourcingMatches`, `jumunpangpang.sourcingPayments`다.
- React Query는 실주문·마켓계정·클레임 cursor API 조회와 오류/재시도에 사용한다.
- Zustand는 현재 대시보드 등 클라이언트 상태 관리 기반으로 사용한다.
