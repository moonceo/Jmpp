# 주문팡팡 + 소싱라이프 서비스 기획

## 1. 서비스 정의

주문팡팡은 여러 판매처의 주문을 한 화면에서 수집, 조회, 처리하는 통합 주문관리 프로그램이다.
주문 처리 과정에서 소싱라이프를 연결해 상품 소싱, 구매 처리, 국내송장 확보를 진행한다.

현재 MVP는 백엔드/API 실연동 전 단계의 Next.js 프론트 프로토타입이다.
주문, 마켓 계정, 소싱라이프 처리 결과는 mock data와 브라우저 상태를 기준으로 동작을 검증한다.

## 2. 핵심 목표

1. 모든 판매처의 주문을 한 화면에서 통합 조회한다.
2. 마켓별 주문 상태를 주문팡팡 내부 상태로 통일한다.
3. 운영자는 주문팡팡에서 주문확인, 소싱 진행상태 확인, 국내송장 확인, 배송중 처리를 진행한다.
4. 소싱라이프는 외부 소싱/구매 서비스로 연결하며, 주문팡팡은 소싱라이프 연동 상태만 관리한다.
5. 스마트스토어, 쿠팡을 먼저 연동하고 11번가, 지마켓, 옥션으로 확장한다.
6. 화면 기준의 MVP에서는 실제 API 호출보다 운영 흐름, 상태 전환, 화면 구성, 사용자 판단 기준을 먼저 확정한다.

## 3. 연동 우선순위

최종 연동 대상은 스마트스토어, 쿠팡, 11번가, 지마켓, 옥션이다.
화면 프로토타입에서는 5개 마켓 모두 등록 대상으로 제공한다.
실제 API 안정화와 운영 우선순위는 스마트스토어, 쿠팡을 먼저 검증하고 11번가, 지마켓, 옥션 순서로 확장한다.

| 우선순위 | 판매처 | 연동 기준 |
|---|---|---|
| 1 | 스마트스토어 | 커머스API |
| 2 | 쿠팡 | 쿠팡 Open API |
| 3 | 11번가 | 11번가 Open API |
| 4 | 지마켓 | ESM PLUS API |
| 5 | 옥션 | ESM PLUS API |

## 3-1. 판매처 계정 등록 정책

- 주문팡팡은 마켓별 다중 계정 등록을 지원한다. 최종적으로 사용자는 스마트스토어, 쿠팡, 11번가, 지마켓, 옥션에서 운영 중인 판매자 계정 또는 스토어를 개수 제한 없이 등록할 수 있다.
- 주문수집은 활성화된 모든 연동 계정을 대상으로 실행하며, 특정 판매처만 수집하거나 특정 계정만 수집하는 기능은 초기 범위에 포함하지 않는다.
- 주문 목록에는 판매처뿐 아니라 어떤 판매자 계정/스토어에서 수집된 주문인지 함께 표시한다.
- 여러 개의 스토어/판매자 계정이 등록된 경우 주문수집 화면에서 마켓별, 계정별, 기간별, 검색어 기준으로 주문 목록을 조회할 수 있어야 한다.
- 주문 목록에는 주문이 수집된 마켓과 연동 계정을 별도 정보로 표시한다.
- 주문 테이블과 행 확장 자세히 보기는 주문 처리에 필요한 정보와 현재 상태에서 가능한 다음 단계 액션을 제공한다.
- 마켓별/계정별 필터는 주문 조회용 필터이며, 주문수집 실행 범위를 제한하는 기능은 아니다.
- 현재 마켓연동 화면은 마켓, 스토어명, 연동상태, 활성, 관리 중심으로 제공한다. 수집 성공/실패 상태와 마지막 수집 시각은 추후 API 연동 또는 운영 진단 정보로 분리한다.

## 4. 전체 주문 처리 흐름

```text
마켓 결제완료 주문
→ 주문팡팡 주문수집
→ 신규주문
→ 주문확인 또는 매칭하기(소싱라이프 후보/옵션 매칭 + 주문확인)
→ 상품준비
→ 소싱하기(소싱라이프 후보 확인, 옵션 선택, 결제) 또는 수동구매 완료
→ 발송대기
→ 소싱라이프 국내송장 확보 또는 운영자 수동 입력
→ 국내송장 자동저장
→ 배송중 처리
→ 배송중
→ 배송완료
```

## 5. 소싱라이프 관계 정의

- 소싱라이프는 주문팡팡 내부 기능이 아니다.
- 주문팡팡은 소싱라이프 주문 생성 여부, 소싱라이프 결제 여부, 국내송장 확보 여부를 주문 단위로 관리한다.
- 소싱라이프 주문번호는 소싱라이프 주문 생성 성공 시점에 저장하며, 소싱라이프 결제 완료 여부와 별도로 관리한다.
- 소싱라이프 내부의 구매, 검수, 입고, 물류 상세 처리는 주문팡팡 범위가 아니다.
- 주문팡팡의 책임은 소싱라이프 처리 결과를 주문 상태에 반영하고, 국내송장을 기준으로 배송중 처리를 할 수 있도록 관리하는 것이다.
- 소싱 후보가 적합하지 않은 경우 운영자는 `소싱라이프에서 직접 찾기`로 외부 검색 흐름을 이어갈 수 있다.
- 현재 MVP는 타오바오 직접 결제, 내부 배대지/창고 관리, 소싱라이프 내부 배송대행 운영 기능을 주문팡팡 안으로 가져오지 않는다.

## 6. 주요 메뉴

| 메뉴 | 역할 |
|---|---|
| 주문관리 > 주문수집 | 일반 주문의 신규주문, 상품준비, 발송대기, 배송중, 배송완료 상태별 통합 조회 |
| 주문관리 > 취소/반품/교환 | 마켓에서 수집된 취소, 반품, 교환 클레임 조회 |
| 주문관리 > 문의관리 | 마켓 문의 확인 및 응대 |
| 주문관리 > 마켓연동 | 판매처별 API 인증 정보와 스토어명 관리 |

## 7. 주요 화면 흐름

| 화면 | 핵심 기준 |
|---|---|
| 사이드바 | 소싱라이프 타오바오 메뉴 안에 `주문관리`를 두고 하위 메뉴로 주문수집, 취소/반품/교환, 문의관리, 마켓연동을 제공 |
| 주문수집 화면 | 본문 상단 탭에서 신규주문, 상품준비, 발송대기, 배송중, 배송완료를 선택하고 검색/필터 + 주문 테이블을 구성 |
| 신규주문 | 선택된 주문에만 `주문확인`, `주문취소` 전역 액션 제공, 행별 `주문확인`, `매칭하기`, `주문취소` 노출 |
| 상품준비 | `소싱하기` 액션으로 소싱라이프 상품 매칭, 옵션 선택, 결제 진행, 소싱라이프 송장 수신 시 자동 배송중 처리 토글 제공 |
| 상품준비 수동구매 | 소싱라이프를 통하지 않고 외부에서 구매한 주문은 `수동구매 완료`로 발송대기 처리 또는 송장 저장 후 배송중 처리 |
| 발송대기 | 송장 상태 드롭다운(`전체`, `송장 있음`, `송장 없음`)과 `소싱라이프 송장 수집`, `배송중 처리` 제공 |
| 배송중/배송완료 | 상태 확인 목적 조회 화면, 개별 액션은 기본적으로 비활성 |
| 취소/반품/교환 | 일반 주문과 별도 클레임 그룹으로 노출하고 주문별 `취소처리`, `반품처리`, `교환처리` 액션 제공 |
| 소싱하기 모달 | 매칭 후보 확인, 옵션 선택, 구매대행 신청, 결제 화면 흐름을 모달 안에서 확인 |
| 마켓연동 | 우측 상단 `마켓 추가`, 마켓별 인증정보 입력, 테스트, 관리/삭제, 활성 스위치 제공 |

## 7-1. 검색/필터 기준

- 기간 필터는 `오늘`, `3일`, `7일`, `30일`, `직접 입력`을 제공한다.
- `직접 입력`은 시작날짜와 끝나는날짜를 선택하는 작은 모달로 처리한다.
- 검색어는 상품명, 주문번호, 주문자, 수령인 기준으로 주문 목록을 좁힌다.
- 마켓/스토어 필터는 중복 선택을 지원한다.
- 마켓을 선택하면 해당 마켓에 속하지 않은 스토어는 숨기지 않고 비활성화한다.
- 필터는 조회 조건이며 주문수집 실행 대상 계정을 제한하지 않는다.

## 8. 초기버전 주문 테이블 기준

- 주문 목록은 처리에 필요한 핵심 컬럼만 우선 노출한다.
- 주문 행을 클릭하면 행 아래에 자세히 보기를 펼쳐 목록에 없는 주문 관련 정보를 확인한다.
- 하나의 컬럼은 하나의 업무 목적 또는 하나의 기능 단위를 담당한다.
- 같은 업무 목적의 값과 상태 표시는 한 컬럼에 함께 표시할 수 있다.
- 서로 다른 업무 목적의 상품정보, 구매자정보, 수령인정보, 소싱정보, 송장정보, 처리버튼을 한 컬럼에 섞어 표시하지 않는다.
- 마켓수수료율은 현 주문수집 MVP 화면 범위에서 제외한다.
- 주문수집 화면에서는 주문 처리에 필요한 핵심 정보와 액션을 우선 표시하고, 수수료 상세값은 장부/정산 기능에서 중심적으로 다룬다.
- 처리이력은 초기버전 주문관리 화면 범위에서 제외한다.

초기 주문 테이블 컬럼 순서는 다음 기준을 따른다.

1. 선택
2. 처리하기
3. 주문일시
4. 상품정보
5. 택배정보
6. 배송정보
7. 판매처
8. 소싱라이프

행 확장 자세히 보기의 정보 순서는 `주문상품`, `구매자`, `배송정보`, `택배정보`, `소싱상품`이다.
배송정보는 목록과 자세히 보기에서 모두 수정할 수 있다.

## 8-1. 국내송장 처리 기준

- 상품준비에서 `소싱하기`로 소싱라이프 결제가 완료되면 소싱라이프 주문번호, 소싱금액, 국내송장 정보를 함께 반영한다.
- 국내송장이 없으면 주문은 발송대기 상태로 이동한다.
- 국내송장이 있더라도 `소싱라이프 송장 수신 시 자동 배송중 처리`가 OFF이면 송장번호가 입력된 상태로 발송대기에 남긴다.
- 국내송장이 있고 해당 토글이 ON이면 배송중 처리를 자동 시도하고 성공 시 배송중으로 이동한다.
- 발송대기 상태는 배송중 처리 전 국내송장 수집 또는 확인이 필요한 상태다.
- 국내송장은 소싱라이프에서 발급된 송장을 가져오거나 운영자가 직접 입력한다.
- 국내송장은 자동수집, 송장 수집, 운영자 수동 입력 중 어떤 방식으로 입력되어도 즉시 자동저장된다.
- 소싱라이프 송장 자동 수집 ON은 발송대기 상태에서 소싱라이프에 발급된 국내송장을 자동으로 가져오는 기능이다.
- 소싱라이프 송장 수집은 운영자가 버튼을 눌러 소싱라이프 주문번호 기준으로 발급된 국내송장을 조회하는 기능이다.
- 소싱라이프 송장 수집 대상은 소싱라이프 주문번호가 있고 국내송장이 없는 발송대기 주문이다.
- 수동 입력은 운영자가 국내 택배사와 국내송장번호를 직접 입력하는 기능이다.
- 자동 배송중 처리 ON은 국내송장이 입력되는 즉시 배송중 처리를 시도하고 배송중으로 넘기는 기능이다.
- 자동 배송중 처리 OFF일 때는 국내송장이 입력되어도 운영자가 `배송중 처리` 버튼을 눌러야 배송중으로 이동한다.
- 배송중 처리는 국내송장이 있는 발송대기 주문만 대상으로 한다.
- 배송중 처리가 성공하면 주문 상태는 배송중으로 변경된다.
- 상품준비에서 `수동구매 완료`를 사용하는 경우 송장번호 없이 `발송대기 처리`가 가능하다.
- `수동구매 완료`에서 송장번호를 입력하고 `발송대기 처리`를 누르면 송장번호만 저장된 상태로 발송대기에 남는다.
- `수동구매 완료`에서 송장번호를 입력하고 `배송중 처리`를 누르면 저장과 함께 배송중으로 이동한다.
- 배송중 상태에서는 마켓 API로 송장 변경을 자동 전송하지 않는다. 변경된 송장번호가 있으면 화면에 표시해 운영자가 마켓에서 직접 확인할 수 있게 한다.

## 9. 단계별 처리 건수 표시

- 주문수집 본문 상단 탭에는 단계별 주문 건수를 표시한다.
- 일반 주문 표시 대상은 신규주문, 상품준비, 발송대기, 배송중, 배송완료다.
- 별도 `전체` 탭은 현재 화면에 제공하지 않는다.
- 클레임 처리 건수는 취소/반품/교환 화면에서 별도로 표시한다.
- 배송완료 상태는 마켓 배송완료와 구매확정 주문을 포함하는 조회 상태이며, 구매확정 여부는 별도 속성으로 저장할 수 있다.

## 10. 현재 MVP 데이터/기술 전제

- 현재 주문관리 MVP는 백엔드 없이 프론트와 mock data 중심으로 구현되어 있다.
- 주문 목록은 `lib/mock-data/orders.ts`의 더미 데이터를 기준으로 표시한다.
- 소싱라이프 후보는 `lib/mock-data/sourcing-life.ts`의 더미 데이터를 기준으로 표시한다.
- 소싱 매칭, 소싱 결제, 송장 수집 결과는 브라우저 저장소를 사용해 화면 동작을 검증한다.
- 사용 중인 저장소 키는 `jumunpangpang.syncedInvoices`, `jumunpangpang.sourcingMatches`, `jumunpangpang.sourcingPayments`다.
- React Query는 의존성으로 포함되어 있으나 현재 주문관리 MVP의 주요 주문 데이터 흐름은 mock data와 클라이언트 상태 중심이다.
- Zustand는 현재 대시보드 등 클라이언트 상태 관리 기반으로 사용한다.
