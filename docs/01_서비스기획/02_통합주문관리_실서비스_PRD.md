# 통합 주문관리 실서비스 PRD

## 1. 제품 한 문장

커머스라이프는 해외구매대행 셀러가 5개 판매처의 주문을 수집하고, 주문상품을 타오바오 SKU와 매칭해 소싱라이프에서 구매하며, 국내송장·직접전달·취소·반품·교환까지 한 화면에서 처리하는 독립 주문관리 서비스다.

## 2. 해결할 문제

해외구매대행 셀러는 주문 1건을 처리하기 위해 판매자센터, 타오바오, 소싱 도구, 결제, 배송 추적, 엑셀을 오간다. 이 과정에는 다음 손실이 있다.

- 주문 누락과 중복 수집
- 마켓 상품옵션과 타오바오 SKU의 반복 대조
- 잘못된 옵션·수량·가격으로 인한 오구매
- 개인통관고유부호 불일치
- 송장 복사·붙여넣기와 발송 실패
- 마켓 상태와 실제 해외물류 상태의 혼동
- 취소가 들어왔는데 타오바오 구매가 진행되는 경합
- 반품·교환의 회수·환불·재배송 누락
- 마켓 API 실패를 성공으로 오해하는 문제
- 처리자와 변경 이유를 확인할 수 없는 문제

이 제품의 핵심 가치는 단순한 주문 모아보기가 아니라 “마켓 주문에서 소싱 실행까지의 재입력을 제거하면서도 실패와 예외를 숨기지 않는 것”이다.

## 3. 목표 사용자

### 3-1. 1인 해외구매대행 셀러

- 하루 수 건에서 수십 건을 직접 처리한다.
- 마켓별 판매자센터 전환과 수작업을 줄이고 싶다.
- 설정이 쉽고 실패 이유가 명확해야 한다.

### 3-2. 소규모 운영팀

- 여러 스토어와 담당자를 운영한다.
- 상품 매칭과 주문 처리를 나누어 수행한다.
- 담당자, 처리이력, 권한, 일괄 작업이 필요하다.

### 3-3. 운영 관리자

- API 계정 상태, 주문 누락, 실패 작업을 관리한다.
- 마켓과 내부 상태의 정합성을 확인해야 한다.
- 재처리와 장애 대응 근거가 필요하다.

### 3-4. 소싱라이프 운영

- 구매대행 신청, 결제, 상품 구매, 물류 이벤트를 주문관리와 연결한다.
- 잘못된 옵션·중복 주문·취소 경합을 줄여야 한다.
- 마켓 주문과 소싱 주문을 상호 추적해야 한다.

## 4. 핵심 사용자 작업

1. 여러 판매처 계정을 연결하고 정상 수집 여부를 확인한다.
2. 오늘 처리할 신규주문과 클레임을 한 작업함에서 확인한다.
3. 주문상품을 타오바오/소싱라이프 상품과 매칭한다.
4. 이전에 승인한 같은 마켓 SKU 매칭을 재사용한다.
5. 가격·재고·통관정보를 확인하고 소싱라이프 구매를 신청한다.
6. 결제완료 후 선택한 배송대행지 사이트를 열고 주문서를 자동입력해 접수한다.
7. 접수와 동시에 발급된 국내송장을 저장하고 자동 또는 수동으로 마켓 배송중 처리한다.
8. 취소·반품·교환을 마켓과 소싱라이프 양쪽에서 끝까지 추적한다.
9. 실패한 수집·발송·클레임을 안전하게 재시도한다.
10. 누가 언제 무엇을 처리했는지 확인한다.

## 5. 제품 원칙

### 5-1. 성공을 추정하지 않는다

외부 API가 명확히 성공했거나 후속 조회로 확인된 경우에만 최종 성공으로 표시한다. timeout은 실패나 성공으로 단정하지 않고 확인 중으로 둔다.

### 5-2. 공통 UI와 마켓별 규칙을 함께 제공한다

사용자는 하나의 주문관리 화면을 사용하지만, 필수 입력값·가능 상태·사유코드·처리 순서는 마켓별 adapter와 capability로 결정한다.

### 5-3. 주문상품이 처리 단위다

한 주문에 여러 상품이 있고 일부만 취소·발송될 수 있으므로 주문 헤더가 아니라 상품주문/주문라인을 액션 단위로 사용한다.

### 5-4. 매칭은 재사용 가능한 자산이다

주문마다 임시 저장하지 않는다. 마켓 상품·옵션과 타오바오 SKU의 승인된 관계를 버전으로 관리한다.

### 5-5. 상태 축을 분리한다

마켓 상태, 내부 작업단계, 소싱, 구매, 실제 배송, 클레임, 동기화 상태를 한 개의 상태값으로 합치지 않는다.

### 5-6. 위험한 자동화는 사용자 통제를 둔다

유료 구매, 판매자 취소, 반품 거부, 교환 재배송처럼 비용·고객 영향이 큰 작업은 명확한 확인과 결과 추적을 요구한다.

### 5-7. 미지원 기능을 가짜로 흉내 내지 않는다

직접전달이나 클레임 액션을 마켓이 지원하지 않으면 MANUAL_FALLBACK 또는 UNSUPPORTED로 표시한다. 임의 송장과 거짓 성공 상태를 만들지 않는다.

- 회사/사용자/역할과 개인정보 보호
- 5개 판매처 다중 계정 연결
- 최초·증분 주문 및 클레임 수집
- 통합 주문 목록과 전체/작업단계별 조회
- 개별·일괄 주문확인
- 판매자 취소와 구매자 취소 요청 처리
- 타오바오/소싱라이프 상품·SKU 영구 매칭
- 매칭 자동 재사용과 구매 전 가격·재고 재검증
- 소싱라이프 구매신청·결제상태·송장 연동
- 외부구매 배송처리
- 일반 송장 발송과 마켓별 직접전달
- 취소·반품·교환 세부 상태와 마켓별 액션
- 동기화센터, 실패 작업함, 재시도, 대사
- 주문·매칭·구매·송장·클레임 처리이력
- 감사로그와 비밀키 암호화

### 6-2. P1 운영 고도화

- 배송추적과 고객 단계별 알림

- 문의관리와 주문 연결

- 세부 권한과 2인 승인
- 소싱라이프 취소·환불 복구 자동화

### 6-3. P2 차별화

- 이미지·상품명·옵션 AI 자동매칭

- 문의·클레임 답변 초안

- 타오바오 직접 로그인·직접 결제: 소싱라이프 계약과 직접 구현 책임모델 비교 후 단계 선택

- 카드 결제: 카드번호 직접 보관 대신 PG 토큰화·승인·환불 정책 검증
- 직접전달: 공식 지원과 실계정 UAT가 확인된 마켓부터 선택

## 7. 전체 업무 흐름

### 7-1. 연결과 최초 수집

마켓 선택 → 인증정보 입력 → 서버 연결검증 → 판매자/스토어 확인 → capability 확인 → 초기 수집 범위 선택 → 최초 수집 → 판매자센터 대사 → 활성화

연결 성공은 필수값 입력이 아니라 실제 읽기 API 성공과 판매자 식별 일치로 판정한다.

### 7-2. 신규 주문

마켓 결제완료 → 증분 수집 → 중복 제거 → 신규주문 작업함 → 배송·통관정보 검증 → 주문확인 → 상품준비

주문확인 중 구매자 취소가 확인되면 주문확인을 중단하고 클레임 작업으로 전환한다.

### 7-3. 매칭

기존 승인 매핑 조회 → 있으면 자동 적용 → 없거나 검토 필요면 이미지/키워드/URL 후보 → 상품 선택 → SKU·옵션·수량 배수 선택 → 승인 저장 → 주문별 선택 snapshot

매칭은 원본 마켓 상품 ID와 옵션 ID를 기본 키로 사용한다. 옵션명이 같다는 이유만으로 다른 스토어 상품에 자동 공유하지 않는다.

### 7-4. 소싱라이프 구매

통관정보 검증 → 가격·재고·SKU 재조회 → 비용·수량 확인 → 구매대행 신청 → 소싱라이프 결제화면 → 결제 결과 대사 → 선택 배송대행지 사이트 열기 → 주문서 자동입력 → 접수 → 국내송장 즉시 수신 → 중국 구매·배송·통관 이벤트 동기화

결제 결과, 배송대행지 접수, 국내송장은 별도 사건으로 저장한다. 다만 연결 대상은 접수 응답에서 국내송장을 즉시 발급하는 배송대행지로 제한한다. 화면의 `접수대기`와 `접수신청`은 동일 단계이며 정상 응답이면 별도 장기 송장대기 상태를 만들지 않는다. 응답 실패·유실 시 결제 성공은 보존하고 접수 재시도 또는 결과 대사를 수행한다.

### 7-5. 외부 구매

소싱라이프를 사용하지 않고 직접 구매한 주문은 `외부구매 배송처리`에서 배송대행지로부터 받은 택배사와 국내송장번호만 등록한다. 구매처·상품 URL·구매일·금액·증빙은 주문관리에서 입력받지 않는다. 처리된 주문은 구매경로를 외부구매로 구분하며, 자동 배송중 처리 OFF이면 발송대기, ON이면 마켓 송장 발송 성공 후 배송중으로 이동한다.

### 7-6. 마켓 발송

실제 국내송장 확보 → 택배사 코드 변환·검증 → 자동 또는 수동 발송명령 → 마켓 성공 확인 → 내부 배송중 → 실제 배송추적 → 배송완료 → 마켓 구매확정 수집

소싱라이프 결제완료 주문은 자동 배송중 처리 설정과 관계없이 내부 `SHIPPING`으로 이동한다. OFF는 마켓을 결제완료로 유지하고, ON은 국내송장 확보 직후 마켓 발송 명령을 실행한다. 마켓 성공 여부와 내부 배송중 관리는 별도 축이며, 실패해도 결제 사실과 내부 `SHIPPING`은 유지한다. 외부 구매는 OFF일 때 기존 `READY_TO_SHIP`을 사용한다.

배송중 작업함은 소싱 결제완료부터 배송완료까지의 통합 관리 구간이다. 배송중과 배송완료 목록 `처리하기`에는 버튼을 표시하지 않고, 행 자세히 보기에서 `소싱상품관리`, `배송추적`과 `배송중 처리` 시작 전 `운송장 수정`을 제공한다. 처리 명령을 접수한 순간부터 운송장 수정은 잠근다. `소싱상품관리`는 결제완료부터 배송완료까지 항상 유지한다. 배송완료 전 조건부 `반품·환불 신청`은 이 화면 안에서 진행하며, 중국 판매자 대화와 기존 환불 내역은 배송완료까지 유지한다.

### 7-7. 직접전달

마켓 capability 확인 → 공식 필수값 생성·검증 → 사용자 확인 → 마켓 직접전달 처리 → 마켓 결과 저장

직접전달은 마켓에 제출하는 방식이며 실제 국내배송과 분리한다. 구매와 실제 국내송장이 완료되기 전에는 내부 배송중 완료조건을 충족하지 않는다.

스마트스토어·11번가는 계정 연동 시 배송중 처리 기본값을 `송장전송` 또는 `직접전달` 중 하나로 필수 저장한다. 쿠팡·G마켓·옥션은 `송장전송`으로 고정한다. 주문의 `배송중 처리`는 주문별 선택을 받지 않고 백엔드가 계정 기본값을 적용하며, 일괄 처리도 계정별 설정에 따라 자동 분리한다. 전송 후 API 정정은 실행하지 않고 마켓 관리자 수동 수정과 재수집으로 처리한다.

### 7-8. 취소

취소 접수 → 주문·구매·배송 최신 상태 확인 → 처리 가능 액션 계산 → 마켓 취소 승인/거부 또는 판매자 취소 → 소싱 구매 중단/환불 작업 → 결과 대사 → 완료

마켓 취소가 성공해도 소싱 환불이 남으면 전체 작업을 완료로 숨기지 않는다.

### 7-9. 반품

반품 접수 → 사유·귀책·수량 확인 → 승인/거부/보류 → 회수방법·회수송장 → 입고·검수 → 마켓 환불 → 소싱라이프 비용·환불 정리 → 완료

### 7-10. 교환

교환 접수 → 승인/거부/보류 → 회수 → 입고·검수 → 교환품 확보 → 재배송송장 → 마켓 교환 재배송 → 완료

기존 배송송장, 회수송장, 교환 재배송송장을 서로 다른 배송으로 저장한다.

## 9. 핵심 화면 요구사항

### 9-1. 작업함

- 주문확인 필요
- 매칭 필요·재검토
- 통관정보 확인 필요
- 구매 실패·부분구매
- 송장대기·발송실패
- 오늘 마감 임박
- 처리기한 임박 클레임
- 동기화·인증 오류

각 카드에서 주문 목록으로 이동하고 현재 권한으로 실행 가능한 다음 액션을 표시한다.

### 9-2. 전체 주문 목록

- 주문 헤더와 상품주문을 시각적으로 구분한다.
- 마켓, 스토어, 주문·상품주문번호, 상품, 구매자, 수취인, 통관부호, 송장, 소싱주문번호를 검색한다.
- 상태별 저장 필터와 컬럼 프리셋을 지원한다.
- 현재 UI의 주요 컬럼은 유지하되 동기화 오류와 작업 필요 표시를 추가한다.
- 대량 선택은 현재 검색 결과 전체가 아니라 명시적으로 선택한 상품주문만 처리한다.

### 9-3. 주문 상세

- 주문상품과 금액
- 마켓 원상태와 내부 정규화 상태
- 수취정보와 통관 검증
- 매칭 버전과 소싱 SKU
- 구매·결제·환불
- 중국·국제·통관·국내 배송
- 클레임
- 처리 타임라인과 기술 시도
- 현재 가능한 액션과 불가 사유

원문 API payload는 일반 운영자에게 그대로 노출하지 않고 권한 있는 진단 화면에서 마스킹해 제공한다.

### 9-4. 매칭관리

- 마켓·스토어·상품·옵션 검색
- 연결된 소싱 상품과 SKU
- 수량 배수, 가격한도, 대체 SKU
- 활성·검토필요·품절·무효
- 마지막 가격·재고 검증시각
- 생성자·승인자·버전·변경 이유
- 주문별 사용 이력

### 9-5. 동기화센터

- 계정별 마지막 성공·시도·지연
- 수집 작업의 읽기 범위·cursor·건수
- 외부 쓰기 명령의 pending·성공·실패·확인중
- 인증 만료·권한 부족·호출 제한
- 실패 단건 재시도, 범위 재수집, 재인증
- 마켓과 내부 상태 불일치 대사

사용자에게 “성공” 토스트만 보여주지 않고 결과가 확정될 때까지 상태를 추적한다.

## 10. 플랫폼 capability 정책

각 마켓 adapter는 액션별로 다음 값을 제공한다.

| 값 | 의미 | UI |
|---|---|---|
| API | 공식 API로 실행 가능 | 버튼과 마켓별 입력 폼 |
| MANUAL_FALLBACK | 판매자센터에서 실행 후 재수집 | 단계별 안내와 재동기화 |
| UNSUPPORTED | 해당 마켓·상태에서 불가 | 버튼 숨김, 불가 사유 |

capability 예시:

- 주문·클레임 읽기
- 주문확인
- 일반 송장 발송
- 송장 정정
- 직접전달
- 판매자 취소
- 구매자 취소 승인·거부
- 반품 승인·거부·보류·입고·환불
- 교환 승인·거부·회수·재배송
- 구매확정 조회

capability는 코드 상수만이 아니라 공식문서 버전·확인일·실계정 UAT 결과와 연결한다.

## 13. 성과 지표

| 지표 | 정의 |
|---|---|
| 주문수집 완전성 | 판매자센터 대상 주문 대비 내부 수집 비율 |
| 수집 지연 | 마켓 변경시각부터 내부 반영까지 |
| 자동 매칭 재사용률 | 신규 주문상품 중 승인 mapping 자동 적용 비율 |
| 매칭 수정률 | 자동 적용 후 사용자가 다른 SKU로 바꾼 비율 |
| 주문 처리시간 | 수집부터 구매·발송 준비 완료까지 |
| 복사·붙여넣기 제거율 | 수동 상품URL·옵션·송장 재입력 없이 처리한 비율 |
| 외부 명령 성공률 | 확정 성공 / 전체 명령 |
| UNKNOWN 해소시간 | 결과 불명 명령이 대사될 때까지 |
| 클레임 기한 준수율 | 마켓 처리기한 안에 조치된 비율 |
| 판매자센터 병행률 | 내부에서 완료하지 못하고 수동 처리한 비율 |
| 오류 복구시간 | 감지부터 정상화까지 |

초기 북극성 지표는 “상품주문 1건을 수집해 올바른 SKU로 구매·발송 준비까지 완료하는 중앙값 시간”으로 둔다. 품질 가드레일은 주문 누락, 중복구매, 잘못된 SKU 구매, 거짓 성공 표시 0건이다.
