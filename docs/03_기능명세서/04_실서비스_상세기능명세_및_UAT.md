# 실서비스 상세기능명세 및 UAT

## 1. 공통 완료 규칙

모든 외부 작업은 다음 상태를 사용한다.

- QUEUED: 접수
- RUNNING: 실행 중
- VERIFYING: 결과 확인 중
- SUCCEEDED: 외부 상태까지 확인
- PARTIAL: 일부 대상 성공
- RETRYING: 재시도 예정
- FAILED: 사용자 수정 후 재실행 가능
- NEEDS_ATTENTION: 자동 판단 불가

화면의 최종 성공은 SUCCEEDED만 사용한다. 요청 접수와 외부 처리 성공을 같은 토스트로 표현하지 않는다.

모든 요구사항은 정상, 실패, 부분성공, 중복, 경합 시나리오를 갖는다.

## 2. 마켓 계정

### ACC-001 계정 등록

- 스마트스토어, 쿠팡, 11번가, G마켓, 옥션의 여러 계정을 등록한다.
- 표시 스토어명과 외부 seller/channel ID를 분리한다.
- 비밀키는 서버에만 저장하고 응답에서 마스킹한다.

검증:

- 정상 키는 실제 읽기 API와 판매자 ID 일치 후 CONNECTED.
- 잘못된 키는 저장 가능하더라도 UNVERIFIED로 두고 활성 수집을 막는다.
- 같은 외부 seller ID를 같은 tenant에 중복 등록하지 않는다.
- 다른 tenant의 같은 seller ID는 별도 권한으로 취급한다.

### ACC-002 계정 상태

- CONNECTED, EXPIRING, EXPIRED, REVOKED, PERMISSION_ERROR, IP_ERROR, DISABLED를 표시한다.
- 마지막 성공 호출, 키 만료, 갱신 가능일, 마지막 실패를 표시한다.
- 만료 계정의 쓰기 명령을 접수하지 않는다.

### ACC-003 capability

- 주문확인, 송장, 송장정정, 직접전달, 취소, 반품, 교환의 API/MANUAL_FALLBACK/UNSUPPORTED를 저장한다.
- 공식문서 확인일과 UAT 결과를 capability에 연결한다.
- UNKNOWN을 API 가능으로 취급하지 않는다.

## 3. 주문·클레임 수집

### SYNC-001 최초 수집

- 계정 활성화 전 기본 기간을 읽는다.
- 모든 페이지를 저장한 후 완료한다.
- 원문, 정규화 결과, 생성·수정·무변경·오류 건수를 보존한다.

### SYNC-002 증분 수집

- 계정·스트림별 cursor/watermark를 사용한다.
- 안전 overlap 구간을 다시 읽고 외부 ID로 중복 제거한다.
- cursor는 성공 트랜잭션에서만 전진한다.

### SYNC-003 클레임 별도 수집

- 일반 주문 목록에서 클레임을 완전히 제공하지 않는 마켓은 취소·반품·교환 API를 별도 조회한다.
- 주문 이벤트와 클레임 이벤트가 순서가 바뀌어도 최신 provider 시각을 기준으로 한다.

### SYNC-004 수동 수집

- 예약 수집과 같은 파이프라인을 사용한다.
- 같은 account+stream 작업이 실행 중이면 새 작업을 병합 또는 대기한다.
- 필터는 목록 조회 조건이며 기본 수집 범위를 암묵적으로 제한하지 않는다.

### SYNC-005 대사

- 하루 1회 이상 최근 주문·클레임을 재조회한다.
- 내부와 마켓의 상태·건수 차이를 목록으로 만든다.
- 자동 수정 가능, 사용자 확인 필요, 마켓 수동 처리 필요로 분류한다.

Acceptance:

| 경우 | 기대 결과 |
|---|---|
| 정상 | 모든 페이지 저장, cursor 전진, 건수 일치 |
| 실패 | cursor 유지, 오류와 retryable 표시 |
| 부분 | PARTIAL, 성공·실패 페이지/건수 보존 |
| 중복 | 같은 주문·이벤트가 한 행만 유지 |
| 경합 | 계정·stream 실행 1개, 오래된 event는 상태 역행 금지 |

## 4. 주문확인·취소

### ORD-001 개별 주문확인

- 액션 전 최신 마켓 상태와 활성 클레임을 조회한다.
- 허용 상태에서만 외부 명령을 실행한다.
- 성공 상품주문만 상품준비로 이동한다.

### ORD-002 일괄 주문확인

- 사용자가 체크한 상품주문만 대상이다.
- 마켓별 최대 batch 크기로 나눈다.
- 결과를 주문별로 표시한다.
- 실패만 재시도할 수 있다.

### ORD-003 판매자 취소

- 취소 가능 상태·사유코드를 마켓별로 제공한다.
- 수량과 주문상품을 명시한다.
- 구매가 시작됐으면 소싱 취소/환불 작업도 만든다.
- 판매자 취소 주문이 목록에서 사라지지 않고 종료·클레임 이력에서 조회된다.

Acceptance:

| 경우 | 기대 결과 |
|---|---|
| 정상 | 요청 접수 성공 후 `ON_HOLD / CANCEL_REQUESTED`와 작업자·시각 저장, provider 최종 `CANCELED` 확인 후 종료 |
| 실패 | 기존 내부 상태 유지, 오류·다음 조치 |
| 부분 | 성공 item만 보류 전환, 실패 item 잔류·주문번호별 사유 표시·모달 유지 |
| 중복 | 동일 멱등키 한 번만 효과 |
| 경합 | 주문확인 중 취소 발생 시 최신 마켓 상태와 클레임 우선 |

판매자 취소 UAT에는 다음 fail-closed 회귀를 포함한다.

- 수량 생략 요청은 실제 body에 `cancelQuantity`가 없고 provider 현재 `remainQuantity` 전체 취소로 해석된다. 명시적 부분수량은 `remainQuantity` 이하여야 하며 로컬 원수량은 `initialQuantity`와 일치해야 한다.
- 완료된 부분취소, 구매자 `currentClaim.cancel`, deprecated cancel, `ADMIN_CANCEL`, `CANCEL_REJECT` 흔적은 이 명령의 적용·미적용을 증명하지 못하므로 자동 재시도하지 않는다.
- 현재 반품·교환 claim이 있으면 판매자 취소와 충돌로 종료하고 쓰기를 호출하지 않는다.
- provider 상품주문 최종 상태 `CANCELED`만 적용 완료로 판정한다. causal baseline과 request channel allowlist 전 `SELLER_CANCEL UNKNOWN`은 수동 대사로 유지한다.
- 요청 접수 후 `ON_HOLD` 행이 `/orders?view=all`의 `처리보류` 필터에 남고 주문확인·매칭·소싱·외부구매·직접전달·발송·재취소가 모두 차단되는지 확인한다.
- PGlite 회귀 검증과 별개로 native PostgreSQL 16에서 migration, RLS, trigger, 역할 권한을 재검증하고 실제 네이버 계정 UAT 증빙이 승인되기 전 capability를 승격하지 않는다.

## 5. 영구 상품·옵션 매칭

### MAP-001 매칭 생성

- 원본 키: tenant, market account, market product ID, market option ID.
- 대상: source platform, product ID, SKU ID, 수량 배수.
- 생성자, 승인자, source, confidence, 검증시각을 저장한다.

### MAP-002 자동 재사용

- 동일 원본 키의 활성 mapping을 새 주문에 제안한다.
- 자동 적용 사실과 사용한 version을 표시한다.
- 주문별 selection을 snapshot으로 고정한다.

### MAP-003 구매 전 재검증

- 상품·SKU 존재, 재고, 가격, 최소수량, 제한품목, 중국 배송비를 확인한다.
- 가격 변동 허용한도는 tenant 설정을 사용한다.
- 품절·삭제·한도 초과는 구매를 막고 검토필요로 만든다.

### MAP-004 변경·대체

- 변경은 새 version으로 저장한다.
- 기본 SKU와 승인된 대체 SKU 순서를 관리한다.
- 사용 중인 과거 selection은 변경하지 않는다.

### MAP-005 수량 변환

- 1:N, N:1, 세트상품, 최소수량을 quantity multiplier와 구성으로 표현한다.
- 계산된 구매수량과 마켓 판매수량을 구매 전에 함께 보여준다.

Acceptance:

| 경우 | 기대 결과 |
|---|---|
| 정상 | 다음 동일 옵션 주문에 같은 SKU·수량 자동 제안 |
| 실패 | SKU 품절·삭제 시 구매 차단과 재매칭 |
| 부분 | 매칭된 item만 구매 가능 |
| 중복 | 동일 활성 mapping 1개 |
| 경합 | version 충돌 409, 구매가 사용한 version 불변 |

## 6. 소싱라이프 구매

### PUR-001 구매 전 점검

- 통관정보 상태
- SKU·재고·가격
- 원화·위안 가격
- 환율·수수료
- 중국 내 배송비
- 국제배송·관부가세 안내
- 제한품목

미확정 비용을 0원으로 표시하지 않는다.

### PUR-002 구매대행 신청

- 주문상품, selection version, SKU, 수량, 견적 version을 전송한다.
- idempotency key로 중복 신청을 막는다.
- item별 성공·실패를 저장한다.

### PUR-003 결제

- 결제정보를 주문관리 DB에 저장하지 않는다.
- 사용자는 소싱라이프 결제화면에서 최종 확인한다.
- redirect만으로 성공 처리하지 않고 조회/webhook으로 대사한다.

### PUR-004 상태

- 신청, 결제, 타오바오 구매, 배송대행지 접수, 국내송장 수신, 중국 발송, 환불을 분리한다.
- 결제완료 후 선택 배송대행지 사이트를 열고 주문서를 자동입력한다.
- `접수대기`와 `접수신청`은 같은 접수 단계로 처리하며, 연결 배송대행지는 정상 접수 응답에서 국내송장을 즉시 발급해야 한다.
- PAID를 국내송장 수신으로 간주하지 않고, 접수 또는 송장 응답 실패 시 PAID를 보존한 채 발송 단계 전환을 차단한다.

### PUR-005 외부 구매

- 사용자 액션은 `국내송장 등록`으로 제공하고 택배사와 국내송장번호를 필수 저장한다.
- 구매처, URL, 날짜, 금액, 통화, 증빙은 입력받지 않는다.
- 등록 결과는 외부구매로 구분하고 소싱라이프 구매 상태를 만들지 않는다.
- 자동 배송중 처리 OFF는 발송대기, ON은 마켓 송장 발송 성공 후 배송중으로 이동한다.

Acceptance:

| 경우 | 기대 결과 |
|---|---|
| 정상 | application·purchase ID와 결제 상태 저장 |
| 실패 | 결제완료로 표시 금지, 안전 재시도 |
| 부분 | 성공·실패 purchase item 분리 |
| 중복 | 더블클릭·중복 callback에도 구매 1개 |
| 경합 | 취소와 구매 동시 실행 시 잠금·최신상태, 이미 결제면 환불 작업 |

## 7. 국내송장·발송·직접전달

### SHIP-001 국내송장

- 소싱라이프 구매는 배송대행지 접수 응답, 외부 구매는 권한 있는 운영자 입력으로 생성한다.
- 실제 carrier·tracking과 source·수신시각을 저장한다.
- 택배사 코드·형식·중복을 검증한다.
- 정상 접수인데 국내송장이 없으면 오류로 분류하고 자동 배송중 처리를 실행하지 않는다.

### SHIP-002 일반 발송

- 마켓별 carrier code로 변환한다.
- 최신 클레임·마감·주문상태를 다시 확인한다.
- 외부 성공 item만 market invoice SUBMITTED와 SHIPPING으로 만든다.

### SHIP-003 자동 발송

- tenant/market account별 기본 OFF.
- 유효 국내송장, 구매 완료, 활성 클레임 없음, capability API일 때만 명령을 만든다.
- 수동 발송과 같은 command 파이프라인을 사용한다.

### SHIP-004 직접전달

- 스마트스토어 DIRECT_DELIVERY는 공식 capability로 제공한다.
- 쿠팡 DIRECT는 운영 승인 후 제공하며 숫자 마켓값과 실제 송장을 분리한다.
- 11번가·ESM은 검증 전 숨기거나 수동 대체를 표시한다.
- 직접전달 성공만으로 구매·실제배송 완료를 만들지 않는다.

### SHIP-005 송장 정정

- 마켓 지원 capability와 허용 상태를 확인한다.
- 새 revision을 만들고 이전 제출값은 SUPERSEDED로 보존한다.
- 미지원이면 판매자센터 안내와 단건 재동기화를 제공한다.

Acceptance:

| 경우 | 기대 결과 |
|---|---|
| 정상 | 송장 저장 후 마켓 성공 건만 배송중 |
| 실패 | 송장 보존, 발송대기, 오류 수정·재시도 |
| 부분 | 일괄 성공/실패 item 분리 |
| 중복 | 이미 발송됨은 재조회로 성공 대사 |
| 경합 | 취소 접수 후 발송 차단, 이미 발송이면 반품 흐름 제안 |

## 8. 취소·반품·교환

### CLM-001 공통 claim

- type, 주문상품, 수량, 사유, 귀책, 요청자, 기한, 원상태를 저장한다.
- 마켓 원상태와 내부 workflow를 분리한다.
- 기존 주문·구매·배송 상태를 보존한다.

### CLM-002 취소

- 구매자 요청 승인·거부와 판매자 취소를 구분한다.
- 전체·부분 수량을 지원한다.
- 소싱 구매 전이면 중단, 구매 후이면 환불 saga를 만든다.

### CLM-003 반품

- 접수, 승인, 거부, 보류, 해제, 회수, 입고, 환불, 완료를 지원한다.
- 회수지·방법·택배사·회수송장을 보존한다.
- 마켓과 소싱 환불 상태를 별도로 표시한다.

### CLM-004 교환

- 접수, 승인, 거부, 보류, 회수, 입고, 재배송, 완료를 지원한다.
- 회수송장과 교환 재배송송장을 분리한다.
- 대체 상품의 재고·구매 필요 여부를 확인한다.

### CLM-005 보상·복구

| 마켓 결과 | 소싱 결과 | 처리 |
|---|---|---|
| 성공 | 성공 | 완료 |
| 성공 | 실패/대기 | 소싱 환불 작업 필요 |
| 실패 | 성공 | 마켓 수동 복구 필요 |
| 확인중 | 확인중 | 대사 중 |

Acceptance:

| 경우 | 기대 결과 |
|---|---|
| 정상 | 마켓 외부 처리번호와 세부상태 저장 |
| 실패 | 완료 금지, 원인·다음 조치 |
| 부분 | item·수량별 결과 보존 |
| 중복 | claim·회수·환불 작업 1개 |
| 경합 | 취소/발송, 반품/교환 충돌은 최신상태와 상호배타 규칙 |

현재 공통 기반 구현:

- 마켓 inbound claim은 임대된 trusted worker context에서 tenant/account/correlation을 주입해 멱등 upsert한다. provider payload가 tenant를 선택하지 못한다.
- 네이버 주문 상세는 `quantityClaimCompatibility=true`로 조회하고 `currentClaim`·`completedClaims`의 취소·반품·교환을 공통 claim으로 정규화한다. 불가능한 부분수량·식별자 누락은 보정하지 않고 감사로그와 PARTIAL로 격리한다.
- 동일 event는 replay로 처리한다. 동일 claim·동일 수정시각에 새 주문상품 라인이 도착하면 기존 case를 덮어쓰지 않고 병합하며, 같은 라인의 상이 payload만 충돌로 격리한다. 오래된 provider 수정시각, 과도한 미래시각과 허용되지 않은 상태 역행은 원장 변경 없이 차단·기록한다.
- claim과 line은 주문 당시 상태 snapshot, 요청자, 귀책, 부분수량, 기한, 해결상태, 구매 보상상태를 독립 보존하며, line별 상태·수량·해결 결과도 암호화 사유와 함께 append-only event snapshot에 남긴다.
- 명시적인 0·음수·소수·비숫자 요청수량은 전체수량으로 보정하지 않고 격리한다. provider event 해시는 내부 raw snapshot 저장 경로를 제외해 동일 이벤트 재수집의 멱등성을 유지한다.
- 활성 claim 수량보다 주문상품 수량을 작게 줄이는 변경, claim case/line soft delete, terminal case와 line의 상이 종료상태를 DB에서 거부한다. 한 claim의 비재시도성 도메인·제약 오류는 savepoint로 격리하고 원본 snapshot·안전한 오류코드·감사로그를 저장한 뒤에만 cursor를 전진시킨다.
- 구매 보상 상태는 마켓 inbound가 덮어쓰지 않는다. DB가 신뢰된 주문상품 snapshot에서 최초 상태를 강제 파생하고 새 line 추가 시 trigger-only `SECURITY DEFINER` 함수로 `NOT_REQUIRED/UNKNOWN/NEEDS_ATTENTION`만 재계산한다. inbound worker는 보상 완료·참조 필드를 갱신할 권한이 없다.
- 클레임 작업함 목록과 상세는 signed cursor 조회를 제공하며 구매자·수취인·자유서술 사유를 마스킹한다. 오류·0건에서 demo를 표시하지 않는다.
- 클레임 작업함의 구매자 취소승인·반품승인/거부·회수·교환 재배송 쓰기는 아직 구현하지 않아 action availability를 명시적으로 불가로 반환한다. 주문 화면의 판매자 원인 취소 요청 코어만 별도로 구현되어 있으며, 계정별 실계정 UAT 전에는 `MANUAL_FALLBACK`으로 차단한다. UI나 API는 성공을 흉내 내지 않는다.

## 9. 동기화센터·실패 작업함

### OPS-001 계정 상태

- 마지막 성공·시도·지연, cursor, 오류, 키 만료를 표시한다.

### OPS-002 실행 결과

- 수집·명령별 대상, 성공, 실패, 무변경, cursor before/after를 표시한다.

### OPS-003 재처리

- 실패 item 재시도
- 범위 재수집
- 단건 재동기화
- 재인증
- UNKNOWN 결과 대사

### OPS-004 처리이력

- 사용자 의도 1개와 기술 시도 여러 개를 구분한다.
- 같은 업무 재시도는 중복 업무이력이 아니라 attempt로 쌓는다.

## 10. 권한·개인정보·감사

### SEC-001 역할

- OWNER, ADMIN, OPERATOR, VIEWER.
- 계정, 구매, 클레임 거부, 대량 내보내기를 별도 권한으로 분리한다.

### SEC-002 개인정보

- VIEWER는 마스킹.
- 통관부호·연락처·주소는 암호화.
- 일반 검색 로그에 원문을 남기지 않는다.
- 보존기간이 끝난 통관정보를 선택적으로 파기할 수 있어야 한다.

### SEC-003 감사

- 계정 변경, 수취정보 수정, mapping, 구매, 송장, 클레임, 재처리를 append-only 기록한다.
- 사용자, 역할, 대상, 전후값의 마스킹 diff, 시각, IP/session, correlation ID를 포함한다.

Acceptance:

- 권한 없는 쓰기는 외부 호출 전 403.
- 다른 tenant 데이터는 ID를 알아도 접근 불가.
- Secret·전체 통관부호·결제정보는 브라우저와 로그에 노출 0건.
- 동일 멱등 재시도는 업무 감사 1개, 기술 attempt만 추가.
