# 공통 주문 모델, 마켓 API, 소싱라이프 연동 기준

## 1. 문서 목적

이 문서는 실서비스 PostgreSQL 공통 모델과 demo 프론트 모델, 향후 마켓 API 확장 기준을 분리해 정의한다.
서버 원장의 1차 기준은 `db/migrations/`, `lib/server/`, `app/api/`이며 UI projection은 `types/order.ts`, `lib/constants/orders.ts`, `components/orders/`, `components/claims/`를 따른다.

## 2. 현재 데이터 흐름

| 영역 | 현재 구현 |
|---|---|
| 주문 원천 | 스마트스토어 변경주문·상세조회 worker → PostgreSQL, 미연동 환경은 명시적 demo 주문 |
| 주문 상태 변경 | outbound command/attempt와 provider 재조회·UNKNOWN 대사, demo만 client state |
| 소싱 매칭 저장 | 실주문 `source_*`·mapping 원장, demo만 `jumunpangpang.sourcingMatches` |
| 소싱 결제 | 실연동 미구현·hard stop, demo 가정만 `jumunpangpang.sourcingPayments` |
| 송장 저장/배송중 처리 | 실주문 국내송장 API·outbound command, demo만 `jumunpangpang.syncedInvoices` |
| 클레임 | 네이버 상세 `currentClaim`·`completedClaims` → claim case/line/event와 조회 전용 UI |
| 데이터 초기화 | demo localStorage만 삭제, 서버 원장은 영향 없음 |
| 서버 API | 로그인·계정·주문·클레임·소싱매핑·송장·명령·동기화 API 구현 |
| React Query | 실원장 cursor/query, 오류·빈 상태·재시도에 사용 |
| Zustand | 현재 대시보드 store 중심 |

주문관리는 소싱라이프 내부 기능이지만 주문수집의 원천은 마켓 주문이다.
소싱라이프에서 직접 생성하거나 주문한 내역은 주문관리의 주문수집 목록에 포함하지 않는다.
소싱라이프의 구매, 검수, 입고, 물류 상세 처리는 소싱라이프 기존 기능에서 진행하며 주문관리 데이터 모델로 흡수하지 않는다.

## 5. 주문 상태 모델

현재 타입 기준 주문 상태는 다음과 같다.

| 코드 | 라벨 | 정의 |
|---|---|---|
| `NEW` | 신규주문 | 마켓 결제완료 주문 수집 후 주문확인 전 |
| `PREPARING` | 상품준비 | 주문확인 후 소싱라이프 구매 또는 외부 구매 진행 |
| `READY_TO_SHIP` | 발송대기 | 구매·국내송장 저장 완료 후 마켓 배송중 처리 대기 |
| `SHIPPING` | 배송중 | 배송중 처리 완료 |
| `DELIVERED` | 배송완료 | 배송완료 또는 구매확정 |
| `ON_HOLD` | 처리보류 | 판매자 취소 요청은 접수됐지만 provider 최종 취소가 확인되지 않아 후속 작업을 차단한 상태 |
| `CANCELED` | 판매자취소 | 판매자 직접 주문취소 처리 |
| `CLAIM` | 취소/반품/교환 | 구매자 요청 또는 마켓 클레임 수집 |

현재 화면 흐름:

```text
NEW
→ 주문확인 또는 소싱하기
→ PREPARING
→ 소싱하기 또는 직접구매 국내송장 등록
→ 소싱 결제완료
→ 선택 배송대행지 주문서 자동입력과 접수
→ 접수 응답에서 국내송장 즉시 발급·저장
→ 자동 배송중 처리 OFF 또는 API 실패: READY_TO_SHIP
→ 자동 배송중 처리 ON + API 성공: SHIPPING
→ READY_TO_SHIP 주문은 운영자가 배송중 처리
→ SHIPPING
→ DELIVERED
```

구매자 요청 취소/반품/교환은 `CLAIM`으로 분리한다.
판매자 직접 취소 요청 접수 시에는 `ON_HOLD / CANCEL_REQUESTED`로 보류하고, provider 최종 `CANCELED` 확인 후에만 마감한다.
`/orders?view=all` 전체주문 탭은 `ON_HOLD`를 포함한 일반 주문을 조회하며 `처리보류` 상태 필터를 제공한다.

## 6. 소싱라이프 상태 모델

현재 타입 기준 소싱라이프 동기화 상태는 다음과 같다.

| 코드 | 의미 |
|---|---|
| `NOT_LINKED` | 소싱라이프 연결 전 |
| `MATCHING` | 매칭 진행 중 |
| `MATCH_SAVED` | 소싱완료 |
| `PAYMENT_READY` | 결제 가능 |
| `PAID` | 소싱라이프 결제 완료 |
| `INVOICE_RECEIVED` | 국내송장 수신 |
| `HOLD` | 소싱 처리보류 |

주문 목록의 `상태` 컬럼과 상태 필터는 소싱 진행 상태와 배송완료 주문의 구매확정 상태를 함께 사용한다.

소싱 진행 상태는 소싱라이프 동기화 상태와 별도로 다음 값을 사용한다.

| 코드 | 의미 |
|---|---|
| `MATCH_REQUIRED` | 매칭 필요 |
| `MATCHED` | 매칭 완료 |
| `EXTERNAL_PURCHASE` | 외부 구매 완료, 소싱라이프 미사용 |
| `SOURCED` | 소싱라이프 결제 완료 |
| `CHINA_SHIPPING` | 중국 배송중 |
| `CUSTOMS_CLEARANCE` | 통관 중 |
| `DOMESTIC_SHIPPING` | 국내 배송중 |
| `DELIVERED` | 배송완료 |

목록과 필터에서 사용하는 상태값 타입은 `OrderListStatus = SourcingProgressStage | ON_HOLD | PURCHASE_CONFIRMED`다. 한 주문은 표시된 배지에 따라 여러 목록 상태값을 가질 수 있다.
`status === DELIVERED` 주문은 모두 `DELIVERED` 목록 상태값을 가지며, `marketOrderStatus === PURCHASE_DECIDED`이면 `PURCHASE_CONFIRMED`를 추가한다.
`PURCHASE_CONFIRMED`는 소싱 진행 상태나 새 내부 주문 단계가 아니다. 배송완료 필터는 전체 배송완료 주문을, 구매확정 필터는 그중 구매확정 배지가 있는 주문을 조회한다.

## 8. 주문 액션 기준

| 액션 | 대상 | 현재 결과 |
|---|---|---|
| `주문확인` | `NEW` | `PREPARING`으로 이동 |
| `소싱하기` | `NEW` | 소싱 매칭 저장 + 주문확인 처리 후 `PREPARING` 이동 |
| `소싱하기` | `PREPARING` | 후보/옵션/수량·배대지 선택, 구매대행 신청과 결제. 실서비스는 결제 후 배대지 주문서 자동입력·접수로 국내송장을 즉시 받으며, 프로토타입은 이를 더미 송장으로 대체. 자동 배송중 처리 OFF는 `READY_TO_SHIP`, ON은 마켓 발송 성공 후 `SHIPPING` |
| `국내송장 등록` | `PREPARING` | 직접 구매한 주문의 택배사와 국내송장번호를 필수 저장하고 소싱 상태 `EXTERNAL_PURCHASE`를 저장한다. 자동 배송중 처리 OFF는 `READY_TO_SHIP`, ON은 마켓 발송 성공 후 `SHIPPING` |
| `배송중 처리` | `READY_TO_SHIP` | 마켓 발송 API 성공 후 `SHIPPING`으로 이동 |
| `주문취소` | 일반 주문 | 공식 사유·수량 확인 후 실주문은 UAT-gated 판매자 취소 명령 접수. 접수 성공은 `ON_HOLD / CANCEL_REQUESTED`, provider 최종 확인 후 `CANCELED`; 데모만 즉시 `CANCELED` 시연 |
| `취소처리` | 취소 클레임 | 실클레임은 조회 전용, 데모에서만 취소승인·거부 시연 |
| `반품처리` | 반품 클레임 | 사유와 진행단계 조회 중심 화면 |
| `교환처리` | 교환 클레임 | 사유와 진행단계 조회 중심 화면 |

배송중 상태에서 송장 수정 API 전송 버튼은 현재 제공하지 않는다.
변경된 송장번호 항목은 목록과 상세에 표시하지 않는다.

실클레임 작업함은 승인·거부·보류·입고·교환발송을 모두 비활성화하며 로컬 성공 상태를 만들지 않는다. 데모 취소 클레임은 `claimStatus`, `claimProcessedAt`, `failureReason`만 갱신하고 기존 소싱 상태를 보존한다.
주문 화면의 판매자 원인 취소는 이 구매자 클레임 승인과 분리된 명령이다. 스마트스토어 코어는 구현됐지만 계정별 UAT 전에는 `MANUAL_FALLBACK`이고, 반품/교환은 승인·회수·재발송 API를 호출하지 않는 조회 중심 화면이다.
`ON_HOLD` 주문은 전체주문 화면에 남고 `처리보류`와 `마켓 취소요청` 배지를 함께 표시한다. 이 상태에서는 주문확인·매칭·소싱·외부구매·직접전달·발송·재취소를 모두 차단한다.

## 9. 소싱라이프 연동 기준

신규주문:

- 신규주문의 `소싱하기`는 match-only 모드다.
- 후보/옵션 선택 후 매칭 정보를 저장한다.
- 저장과 동시에 주문확인을 처리해 상품준비로 이동한다.

상품준비:

- 소싱라이프 결제 요청 전 개인통관부호가 `P` + 숫자 12자리 형식인지 검증한다.
- 통관부호가 불일치하면 결제를 요청하지 않고, 내부 상태는 상품준비에 유지한다.

상품준비:

- `소싱하기`는 payment 모드다.
- 추천 소싱 상품, 옵션, 수량을 선택한다.
- 후보는 한국어 상품명, 중국어 상품명, 판매처, 원화/위안 상품원가를 표시한다.
- 옵션은 한국어 옵션명 아래 중국어 옵션명을 표시한다.
- 품절 옵션은 결제 버튼을 비활성화한다.
- 구매대행 신청은 `sourcingProgressStage=PAYMENT_WAITING`, `sourcingLifeSyncStatus=PAYMENT_READY`, 선택한 `sourcingForwarder`, `sourcingPaymentRequestedAt`을 저장한다.
- API 내부 projection은 `PAYMENT_READY → PAYMENT_WAITING`, `PAID/INVOICE_RECEIVED → SOURCED`, `EXTERNAL_PURCHASE → EXTERNAL_PURCHASE`로 고정한다. 목록 표시 projection에서는 `EXTERNAL_PURCHASE`도 `결제완료`로 합치고 구매경로는 상세 소싱상품 영역에서 구분한다.
- `INVOICE_RECEIVED`는 국내송장 수신 사건이며 중국 발송 증거가 아니므로 단독으로 `CHINA_SHIPPING`을 만들지 않는다.
- 외부구매의 `sourcingLifeSyncStatus`는 `NOT_LINKED`를 유지하며 소싱라이프 `PAID`로 변환하지 않는다. 자세히 보기에는 `외부구매` 배지와 외부 구매처 결제완료 안내를 표시한다.
- 판매자 취소의 `ON_HOLD`와 구매자 클레임 상태는 소싱 상태를 덮어쓰지 않는다. `sourcingLifeSyncStatus=HOLD`는 소싱 연동 자체의 보류에만 사용한다.
- 이 전환은 결제 성공이 아니므로 `sourcingLifeOrderId`, 실제 결제금액, 국내송장을 만들지 않는다.
- 이후 `결제하기`에서 별도 결제 화면으로 이동하고 결제 성공 응답을 받은 경우에만 구매완료 상태로 전환한다.
- 다음 단계에서 약관 동의와 결제 정보 입력 화면을 표시한다.

추후 실제 API 연동 시에는 소싱라이프 주문번호, 결제 상태, 국내송장 수신 여부를 주문에 반영한다.

## 10. 국내송장/배송 처리 기준

발송대기 화면:

- 소싱라이프·외부 구매 완료에는 국내송장이 필수이므로 발송대기 송장 유무 필터는 제공하지 않는다.
- 별도 `소싱라이프 송장 수집` 버튼은 제공하지 않는다.
- `자동 배송중 처리`는 구매 완료와 송장 확보 직후 마켓 배송중 처리를 자동 시도하는 토글이다.
- 소싱라이프 또는 외부 구매 완료 + 실제 국내송장 보유 + 자동 배송중 처리 ON인 일반 택배 주문은 마켓 발송 API 성공을 기준으로 `marketOrderStatus: DELIVERING`, `marketDeliveryMethod: DELIVERY`, 내부 `status: SHIPPING`을 함께 반영한다.
- 마켓 발송 API 실패 시 `uploadedToMarketAt`을 기록하지 않고 내부 `status: READY_TO_SHIP`을 유지한다. 내부 상태만 배송중으로 먼저 변경해서는 안 된다.
- 일괄 `배송중 처리`는 송장번호가 있고 직접전달로 이미 처리되지 않은 주문만 대상으로 한다.
- 발송대기의 `발송 처리`는 저장된 국내송장을 기준으로 네이버·쿠팡의 택배 발송 또는 직접전달 API를 즉시 호출한다. 구매 전 직접전달은 상품준비에서만 실행한다.
- 직접전달 API 성공은 `marketOrderStatus: DELIVERING`, `marketDeliveryMethod: DIRECT_DELIVERY`를 저장한다. 구매 완료와 실제 국내송장 보유 조건까지 충족하면 내부 `status`를 `SHIPPING`으로 변경하고, 아니면 기존 내부 단계를 유지한다.
- 체크된 주문이 있으면 전역 액션은 체크된 주문을 우선 대상으로 하고, 없으면 현재 필터로 보이는 발송대기 주문을 대상으로 한다.
- 조건에 맞지 않는 주문은 체크되어 있어도 배송중 처리 대상에서 제외한다.

국내송장 확인/정정:

- 발송대기 행에서는 구매 완료 시 저장된 택배사와 송장번호를 확인한다.
- 송장번호 수정값은 자동 저장한다.
- 송장이 누락된 주문은 정상 발송대기로 처리하지 않고 구매 완료 또는 연동 오류로 분류한다.

직접전달 입력:

- 상품준비에서는 네이버·쿠팡 주문에 한해 예외 액션 `마켓 직접전달`을 바로 실행한다. 발송대기에서는 `발송 처리` 모달에서 직접전달을 선택하고 즉시 실행한다.
- 네이버는 `deliveryMethod: DIRECT_DELIVERY`로 발송 처리한다. 소싱라이프 국내송장은 택배정보에 유지하되 마켓에는 전송하지 않는다.
- 쿠팡은 `deliveryCompanyCode: DIRECT`로 송장 업로드하며, 소싱라이프 국내송장은 택배정보에 유지하고 API 필수값인 `invoiceNumber`에는 시스템이 생성한 임의의 숫자 식별값을 전송한다.
- 성공하면 `marketOrderStatus`를 `DELIVERING`, `marketDeliveryMethod`를 `DIRECT_DELIVERY`로 저장한다. 내부 `status`는 변경하지 않는다.
- 구매와 송장이 완료된 `READY_TO_SHIP` 주문에서 직접전달 API가 성공하면 내부 `status`도 `SHIPPING`으로 변경한다. 직접전달을 먼저 처리한 상품준비 주문은 이후 구매 완료와 필수 송장 저장 시 같은 결과가 된다.
- 직접전달 주문의 마켓 배송 상태는 추적할 수 없으나, 화면의 택배정보는 소싱라이프에서 받은 실제 국내송장을 계속 표시한다.
- 소싱라이프 실제 국내송장의 배송완료를 수신하면 내부 `status`는 `DELIVERED`로 변경한다. 직접전달 마켓 주문은 `marketOrderStatus: DELIVERING`을 유지해 마켓 구매확정 전 상태를 구분한다.

배송중 화면:

- 택배사와 송장번호를 조회 전용으로 표시한다.
- 송장 수정 전송 버튼은 제공하지 않는다.

## 11. 마켓 API 매핑 기준

현재는 실제 API 호출 없이 mock으로 동작한다.
추후 API 연동 시 마켓별 응답은 내부 상태로 변환한다.

| 마켓 이벤트 | 내부 처리 |
|---|---|
| 결제완료 주문 수집 | 신규 주문이면 `NEW` 생성 |
| 주문확인 성공 | `PREPARING`으로 변경 |
| 소싱라이프 결제 완료 + 실제 국내송장 수신 | 일반 발송은 `READY_TO_SHIP`, 직접전달 완료 주문은 `SHIPPING`으로 변경 |
| 소싱라이프 결제 완료 + 실제 국내송장 없음 | 완료 반영 금지, 연동 오류로 처리 |
| 외부 구매 완료 + 실제 국내송장 있음 + 자동 배송중 처리 OFF | 일반 택배는 `READY_TO_SHIP`, 직접전달 처리 완료 주문은 `SHIPPING`으로 변경 |
| 외부 구매 완료 + 실제 국내송장 있음 + 자동 배송중 처리 ON | 일반 택배 마켓 발송 API 성공 후 마켓 `DELIVERING` 및 내부 `SHIPPING`으로 변경 |
| 외부 구매 완료 + 실제 국내송장 없음 | 완료 및 상태 변경 금지, 입력 오류로 처리 |
| 국내송장 배송중 처리 성공 | `SHIPPING`으로 변경 |
| 직접전달 발송처리 성공 | `marketOrderStatus: DELIVERING`, `marketDeliveryMethod: DIRECT_DELIVERY` 저장. 구매 완료 + 실제 국내송장 보유 시 `SHIPPING`, 아니면 내부 `status` 유지 |
| 직접전달 처리 후 실제 국내송장 수신 | 구매 완료 상태이면 내부 `status: SHIPPING`으로 변경 |
| 직접전달 주문의 실제 국내송장 배송완료 | 내부 `status: DELIVERED`로 변경, 마켓 상태는 별도 유지 |
| 네이버 구매확정 수집 | `marketOrderStatus: PURCHASE_DECIDED`, `marketPurchaseConfirmedAt` 저장. 판매자 실행 API 없이 조회 결과만 동기화 |
| 배송완료 또는 구매확정 수집 | `DELIVERED`로 변경 |
| 구매자 취소/반품/교환 요청 수집 | `CLAIM`으로 변경 |
| 판매자 직접 주문취소 요청 접수 성공 | `ON_HOLD`, `marketFulfillmentStatus: CANCEL_REQUESTED`로 변경하고 후속 액션 차단 |
| 판매자 직접 주문취소 최종 확인 | provider 상품주문이 `CANCELED`이면 내부 `CANCELED`로 마감 |

### 14-2. 유효한 상태 차이

| 조합 | 판정 이유 |
|---|---|
| 상품준비 + 마켓 배송중·직접전달 | 직접전달을 먼저 처리했지만 구매가 끝나지 않은 경우 |
| 상품준비 + 마켓 배송중·직접전달 | 직접전달만 완료되고 소싱라이프·외부 구매는 아직 완료되지 않은 경우. 국내송장 없음 |
| 배송중 + 결제완료/중국배송중/통관 중 | 국내송장이 선발급되어 마켓 발송은 완료됐지만 실제 해외 물류가 진행 중인 경우 |
| 배송완료 + 마켓 배송중·직접전달 | 실제 국내 배송은 완료됐지만 직접전달 마켓의 구매확정이 남은 경우 |

### 14-3. 모순으로 처리할 조합

| 조합 | 정상화 기준 |
|---|---|
| 신규주문 + 소싱 결제완료 또는 국내송장 보유 | 상품준비 이후 단계로 재분류 |
| 상품준비 + 구매 완료 + 일반 택배 마켓 발송 완료 | 배송중으로 이동 |
| 상품준비 + 구매 완료 + 직접전달 완료 + 국내송장 보유 | 배송중으로 이동 |
| 발송대기 + 직접전달 완료 + 국내송장 보유 | 배송중으로 이동 |
| 발송대기 + `marketDeliveryMethod: DELIVERY` + 마켓 결제완료 | 발송 성공 전에는 배송방법을 미선택으로 유지 |
| 배송중 + 일반 택배 + 국내송장 없음 | 발송 데이터 오류로 처리 |
| 배송중 + 직접전달 + 실제 국내송장 없음 | 정상 상태로 저장하지 않고 송장 수신 데이터 오류로 처리 |
| 배송완료 + 소싱 단계가 중국배송중/통관 중/국내배송중 | 소싱 단계를 배송완료로 정상화 |
| 소싱라이프 구매 완료 + 실제 국내송장 없음 | 구매 완료 반영을 취소하고 연동 오류로 처리 |
| 직접전달 완료 + 소싱라이프 구매 완료 + 실제 국내송장 없음 | 구매 완료와 내부 상태 전환을 모두 차단하고 연동 오류로 처리 |
| 외부 구매 완료 + 실제 국내송장 없음 | 구매 완료와 상태 변경을 차단하고 택배사·송장번호 입력 오류로 처리 |
| 직접전달 완료 + 외부 구매 완료 + 실제 국내송장 없음 | 외부 구매 완료와 내부 `SHIPPING` 전환을 모두 차단하고 입력 오류로 처리 |
| 직접전달 완료 + 구매 안 함 + 실제 국내송장 있음 | `구매 안 함` 상태 자체를 허용하지 않으며 송장 저장과 상태 전환을 차단 |

### 14-4. 별도 종료·예외 분기

- 판매자 취소는 신규주문, 상품준비, 발송대기에서만 직접 실행한다.
- 판매자 취소 요청 접수 후 `ON_HOLD`에서는 주문확인·매칭·소싱·외부구매·직접전달·발송·재취소를 실행하지 않는다. `SELLER_CANCEL UNKNOWN`도 causal baseline 구현 전에는 자동 재호출하지 않는다.
- 배송중 이후 취소·반품·교환은 일반 단계 버튼이 아니라 클레임 화면으로 분리한다.
- 클레임 진입 시 `previousStatus`를 저장해 요청 당시의 내부 단계를 보존한다.
- 현재 MVP의 반품·교환은 조회 중심이며 승인, 회수, 재배송 API 처리는 아직 구현 범위 밖이다.
- 실제 택배 배송완료 이벤트를 수신해 `DELIVERED`로 바꾸는 런타임 연동은 아직 mock 데이터로만 표현되어 있다.
