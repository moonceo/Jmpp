# 공통 주문 모델, 마켓 API, 소싱라이프 연동 기준

## 1. 문서 목적

이 문서는 주문팡팡의 주문수집, 주문상태 표준화, 소싱라이프 연동, 국내송장 처리, 마켓 송장전송을 개발자가 구현할 수 있도록 공통 데이터 모델과 API 처리 기준을 정의한다.

주문팡팡은 마켓별 API 응답을 그대로 화면에 노출하지 않고, 내부 공통 주문 모델로 변환한 뒤 주문관리 화면과 운영 기능에서 사용한다.

## 2. 연동 마켓 범위

최종 연동 대상은 네이버 스마트스토어, 쿠팡, 11번가, 지마켓, 옥션이다.

| 구분 | 마켓 | 처리 기준 |
|---|---|---|
| 초기 활성 | 네이버 스마트스토어 | 계정 등록, 주문수집, 주문확인, 송장전송 우선 구현 |
| 초기 활성 | 쿠팡 | 계정 등록, 주문수집, 주문확인, 송장전송 우선 구현 |
| 확장 예정 | 11번가 | 화면에는 확장 예정으로 관리하고 API 연동은 추후 활성화 |
| 확장 예정 | 지마켓 | ESM 계열 확장 대상으로 관리 |
| 확장 예정 | 옥션 | ESM 계열 확장 대상으로 관리 |

주문수집은 활성화된 모든 연동 계정을 대상으로 실행한다.
마켓별 필터와 계정별 필터는 주문 목록 조회 조건이며, 주문수집 실행 범위를 제한하는 기능이 아니다.

## 3. 마켓 계정 모델

주문팡팡은 마켓별 다중 계정 등록을 지원한다.
사용자는 네이버 스마트스토어, 쿠팡, 11번가, 지마켓, 옥션에서 운영 중인 판매자 계정 또는 스토어를 개수 제한 없이 등록할 수 있어야 한다.

| 필드 | 설명 |
|---|---|
| `id` | 주문팡팡 내부 연동 계정 ID |
| `market` | 네이버 스마트스토어, 쿠팡, 11번가, 지마켓, 옥션 |
| `accountName` | 판매자 계정명 |
| `storeName` | 스토어명 또는 판매채널명 |
| `authStatus` | 정상, 인증만료, 오류, 미연동 |
| `isActive` | 주문수집 대상 포함 여부 |
| `lastCollectedAt` | 마지막 주문수집 시각 |
| `lastCollectionResult` | 마지막 수집 성공/실패 결과 |
| `marketFeeRate` | 마켓 또는 연동 계정 단위 수수료율 |

계정별 인증이 실패해도 다른 정상 계정의 주문수집은 계속 진행한다.
계정 단위 실패는 전체 실패가 아니라 해당 연동 계정의 실패로 기록한다.

## 4. 주문 상태 모델

주문팡팡의 화면과 API는 내부 주문상태를 기준으로 동작한다.

| 코드 | 라벨 | 정의 |
|---|---|---|
| `NEW` | 신규주문 | 마켓 결제완료 주문이 수집되었고 주문확인 전인 상태 |
| `PREPARING` | 상품준비 | 주문확인 완료 후 소싱라이프 상품 매칭, 구매, 결제를 진행하는 상태 |
| `READY_TO_SHIP` | 발송대기 | 소싱라이프 결제 완료 후 국내송장 수집, 입력, 마켓 송장전송을 기다리는 상태 |
| `SHIPPING` | 배송중 | 국내송장을 마켓에 전송 완료한 상태 |
| `DELIVERED` | 배송완료 | 마켓 배송완료 또는 구매확정 주문 |
| `CANCELED` | 판매자취소 | 판매자가 직접 주문취소 처리한 종료 상태 |
| `CLAIM` | 취소/반품/교환 | 구매자가 요청했거나 마켓에서 수집된 취소, 반품, 교환 클레임 처리 대상 상태 |

기본 상태 흐름은 다음과 같다.

```text
NEW
→ 주문확인
→ PREPARING
→ 소싱하기
→ READY_TO_SHIP
→ 국내송장 자동저장
→ 송장전송
→ SHIPPING
→ DELIVERED
```

클레임은 구매자 요청 또는 마켓 클레임 수집으로 `CLAIM` 상태에 진입한다.
판매자가 직접 주문취소한 건은 `CANCELED` 상태로 마감하고 클레임 그룹에 포함하지 않는다.
취소/반품/교환 목록의 유형 필터는 `claimType`을 기준으로 구분한다.
클레임 목록의 주문상태 표시는 마켓의 상품 주문/배송 진행상태를 보존한 `previousStatus`를 기준으로 구분하며, `claimStatus`는 취소/반품/교환 요청 진행상태로 별도 표시한다.

## 5. 소싱상태 모델

소싱상태는 주문상태를 대체하지 않고, 소싱라이프 연동 진행도를 주문 단위로 표시한다.

| 코드 | 라벨 | 전환 기준 |
|---|---|---|
| `NOT_LINKED` | 소싱 전 | 소싱라이프 매칭 전 |
| `MATCHING` | 이미지 매칭 중 | 소싱 후보 조회 중 |
| `MATCH_SAVED` | 매칭 저장 | 후보와 옵션 선택 후 매칭 정보 저장 |
| `PAYMENT_READY` | 결제 가능 | 소싱라이프 결제 화면으로 이동 가능한 상태 |
| `PAID` | 소싱라이프 결제완료 | 소싱라이프 결제 완료가 주문팡팡에 반영된 상태 |
| `INVOICE_RECEIVED` | 국내송장 수신 | 국내송장이 수집되었거나 운영자가 입력한 상태 |
| `HOLD` | 처리 보류 | 필수정보 누락, 매칭 실패, 결제 실패, 송장전송 실패 |

`PAID`가 반영되면 주문상태는 `READY_TO_SHIP`으로 변경한다.
송장전송 실패는 주문상태를 `READY_TO_SHIP`으로 유지하고 소싱상태를 `HOLD`로 표시할 수 있다.

중복 방지 기준은 다음과 같다.

| 단위 | 기준 |
|---|---|
| 주문 단위 | `마켓 + 연동 계정 + 마켓 주문번호` |
| 주문상품 단위 | `마켓 + 연동 계정 + 상품주문번호` |

동일한 마켓 주문번호라도 연동 계정이 다르면 별도 주문으로 관리한다.

## 7. 주문수집 API 기준

주문수집 API는 활성화된 모든 연동 계정을 대상으로 실행한다.

| 기능 | 처리 기준 |
|---|---|
| 주문수집 실행 | 활성화된 모든 연동 계정의 결제완료 주문 조회 |
| 계정별 인증 실패 | 해당 계정만 실패 처리하고 다른 계정 수집은 계속 진행 |
| 중복 주문 | 공통 중복 방지 기준으로 신규/기존 주문 구분 |
| 상태 매핑 | 마켓 상태를 주문팡팡 내부 상태로 변환 |
| 실패 기록 | 연동 계정 단위 실패와 주문 단위 실패를 구분 |

초기 범위에서는 특정 판매처만 수집하거나 특정 계정만 수집하는 API를 제공하지 않는다.

## 8. 주문 액션 API 기준

| 액션 | 대상 상태 | 성공 결과 |
|---|---|---|
| `주문확인` | `NEW` | `PREPARING`으로 변경 |
| `선택 주문확인` | 선택된 `NEW` 주문 | 성공 건만 `PREPARING`으로 변경 |
| `소싱하기` | `NEW` | 매칭 저장과 주문확인을 함께 처리하고 `PREPARING`으로 변경 |
| `소싱하기` | `PREPARING` | 후보 확인, 옵션 선택, 소싱라이프 결제 화면 이동 |
| `송장전송` | `READY_TO_SHIP` + 국내송장 존재 | 마켓 전송 성공 시 `SHIPPING`으로 변경 |
| `주문취소` | `NEW`, `PREPARING`, `READY_TO_SHIP` | `CANCELED`로 변경하고 판매자 취소 사유와 취소일시 반영 |
| `취소처리` | `CLAIM` + 취소 요청 | 취소 상세 확인 및 취소승인/취소거부 전송 |
| `반품처리` | `CLAIM` + 반품 요청 | 반품 사유와 현재 진행단계 확인, 후속 반품 처리 화면 연결 |
| `교환처리` | `CLAIM` + 교환 요청 | 교환 사유와 현재 진행단계 확인, 후속 교환 처리 화면 연결 |
| `취소승인` | `CLAIM` + 취소 요청 | 마켓에 구매자 취소승인 전송 후 `취소승인 전송완료` 기록 |
| `취소거부` | `CLAIM` + 취소 요청 | 마켓에 구매자 취소거부 전송 후 `취소거부 전송완료` 기록 |

`주문취소`는 일반 주문 행 액션으로 제공하며, 주문상세 모달 하단의 다음 단계 버튼에는 포함하지 않는다.
구매자 취소 요청은 판매자 직접 주문취소와 구분해 `CLAIM` 상태에서 처리한다.
취소처리 화면과 목록에는 `previousStatus` 기준 실제 주문 진행상태를 표시해 승인/거부 판단에 사용한다.
`previousStatus`가 `SHIPPING` 또는 `DELIVERED`인 클레임은 `sourcingLifeOrderId`와 `domesticInvoice.trackingNumber`를 필수값으로 본다.
`previousStatus`가 `READY_TO_SHIP`이고 송장이 없는 클레임은 반품이 아니라 취소 요청 또는 출고중지 요청으로 본다.

## 9. 소싱라이프 연동 API 기준

`소싱하기`는 주문상태에 따라 동작 범위가 다르다.

| 주문상태 | 소싱하기 동작 |
|---|---|
| `NEW` | 소싱 후보 확인, 매칭 저장, 주문확인을 함께 처리 |
| `PREPARING` | 소싱 후보 확인, 옵션 선택, 매칭 저장, 소싱라이프 결제 화면 이동 |

소싱라이프 주문번호는 소싱라이프 주문 생성 성공 시점에 저장한다.
소싱라이프 결제 완료 여부는 소싱상태로 별도 관리한다.

소싱 후보가 없거나 적합하지 않은 경우 `후보 없음, 소싱라이프에서 찾기` 경로를 제공한다.
해당 경로는 운영자가 소싱라이프로 이동해 직접 검색 또는 이미지 검색으로 상품을 찾는 흐름이다.

## 10. 국내송장 처리 기준

국내송장은 `READY_TO_SHIP` 상태에서만 입력 또는 수집할 수 있다.

국내송장 입력 경로는 세 가지다.

| 경로 | 설명 |
|---|---|
| 자동수집 | 발송대기 주문을 대상으로 소싱라이프에서 발급된 국내송장을 자동 조회 |
| 송장 수동수집 | 운영자가 버튼을 눌러 소싱라이프에 발급된 국내송장을 조회 |
| 수동 입력 | 운영자가 국내 택배사와 송장번호를 직접 입력 |

어떤 경로로 입력되더라도 국내송장은 즉시 자동저장된다.
별도의 저장 액션은 제공하지 않는다.

자동 송장전송이 ON이면 국내송장 자동저장 직후 마켓 송장전송을 실행한다.
자동 송장전송이 OFF이면 운영자가 `송장전송` 버튼을 눌러야 마켓으로 전송한다.

송장전송 성공 시 주문상태는 `SHIPPING`으로 변경한다.
송장전송 실패 시 주문상태는 `READY_TO_SHIP`으로 유지하고 실패 사유를 표시한다.

## 11. 마켓 API 매핑 기준

마켓별 API 결과는 주문팡팡 내부 상태와 액션으로 변환한다.

| 마켓 API 이벤트 | 주문팡팡 처리 |
|---|---|
| 결제완료 주문 수집 | 신규 주문이면 `NEW` 생성 |
| 주문확인 성공 | `PREPARING`으로 변경 |
| 소싱라이프 결제완료 반영 | `READY_TO_SHIP`으로 변경 |
| 국내송장 마켓 전송 성공 | `SHIPPING`으로 변경 |
| 배송완료 또는 구매확정 수집 | `DELIVERED`로 변경 |
| 구매자 요청 또는 마켓 취소, 반품, 교환 수집 | `CLAIM`으로 변경 |
| 판매자 직접 주문취소 성공 | `CANCELED`로 변경 |

마켓마다 API 필드명과 상태명은 다르지만 주문팡팡 화면에서는 내부 상태 코드와 라벨만 사용한다.

## 12. 실패 및 재시도 기준

| 실패 구분 | 처리 기준 |
|---|---|
| 계정 인증 실패 | 해당 연동 계정에 실패 표시, 다른 계정 수집 계속 진행 |
| 주문수집 실패 | 실패 사유 기록 후 다음 수집에서 재시도 |
| 주문확인 실패 | 주문은 `NEW` 유지, 실패 사유 표시 |
| 소싱라이프 연동 실패 | 주문상태 유지, 소싱상태 `HOLD`, 실패 사유 표시 |
| 소싱라이프 결제 반영 실패 | 주문은 `PREPARING` 유지, 소싱상태 `HOLD` |
| 송장전송 실패 | 주문은 `READY_TO_SHIP` 유지, 소싱상태 `HOLD`, 실패 사유 표시 |

초기 주문관리 화면에서는 처리이력 기능을 제공하지 않는다.
상태 변경 로그와 작업 로그는 내부 진단 또는 추후 운영 기능으로 분리한다.
