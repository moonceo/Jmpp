# 실서비스 아키텍처, 데이터 모델, 동기화 기준

## 1. 목표 구조

초기 실서비스는 마켓별 마이크로서비스가 아니라 모듈형 모놀리스로 구성한다.

| 구성 | 책임 |
|---|---|
| Next.js Web/BFF | 사용자 화면, 인증된 조회·명령 접수, 결과 스트리밍 |
| PostgreSQL | 주문, 상태, 이벤트, 명령, 매칭, 감사로그의 유일한 원장 |
| Worker 프로세스 | 예약 수집, 외부 API 호출, 재시도, 대사 |
| Scheduler | 계정별 증분 수집과 야간 대사 작업 생성 |
| Secret Manager | 마켓 API Key, Secret, 토큰 암호화 보관 |
| 마켓 어댑터 | 스마트스토어, 쿠팡, 11번가, ESM의 인증·매핑·호출 |
| 소싱라이프 어댑터 | 상품/SKU 검색, 구매신청, 결제상태, 송장, 환불 |

초기 작업 큐는 PostgreSQL의 행 잠금과 lease로 구현한다. Redis나 Kafka는 PostgreSQL 큐가 실제 처리량·지연 목표를 충족하지 못한다는 측정 결과가 있을 때만 도입한다.

외부 API는 브라우저에서 직접 호출하지 않는다. 모든 비밀키 사용과 상태 변경은 서버 또는 worker에서 실행한다.

## 2. 모듈 경계

| 모듈 | 주요 책임 |
|---|---|
| identity | 사용자, 워크스페이스, 역할, 세션 |
| integrations | 마켓 계정, 자격증명, 연결 검증, capability |
| orders | 주문·상품주문 정규화, 조회 projection, 내부 작업단계 |
| sync | cursor, 실행, 원문 snapshot, 이벤트, 대사 |
| commands | 주문확인, 발송, 취소, 클레임 쓰기 작업 |
| sourcing | 소싱 상품/SKU, 영구 매핑, 주문별 선택 |
| purchases | 소싱라이프·외부 구매, 결제, 환불 |
| fulfillment | 실제 배송, 국내송장, 마켓 제출 송장 |
| claims | 취소·반품·교환 aggregate와 복구 작업 |
| audit | 사용자·시스템 변경 이력 |
| notifications | 계정 만료, 수집 지연, 고객 알림 |

모듈 간 직접 테이블 수정은 금지하고 application service를 통해 상태를 변경한다.

## 3. 테넌트와 권한

### 3-1. 핵심 엔티티

| 테이블 | 핵심 필드 | 주요 제약 |
|---|---|---|
| tenant | id, name, status, timezone | slug 대소문자 무시 유일 |
| app_user | id, auth_subject, email, status | auth_subject 유일 |
| tenant_membership | tenant_id, user_id, role | tenant+user 유일 |
| market_account | tenant_id, market, seller_id, secret_ref, auth_status | 활성 tenant+market+seller 유일 |

모든 업무 테이블에는 tenant_id를 필수로 둔다. API는 활성 membership을 확인하고, DB는 복합 외래키 또는 Row Level Security로 다른 tenant의 행을 참조하지 못하게 한다.

### 3-2. 기본 역할

| 역할 | 권한 |
|---|---|
| OWNER | 사용자·결제·마켓계정·주문 전체 |
| ADMIN | 마켓계정과 주문·클레임 운영 |
| OPERATOR | 주문, 매칭, 구매, 송장, 클레임 실행 |
| VIEWER | 마스킹된 조회 |

개인통관고유부호 원문 조회, 마켓 키 교체, 대량 내보내기는 별도 고위험 권한으로 분리한다.

### 3-3. 브라우저 세션과 서버간 인증

- 자체 로그인은 워크스페이스 slug·이메일·bcrypt 비밀번호를 확인하고, tenant/user/session ID가 서명된 HttpOnly 쿠키를 발급한다.
- 세션 원장은 `browser_sessions`에 보관하며 만료·로그아웃·관리자 폐기가 가능하다. 모든 API는 활성 세션과 활성 membership을 함께 확인한다.
- 변경 요청은 SameSite=Strict 세션 쿠키와 별도의 double-submit CSRF 쿠키·헤더가 모두 일치해야 한다.
- 인증 프록시나 내부 서비스는 최대 300초의 `x-internal-auth-context` HMAC 서명을 사용할 수 있으며 브라우저에 공유키를 전달하지 않는다.
- 앱 readiness는 DB 연결뿐 아니라 app role이 superuser·BYPASSRLS·테이블 소유자 계열이 아니며 대표 업무 테이블에 RLS가 켜져 있는지 확인한다.
- worker는 반대로 전용 non-superuser BYPASSRLS 역할만 허용한다. `DATABASE_URL`, `MIGRATION_DATABASE_URL`, `WORKER_DATABASE_URL`을 서로 바꿔 사용하지 않는다.

## 4. 주문 데이터 모델

현재 단일 Order.product 구조는 생산 데이터 모델로 사용하지 않는다.

### 4-1. sales_order

마켓의 주문 헤더를 저장한다.

- 내부 ID, tenant, market_account
- 외부 주문번호
- 주문·결제 시각
- 구매자 스냅샷
- 결제 총액과 통화
- 마켓 주문 원상태와 정규화 상태
- 마켓 최종 수정시각
- 최신 원문 snapshot
- optimistic lock version

유일 제약: market_account_id + external_order_id.

### 4-2. order_item

실제 처리 단위인 상품주문/주문라인을 저장한다.

- 외부 상품주문 ID 또는 결정적 source_line_key
- 마켓 상품 ID와 옵션 ID
- 주문 당시 상품명, 옵션명, 수량, 단가
- 내부 작업단계
- 마켓 상품주문 원상태
- 정규화 배송상태
- 구매확정 시각
- 마켓 최종 수정시각
- optimistic lock version

유일 제약:

- market_account_id + external_order_item_id
- 외부 item ID가 없으면 market_account_id + source_line_key

주문확인, 취소, 송장, 클레임은 order_item 단위로 실행한다. 여러 item을 한 요청으로 보내더라도 결과는 item별로 저장한다.

### 4-3. order_recipient

- 수취인명, 연락처, 주소, 상세주소, 우편번호
- 개인통관고유부호
- 배송메시지
- 정확 검색용 blind index
- 수정 version

민감값은 필드 암호화한다. 로그, 오류 메시지, 감사로그 diff에는 원문을 기록하지 않는다.

## 5. 독립 상태 축

한 개의 OrderStatus로 모든 상태를 표현하지 않는다.

| 상태 축 | 원장 |
|---|---|
| 운영자가 할 일 | order_item.internal_work_status |
| 마켓 주문 원상태 | sales_order/order_item의 market_status_raw |
| 정규화 마켓 배송상태 | order_item.market_fulfillment_status |
| 매칭 | 활성 order_item_sourcing_selection |
| 구매 | sourcing_purchase와 purchase_item |
| 실제 물류 | shipment |
| 마켓 송장 제출 | market_invoice |
| 클레임 | claim과 claim_item |
| 기술적 수집 | sync_run과 integration_event |
| 기술적 쓰기 | outbound_command |

현재 UI의 소싱필요, 소싱완료, 결제대기, 결제완료, 중국배송중, 통관 중, 국내 배송중, 배송완료는 위 원장에서 계산하는 read projection이다. 내부 `MATCH_PENDING_REVIEW`도 화면에서는 `소싱필요`로 투영한다.

CLAIM도 주문상태를 덮어쓰지 않는다. 활성 claim을 별도로 보존하고 클레임 작업함에 projection한다. 요청 당시 주문·구매·배송 상태를 잃지 않아야 소싱 취소비용과 처리 가능 액션을 판단할 수 있다.

## 6. 소싱 상품과 영구 매핑

### 6-1. sourcing_product

- tenant, 원천 플랫폼
- 타오바오/티몰/소싱라이프 상품 ID
- 정규화 URL
- 한국어·중국어 상품명
- 판매자 ID/명
- 썸네일
- 활성 상태와 마지막 관측시각

유일 제약: tenant + source_platform + external_product_id.

### 6-2. sourcing_sku

- sourcing_product
- 외부 SKU ID
- 옵션 속성과 한국어·중국어 라벨
- 옵션 fingerprint
- 마지막 가격, 통화, 재고, 확인시각

외부 SKU ID가 없을 때만 옵션 fingerprint를 대체 키로 사용한다.

### 6-3. product_sourcing_mapping

같은 마켓 상품의 다음 주문에 재사용하는 자산이다.

- tenant, market_account
- 마켓 상품 ID와 옵션 ID
- sourcing_sku
- 수량 배수
- 수동/자동/가져오기 출처
- 자동추천 신뢰도
- 활성, 보류, 무효 상태
- 버전, 유효 시작·종료
- 생성자, 승인자, 마지막 검증시각

활성 유일 제약: market_account + market_product_id + market_option_id.

매핑 변경 시 기존 행을 덮어쓰지 않고 유효기간을 닫고 새 버전을 만든다.

### 6-4. order_item_sourcing_selection

주문 당시 실제 선택을 고정한다.

- order_item
- mapping과 sourcing_sku
- 재사용/수동/자동 선택 출처
- 선택 수량
- 당시 상품명, 옵션, URL, 원가 snapshot
- 선택자와 시각

공용 mapping이 나중에 바뀌어도 과거 구매 내역은 변경하지 않는다.

## 7. 구매 모델

### 7-1. sourcing_purchase

- 구매방식: SOURCING_LIFE 또는 EXTERNAL
- 공급자 주문번호
- 구매 신청 idempotency_key
- DRAFT, SUBMITTED, ORDERED, PAID, PARTIAL, CANCELED, REFUNDED, FAILED
- 상품금액, 수수료, 총액, 통화
- 주문·결제·취소 시각
- 공급자 원상태와 최신 snapshot

### 7-2. sourcing_purchase_item

- purchase와 order_item 연결
- sourcing_sku와 실제 수량
- 단가·금액
- line별 구매·취소·환불 상태

하나의 구매에 여러 주문상품을 묶을 수 있고 하나의 주문상품을 여러 구매로 나눌 수 있다. 이 관계를 단일 sourcingLifeOrderId 필드로 축약하지 않는다.

결제, 타오바오 구매 성공, 중국 발송, 국내송장 발급은 서로 다른 사건이다. PAID만으로 국내송장이 존재한다고 판단하지 않는다.

## 8. 실제 배송과 마켓 송장

### 8-1. shipment

- source: SOURCING_LIFE, EXTERNAL, MANUAL
- leg: CHINA_DOMESTIC, INTERNATIONAL, CUSTOMS, KOREA_DOMESTIC
- purpose: CUSTOMER_DELIVERY, RETURN, EXCHANGE_REPLACEMENT
- 내부 표준 택배사, 실제 송장
- PENDING, LABEL_CREATED, IN_TRANSIT, CUSTOMS, OUT_FOR_DELIVERY, DELIVERED, EXCEPTION
- 출발·완료 시각

shipment_item으로 주문상품·수량을 연결해 합배송과 분리배송을 표현한다.

### 8-2. market_invoice

마켓에 제출한 배송방법과 값을 별도로 저장한다.

- order_item
- 실제 shipment 참조
- DELIVERY 또는 DIRECT_DELIVERY
- 마켓 택배사 코드
- 마켓에 전송한 송장값
- revision
- DRAFT, PENDING, SUBMITTED, REJECTED, SUPERSEDED
- outbound_command
- 제출시각과 응답코드

직접전달의 마켓용 임시 숫자와 실제 국내송장을 같은 필드에 저장하지 않는다.

## 9. 클레임 모델

### 9-1. claim

- source: MARKET, SELLER, INTERNAL
- 외부 claim ID와 dedupe key
- CANCEL, RETURN, EXCHANGE
- 공통 workflow 상태와 마켓 원상태
- 사유 코드·설명
- 요청·승인·거부·완료 시각
- 최신 snapshot과 version

공통 상태 흐름:

REQUESTED → UNDER_REVIEW → APPROVAL_PENDING → APPROVED 또는 REJECTED → COLLECTION_PENDING → IN_TRANSIT → RECEIVED → REFUNDED 또는 REPLACEMENT_SHIPPED → COMPLETED

취소는 필요 없는 중간 단계를 건너뛴다.

### 9-2. claim_item

- claim과 order_item
- 외부 claim line ID
- 요청 수량
- item별 workflow 상태
- REFUND, REPLACEMENT, REJECT, NO_ACTION 결과
- 환불금액

부분 취소·반품·교환을 위해 claim 수량은 주문상품 수량 이하로 검증한다.

반품 회수송장과 교환 재배송 송장은 shipment의 purpose와 claim을 연결해 관리한다.

### 9-3. 현재 공통 claim 원장 구현 경계

- `claim_cases`, `claim_lines`, `claim_events`를 주문·상품주문과 연결하되 주문·배송·소싱 상태를 덮어쓰지 않는 독립 aggregate로 저장한다.
- 외부 claim/event ID, provider 수정시각, dedupe key와 version으로 중복 수신 및 오래된 event의 상태 역행을 차단한다.
- 요청 당시 주문·상품·소싱·마켓 fulfillment 상태는 불변 snapshot으로 보존하고, 부분수량은 주문수량 및 다른 활성 claim 수량과 함께 검증한다.
- 자유서술 마켓 사유는 암호문과 `[PROTECTED]` 표시로만 저장한다. append-only event는 case·line별 암호문과 상태 snapshot을 보존하되 목록·상세·감사로그에는 평문을 반환하거나 기록하지 않는다.
- 구매 보상은 마켓 claim 완료와 합치지 않고 `NOT_REQUIRED`, `PENDING`, `IN_PROGRESS`, `SUCCEEDED`, `FAILED`, `NEEDS_ATTENTION`, `UNKNOWN`으로 별도 추적한다.
- 현재 쓰기는 trusted worker의 inbound snapshot upsert만 허용한다. 브라우저 API는 `GET /api/claims`, `GET /api/claims/{id}`만 제공하며 모든 provider action availability는 `false`다.
- 취소 승인·거부, 반품·교환 실행, 철회 등 외부 쓰기는 adapter·실계정 UAT·권한·UNKNOWN 대사가 완성되기 전까지 제공하지 않는다.

## 10. 원문, 이벤트, 동기화

### 10-1. market_raw_snapshot

append-only로 다음을 저장한다.

- 원천 시스템, object 종류, 외부 ID
- 원문 JSON
- payload hash
- adapter schema version
- 공급자 수정시각과 관측시각
- 보관기한

유일 제약: account + object_type + external_object_id + payload_hash.

### 10-2. integration_event

- POLL, WEBHOOK, RECONCILIATION 출처
- ORDER_PAID, ORDER_CHANGED, CLAIM_CREATED 등 표준 사건
- 외부 event ID 또는 결정적 dedupe_key
- raw snapshot 참조
- 사건·수신시각
- PENDING, PROCESSING, PROCESSED, FAILED, DEAD
- 시도 횟수, 다음 시도시각, 오류

유일 제약: market_account + dedupe_key.

늦게 도착한 이벤트는 snapshot으로 보존하되 provider_updated_at이나 sequence가 최신 상태보다 오래되면 현재 projection을 역행시키지 않는다.

### 10-3. sync_cursor

계정과 스트림별로 ORDERS, CLAIMS, FULFILLMENT, PURCHASE_CONFIRMATIONS cursor를 보관한다.

cursor는 원문 저장, 이벤트 처리, 주문 upsert가 모두 성공한 같은 트랜잭션에서만 전진한다.

### 10-4. sync_run

- MANUAL, SCHEDULE, WEBHOOK, RECONCILE trigger
- QUEUED, RUNNING, SUCCEEDED, PARTIAL, FAILED, CANCELED
- cursor before/after
- 요청자, 시작·heartbeat·완료 시각
- 조회·생성·수정·오류 건수

계정·스트림당 QUEUED/RUNNING 작업은 한 개만 허용한다. worker는 advisory lock 또는 행 잠금을 함께 사용한다.

## 11. 수집 알고리즘

1. scheduler 또는 사용자가 sync_run을 생성한다.
2. worker가 계정·스트림 lease를 획득한다.
3. 현재 cursor와 안전 overlap 구간을 읽는다.
4. 마켓 API를 호출하고 페이지 원문을 먼저 저장한다.
5. 원문을 표준 integration_event로 정규화한다.
6. 외부 ID와 dedupe key로 중복을 제거한다.
7. sales_order, order_item, claim, shipment를 멱등 upsert한다.
8. 모든 페이지 처리가 성공한 트랜잭션에서 cursor를 전진한다.
9. 실행 결과와 오류를 sync_run에 기록한다.
10. 야간 대사는 최근 주문을 다시 읽어 누락·상태 차이를 복구한다.

수동 수집도 같은 파이프라인을 사용한다. UI 전용 임시 수집 로직을 만들지 않는다.

## 12. 외부 쓰기 명령

### 12-1. outbound_command

- aggregate 종류·ID
- 주문확인, 취소, 송장, 직접전달, 클레임 액션
- 마켓 독립 payload
- idempotency_key
- 요청 당시 aggregate version
- PENDING, LEASED, SUCCEEDED, RETRY, UNKNOWN, FAILED, DEAD
- 시도횟수, 다음 시도, lease
- 요청자와 correlation ID

유일 제약: tenant + idempotency_key.

### 12-2. outbound_attempt

각 시도의 요청 hash, 시작·종료 시각, HTTP 상태, 마켓 코드, 원문 응답, SUCCESS/RETRYABLE/PERMANENT/UNKNOWN을 보존한다.

### 12-3. 실행 알고리즘

1. UI는 상태를 직접 변경하지 않고 명령을 생성한다.
2. API는 command ID와 접수 상태를 반환한다.
3. worker는 최신 마켓 상태를 사전조회한다.
4. 이미 목표 상태면 명령을 성공으로 대사한다.
5. 가능한 상태면 외부 API를 호출한다.
6. 명확한 성공만 주문·송장·클레임 원장에 반영한다.
7. timeout은 UNKNOWN으로 두고 조회 API로 실제 결과를 확인한다.
8. 재시도 가능 오류만 지수 backoff와 jitter로 재시도한다.
9. 영구 실패는 사용자 조치와 오류코드를 실패 작업함에 표시한다.

외부 요청 후 응답을 받기 전에 서버가 중단될 수 있으므로, 동일 명령의 무조건 재호출은 금지한다.

## 13. 동시성 규칙

- mutable aggregate에 version을 둔다.
- 사용자 명령은 expectedVersion을 전송한다.
- version이 다르면 409 Conflict를 반환하고 최신 상태를 다시 보여준다.
- 구매완료, 송장, 직접전달처럼 여러 테이블을 변경하는 작업은 order_item을 FOR UPDATE로 잠근다.
- worker는 FOR UPDATE SKIP LOCKED와 lease_until로 작업을 획득한다.
- 동일 API 효과를 가진 명령은 하나의 idempotency_key만 허용한다.
- 오래된 마켓 이벤트가 최신 상태를 역행시키지 않는다.
- 마켓 부분성공은 성공 item만 반영하고 실패 item은 새 재시도 대상으로 둔다.

## 14. 상태 불변식

- READY_TO_SHIP은 구매 완료와 유효한 실제 국내송장을 가져야 한다.
- 일반 SHIPPING은 유효한 국내송장과 market_invoice SUBMITTED를 가져야 한다.
- 직접전달 SHIPPING은 직접전달 제출 성공, 구매 완료, 실제 국내송장을 모두 가져야 한다.
- 직접전달만 먼저 성공한 구매대기 주문은 PREPARING을 유지한다.
- DELIVERED는 실제 KOREA_DOMESTIC shipment가 DELIVERED여야 한다.
- market_invoice SUBMITTED는 outbound_command 성공 없이 생성할 수 없다.
- 클레임 생성은 기존 구매·배송 상태를 삭제하지 않는다.
- 소싱라이프 PAID와 INVOICE_RECEIVED는 별도 사건으로 저장한다.

교차 테이블 불변식은 application service가 관련 행을 잠근 단일 트랜잭션에서 검증한다.

## 15. API 표면

초기 내부 API는 다음 역할을 제공한다.

| 메서드/경로 | 역할 |
|---|---|
| GET /api/orders | cursor 기반 주문 목록 |
| GET /api/orders/{id} | 주문·상품주문·구매·배송·클레임 상세 |
| POST /api/market-accounts | 마켓 계정 등록 |
| POST /api/market-accounts/{id}/verify | 실제 연결·권한 검증 |
| POST /api/market-accounts/{id}/sync | 수동 수집 작업 접수 |
| GET /api/sync-runs | 동기화센터 |
| POST /api/order-items/{id}/commands | 주문확인·취소 등 명령 접수 |
| GET /api/commands/{id} | 명령 상태 조회 |
| GET/POST /api/sourcing/mappings | 매핑 조회·승인·변경 |
| POST /api/order-items/{id}/sourcing-selection | 주문별 SKU 선택 |
| POST /api/sourcing-purchases | 소싱라이프 구매 신청 |
| POST /api/order-items/{id}/market-invoices | 송장·직접전달 명령 |
| GET/POST /api/claims | 클레임 조회·명령 접수 |

현재 구현 단계에서는 위 목표 중 조회를 `GET /api/claims`, `GET /api/claims/{id}`로 먼저 제공한다. `POST`와 provider write command는 fail-closed이며 아직 노출하지 않는다.

쓰기는 202 Accepted와 command ID를 반환하고, 외부 결과 확정 후 UI에 최종 성공을 표시한다.

## 16. 관측성과 운영

필수 지표:

- 계정·마켓별 마지막 성공 수집시각
- cursor 지연과 queue age
- 분당 수집 주문·클레임 수
- 외부 API latency, 2xx/4xx/429/5xx
- command 성공·재시도·UNKNOWN·DEAD 비율
- 대사 불일치 건수
- 인증 만료 예정 계정
- 매칭 재사용률과 구매 실패율

모든 로그는 correlation_id, tenant_id, market_account_id, sync_run_id 또는 command_id를 포함한다. 비밀키와 개인정보 원문은 로그에서 제거한다.

경고 조건:

- 정상 계정 수집 지연 10분 초과
- 429·5xx 비율 급증
- UNKNOWN 명령 5분 이상 미대사
- DEAD 명령 발생
- 인증 만료 30일·14일·7일 전
- 야간 대사 미실행 또는 불일치 임계 초과

## 17. 보안·개인정보

- 자격증명은 Secret Manager 또는 envelope encryption으로 저장하고 DB에는 secret_ref만 둔다.
- 통관부호, 이름, 연락처, 주소는 필드 암호화한다.
- 정확 검색은 blind index를 사용하고 부분검색은 기본 비활성화한다.
- 개인정보 내보내기와 원문 조회는 고위험 권한과 감사로그를 요구한다.
- 개발·스테이징에는 운영 개인정보를 복제하지 않는다.
- raw snapshot 보존기간과 마스킹은 데이터 종류별로 설정한다.
- 주문 보존 의무와 통관부호의 목적 종료 후 파기 시점을 분리한다.
- 회원 탈퇴가 주문 원장의 무조건 cascade 삭제를 일으키지 않게 한다.

## 18. 테스트 전략

| 테스트 | 목적 |
|---|---|
| 상태 reducer 단위 테스트 | 역행·금지 조합 차단 |
| 마켓 adapter 계약 테스트 | 원문 schema와 정규화 검증 |
| fixture replay | 저장된 익명 원문으로 회귀 검증 |
| worker 통합 테스트 | cursor 원자성, retry, lease |
| command 통합 테스트 | idempotency와 UNKNOWN 대사 |
| E2E | 연결→수집→매칭→구매→송장→클레임 |
| 실계정 UAT | 판매자센터 실제 결과 확인 |
| 대사 테스트 | 기간별 수량·상태·금액 비교 |
| 장애 주입 | timeout, 401, 429, 5xx, 중복, 순서 역전 |
| 보안 테스트 | tenant 격리, 역할, 비밀키·PII 노출 |

현재 저장소는 Vitest 단위·계약 테스트와 `npm run test`를 제공한다. 실제 PostgreSQL 통합 테스트, 브라우저 E2E, 각 마켓 실계정 UAT는 출시 하드 게이트로 계속 추가한다.

## 19. 점진적 전환

### 1단계: DB 읽기 전환

- 현 mock 44건을 seed/fixture로 보존한다.
- tenant, user, market_account, sales_order, order_item을 도입한다.
- 주문 목록을 React Query 기반 서버 조회로 교체한다.
- 현재 화면 DTO는 read projection으로 유지한다.

### 2단계: 스마트스토어 수집

- 계정 저장·검증과 sync 파이프라인을 도입한다.
- 네이버 증분 수집을 실데이터로 연결한다.
- mock과 실데이터를 feature flag로 구분한다.

### 3단계: 외부 명령

- 주문확인·판매자취소부터 command로 전환한다.
- 현재 handler의 선행 로컬 상태 변경을 제거한다.
- pending, success, fail, retry 상태를 화면에 표시한다.

### 4단계: 영구 매칭·소싱 구매

- 주문 ID 기반 localStorage 매칭을 SKU 매핑 테이블로 교체한다.
- 더미 후보와 가짜 소싱 주문번호·송장 생성을 제거한다.
- 소싱라이프 테스트 API와 callback 대사를 연결한다.

### 5단계: 송장·직접전달·클레임

- 실제 shipment와 market_invoice를 도입한다.
- 마켓별 capability에 따라 UI 액션을 생성한다.
- claim을 독립 aggregate로 전환하고 반품·교환을 완성한다.

### 6단계: 전체 마켓·운영

- 쿠팡, 11번가, ESM을 같은 adapter 계약으로 확장한다.
- 동기화센터, 실패 작업함, 감사로그, 알림을 완성한다.
- mock/localStorage와 자동 초기화 코드를 데모 모드로 격리한다.

각 단계는 tenant별 feature flag로 제한 운영하고 판매자센터 대사 통과 후 확대한다.
