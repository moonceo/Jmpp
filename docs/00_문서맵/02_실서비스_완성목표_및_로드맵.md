# 커머스라이프 실서비스 완성목표 및 로드맵

## 1. 문서 목적

이 문서는 현재 Next.js mock 프로토타입을 해외구매대행 셀러가 실제 주문에 사용할 수 있는 주문관리 서비스로 전환하기 위한 상위 목표와 완료 기준을 정의한다.

현재 화면이 존재하거나 버튼이 동작하는 것만으로는 완료로 보지 않는다. 마켓 API의 실제 성공 결과, 서버 영속 데이터, 재시도와 감사이력, 플랫폼별 정상·예외 시나리오 검증 증거가 모두 있어야 해당 기능을 완료로 판정한다.

## 2. 최종 제품 정의

커머스라이프는 스마트스토어, 쿠팡, 11번가, G마켓, 옥션의 주문을 수집하고 다음 업무를 하나의 흐름으로 처리하는 독립 해외구매대행 셀러용 주문관리 서비스다. 소싱라이프는 상품 소싱·구매·송장 결과를 연결하는 외부 연동 서비스다.

1. 여러 마켓·여러 스토어의 주문과 클레임을 누락 없이 수집한다.
2. 마켓 상품·옵션을 타오바오/소싱라이프 상품·SKU와 매칭한다.
3. 승인된 매칭을 다음 동일 상품 주문에 재사용한다.
4. 소싱라이프 구매대행 신청과 국내 결제 흐름으로 연결한다.
5. 소싱라이프 구매·물류 진행상태와 국내송장을 주문에 연결한다.
6. 마켓별 지원 방식에 맞춰 주문확인, 송장 발송, 직접전달, 취소, 반품, 교환을 처리한다.
7. 실패, 중복, 부분 성공, 인증 만료를 운영자가 화면에서 발견하고 복구할 수 있게 한다.

주문관리는 소싱라이프 안의 기능이다. 주문관리 서버가 타오바오에 직접 로그인하거나 직접 결제하지 않는다. 자체 배대지·창고 운영 기능도 포함하지 않는다. 타오바오 상품 조회와 구매 실행은 소싱라이프의 기존 구매대행 책임으로 둔다.

## 3. 현재 상태

2026-07-13 저장소 기준 현재 상태는 다음과 같다.

| 영역 | 현재 증거 | 판정 |
|---|---|---|
| 주문 화면 | PostgreSQL 주문상품 cursor 목록을 읽고, 원장 비어 있음/장애 시 데모임을 명시해 mock을 표시 | 스마트스토어 수직 슬라이스 구현, 실계정 UAT 전 |
| 데이터 | PostgreSQL tenant/account/order/item/recipient/sync/command/audit 원장과 RLS 역할 분리 구현 | migration 실DB 적용·복구검증 전 |
| 주문수집 | 스마트스토어 계정검증·변경주문·수량클레임 호환 상세조회·cursor·raw snapshot·재시도 worker와 활성 연결계정 자동 예약 scheduler 구현 | 단위·계약 테스트 통과, 실계정 대사·장시간 운전 UAT 전 |
| 마켓연동 | 계정 자격증명 AES-256-GCM 저장, 연결검증 작업 접수, 계정 CRUD 구현 | 스마트스토어만 worker 구현, 나머지 마켓 미구현 |
| 타오바오 매칭 | 상품·정확 SKU·revision·주문 간 재사용 규칙 원장, 가격·재고 freshness, 수동 snapshot fail-closed 구현 | trusted 소싱라이프 조회 worker·승인 UI·실연동 UAT 전 |
| 소싱라이프 구매 | 비용·환율·중국배송·국제배송·관부가세·PCCC·배대지 준비상태를 분리한 구매 전 초안 구현 | 실제 구매신청·결제 세션은 의도적으로 미구현·hard stop |
| 송장·직접전달 | 국내송장 원장 저장, outbound command/attempt/UNKNOWN 대사, 스마트스토어 confirm/dispatch processor 구현 | 계정별 write UAT 승인 전에는 fail-closed |
| 취소·반품·교환 | 공통 case/line/event 원장, 네이버 `currentClaim`·`completedClaims` 정규화 수집, 실원장 목록·기한·상세·이력 UI, 공식 사유·부분수량 기반 스마트스토어 판매자 취소 코어, 접수 후 `ON_HOLD / CANCEL_REQUESTED` 보존 구현 | 판매자 취소는 계정별 UAT 전 `MANUAL_FALLBACK`; causal baseline/channel allowlist 전 `UNKNOWN` 자동 재호출 금지·수동 대사; 구매자 취소승인·반품·교환 쓰기, 회수/재배송 leg, line별 소싱 보상 saga 미구현 |
| 서버 기반 | 자체 로그인, 폐기 가능한 브라우저 세션, CSRF, 단기 HMAC 내부 인증, DB membership, RLS app role, BYPASSRLS worker role, migration/worker/readiness 구현 | PGlite 검증 완료, native PostgreSQL 16·배포환경·브라우저 E2E 검증 전 |
| 운영 안정성 | sync/outbound lease, 멱등키, 시도이력, retry, UNKNOWN 읽기대사·수동해소, append-only 감사로그 구현 | 운영 UI·알림·실장애 훈련 전 |

위 표의 `구현`은 코드와 단위·계약 테스트가 존재한다는 뜻이며, 하드 게이트의 실제 판매자센터 UAT를 통과했다는 뜻이 아니다. 쿠팡·11번가·ESM, 소싱 매핑·구매, 구매자 클레임 승인·거부와 반품·교환 물류 전체 라이프사이클은 계속 미완료다.

따라서 현재 버전은 화면과 정책을 검증하는 기반이며, 실서비스 완성률을 화면 개수로 계산하지 않는다.

## 4. 완성 목표

### G0. 제품·정책 확정

- 공통 주문 단위와 마켓별 처리 단위를 정의한다.
- 마켓 상태, 내부 작업단계, 소싱 상태, 배송 상태, 클레임 상태를 분리한다.
- 결제완료 후 선택 배송대행지 주문서 자동입력·접수를 실행하고, 접수 즉시 국내송장을 발급하는 배송대행지만 연결하는 계약을 적용한다.
- 직접전달은 마켓별 공식 지원 여부가 확인된 경우에만 제공한다.
- 직접 구매와 배대지·창고 기능은 리펀디 벤치마크에 유지하고, 파트너 계약·직접 운영 책임모델 검증 후 MVP 단계를 선택한다.

완료 증거:

- 승인된 PRD, 상태전이표, 마켓 기능지원표
- 미확정 정책이 P0 목록에 남아 있지 않음

### G1. 계정·권한·보안 기반

- 회사/워크스페이스별 데이터를 완전히 격리한다.
- 소유자, 관리자, 운영자, 조회자 역할을 지원한다.
- 마켓 비밀키와 소싱라이프 인증정보는 서버에서 암호화해 보관한다.
- 주문 처리와 개인정보 조회에 감사로그를 남긴다.
- 개인통관고유부호, 연락처, 주소는 권한에 따라 마스킹한다.

완료 증거:

- 서로 다른 워크스페이스 간 접근 차단 테스트
- 비밀키가 브라우저, 로그, DB 평문에 노출되지 않는 보안 점검
- 역할별 허용/거부 E2E 테스트

### G2. 마켓 연결과 상태 진단

- 스마트스토어, 쿠팡, 11번가, ESM의 다중 계정을 등록한다.
- 등록 시 실제 인증, 판매자 식별, 권한, 호출 가능 API를 검증한다.
- 활성, 재인증 필요, 권한 부족, 만료 예정, 장애 상태를 표시한다.
- 초기 수집 기간과 수집 결과를 계정별로 확인한다.

완료 증거:

- 각 마켓의 실제 판매자 테스트 계정 연결 성공
- 잘못된 키, 만료 키, IP 미허용, 권한 부족 시나리오 통과

### G3. 주문·클레임 동기화 엔진

- 계정별 증분 수집 커서와 예약 작업을 운영한다.
- 같은 주문을 반복 수집해도 중복 생성하지 않는다.
- 원본 응답, 정규화 결과, 수집 실행, 오류를 추적한다.
- 누락 방지를 위한 주기적 대사와 수동 재수집을 제공한다.
- 주소 변경, 클레임 전환, 상태 역행, 늦게 도착한 이벤트를 처리한다.

완료 증거:

- 각 마켓 30일 실주문 표본과 판매자센터 수량·상태 대사
- 중복, 순서 역전, 타임아웃, 429, 5xx 재생 테스트
- 수집 누락률과 지연 SLO 대시보드

### G4. 주문 처리

- 상품주문 단위의 주문확인, 일괄 처리, 판매자 취소를 지원한다.
- 복수 품목, 부분 취소, 합배송, 분리배송을 데이터 모델에서 보존한다.
- 외부 API 처리 전 현재 상태를 다시 조회한다.
- 부분 성공은 주문별 결과로 분리해 표시하고 실패 건만 재시도한다.

완료 증거:

- 마켓별 정상·부분 성공·이미 처리됨·상태 변경 경합 UAT
- 사용자 화면 성공 표시와 판매자센터 실제 상태 일치

### G5. 영구 상품·옵션 매칭

- 매칭 키는 워크스페이스, 마켓 계정, 마켓 상품 ID, 마켓 옵션 ID를 사용한다.
- 타오바오/소싱라이프 상품 ID와 SKU ID, 수량 배수, 대체상품을 저장한다.
- 같은 상품의 다음 주문은 승인된 최신 매칭을 자동 제안한다.
- 가격, 재고, 옵션 유효성, 금지품목, 예상원가를 구매 전에 재검증한다.
- 변경 이력, 승인자, 마지막 검증 시각, 해제 사유를 남긴다.

완료 증거:

- 신규 매칭, 재사용, SKU 품절, 가격변경, 옵션명 변경, 대체상품 UAT
- 주문 ID가 달라도 같은 마켓 SKU에 매칭이 재사용되는 테스트

### G6. 소싱라이프 구매 연동

- 매칭된 SKU와 수량, 수취정보, 통관정보를 소싱라이프 구매대행 신청으로 전달한다.
- 결제 세션은 중복 생성·중복 결제를 방지한다.
- 신청, 결제, 중국 판매자 발송, 중국 배송, 통관, 국내송장, 환불 상태를 별도 이벤트로 동기화한다.
- 최종 유료 결제는 사용자 확인 후 소싱라이프 결제 화면에서 실행한다.
- 결제 결과가 불명확하면 성공으로 추정하지 않고 대사 대상에 둔다.

완료 증거:

- 소싱라이프 스테이징/테스트 계약 테스트
- 중복 클릭, 응답 유실, 결제 성공 후 콜백 유실, 품절·가격변경 UAT

### G7. 송장·직접전달

- 실제 국내 택배사 코드와 송장을 내부 배송 데이터로 저장한다.
- 마켓별 택배사 코드 변환과 송장 형식을 검증한다.
- 송장 발송, 송장 정정, 직접전달을 마켓 지원능력에 따라 제공한다.
- 직접전달과 실제 국내배송 추적을 서로 다른 속성으로 관리한다.
- 마켓 발송 성공과 내부 상태 변경을 원자적으로 추적한다.

완료 증거:

- 마켓별 송장 등록 후 판매자센터 확인
- 중복 송장, 잘못된 택배사, 부분 발송, 직접전달 미지원 UAT
- 직접전달 기능에 공식 근거 또는 마켓 승인 기록 존재

### G8. 취소·반품·교환

- 고객 요청과 판매자 요청을 구분한다.
- 전체/부분 수량과 주문상품 단위 클레임을 지원한다.
- 취소 승인·거부, 반품 접수·승인·거부·보류·입고·환불, 교환 수거·입고·재배송·거부를 지원한다.
- 마켓 액션과 소싱라이프 구매취소/환불을 하나의 작업으로 보되 결과는 각각 저장한다.
- 한쪽만 성공한 경우 자동 보상 또는 운영자 복구 작업을 만든다.

완료 증거:

- 마켓별 지원 액션 전체 UAT
- 구매 전/후, 중국 발송 전/후, 국내 발송 전/후 클레임 시나리오
- 마켓 성공·소싱라이프 실패 및 반대 순서의 복구 테스트

### G9. 운영·품질·출시

- 동기화센터, 실패 작업함, 재시도, 처리이력, 감사이력을 제공한다.
- API 키 만료와 수집 지연을 운영자에게 알린다.
- 백업·복구, 배포 롤백, 장애대응 절차를 검증한다.
- 테스트 러너와 계약·통합·E2E 테스트를 CI에 연결한다.
- 운영 매뉴얼과 온보딩 가이드를 제공한다.

완료 증거:

- lint, build, 단위·계약·통합·E2E 전체 통과
- 복구훈련 결과와 RTO/RPO 확인
- 2개 이상 실제 셀러 계정의 제한 운영 및 판매자센터 대사 완료

## 5. 실서비스 완료의 하드 게이트

다음 조건 중 하나라도 충족하지 못하면 “바로 사용 가능”으로 표시하지 않는다.

1. 5개 판매처가 실제 주문수집과 핵심 처리 UAT를 통과했다.
2. 모든 외부 쓰기 작업에 멱등키, 상태 사전조회, 시도 이력, 결과 대사가 있다.
3. 반품·교환이 조회 전용이 아니라 마켓별 허용 범위에서 처리된다.
4. 마켓 계정 비밀키가 암호화되고 브라우저에 전달되지 않는다.
5. 주문과 상품주문이 분리되어 복수 품목·부분 클레임을 보존한다.
6. 타오바오 매칭이 주문 단위 임시값이 아니라 재사용 가능한 SKU 자산으로 저장된다.
7. 실패 작업을 운영자가 발견하고 안전하게 재시도할 수 있다.
8. 성공으로 표시된 작업이 실제 판매자센터 상태와 일치한다.
9. 개인정보 조회·수정·내보내기에 감사이력이 남는다.
10. 실데이터 백업과 복구가 검증됐다.

## 7. 단계별 실행 순서

단계는 시간 약속이 아니라 선행조건과 종료 게이트다. 한 단계의 종료 게이트를 충족하기 전에는 다음 단계를 완료로 선언하지 않는다.

### P0. 실서비스 설계와 외부 접근권 확보

- PRD, 상태모델, 데이터모델, 보안정책, API 기능지원표 확정
- 스마트스토어·쿠팡·11번가·ESM 개발/운영 권한 신청
- 소싱라이프 내부 API 계약과 테스트 환경 확정
- 2026년 전자상거래업자 등록 및 통관정보 처리 의무 검토

종료 게이트: 구현에 필요한 자격증명과 미확정 P0 정책 목록이 문서화돼 있고, 접근 불가 항목은 담당자·신청상태·대체 검증법이 지정됨.

### P1. 서버 기반과 스마트스토어 수직 슬라이스

- 인증, 워크스페이스, PostgreSQL, 큐/워커, 비밀키 저장
- 스마트스토어 연결, 증분 수집, 주문확인, 송장, 취소
- 동기화센터, 실패 재시도, 감사로그

종료 게이트: 스마트스토어 한 계정의 주문수집부터 발송·취소까지 실주문 UAT와 대사 통과.

### P2. 쿠팡 수직 슬라이스와 공통 어댑터 안정화

- 쿠팡 HMAC, 키 만료, 속도제한 대응
- 주문수집, 상품준비, 송장, 취소·반품·교환
- 공통 명령/결과/부분실패 UI 완성

종료 게이트: 네이버·쿠팡에서 같은 공통 UI가 각 마켓의 다른 필수값과 상태를 안전하게 처리.

### P3. 영구 매칭과 소싱라이프 구매

- 상품/SKU 매핑 라이브러리
- 후보 검색, URL 조회, 옵션·가격·재고 재검증
- 구매대행 신청·결제·상태·송장 이벤트 연동

종료 게이트: 새 주문 매칭과 반복 주문 자동 재사용, 결제 중복방지, 송장 결과 연결 UAT 통과.

### P4. 클레임 완성

- 공통 클레임 상태머신
- 네이버·쿠팡 취소·반품·교환 전체 지원 범위
- 소싱라이프 구매취소/환불과 부분실패 복구

종료 게이트: 구매/배송 단계별 클레임과 한쪽만 성공한 복구 시나리오 통과.

### P5. 11번가와 ESM

- 11번가 인증·주문·배송·클레임 어댑터
- ESM 승인·JWT·G마켓/옥션 주문·배송·클레임 어댑터
- 플랫폼별 미지원 액션의 안전한 대체 흐름

종료 게이트: 5개 판매처 실계정 UAT와 초기/증분 수집 대사 통과.

### P6. 경쟁 서비스 수준의 운영 완성도

- 통관부호 고객 요청·검증, 알림, 배송추적
- 문의 통합, 장부·마진, 엑셀 내보내기
- 온보딩, 요금·사용량, 운영 대시보드
- 부하·복구·보안 검증과 제한 운영

종료 게이트: 실셀러가 판매자센터를 상시 병행하지 않고 핵심 주문업무를 완료하며, 30일 제한 운영에서 미해결 P0/P1 결함이 없음.

## 9. P0 정책 결정 목록

### 9-1. 결제와 국내송장

현재 프로토타입은 “구매 완료에는 국내송장이 필수”라는 화면 정책을 사용한다. 실서비스 데이터 모델에서는 다음 이벤트를 반드시 분리한다.

- 소싱라이프 주문 생성
- 결제 승인
- 타오바오 구매 성공
- 중국 판매자 발송
- 국내송장 발급
- 마켓 발송 성공

연결 대상 배송대행지는 주문서 접수 성공 응답에서 유효한 국내 택배사와 송장번호를 즉시 반환해야 한다. 국내송장이 반환되지 않으면 정상적인 송장대기 상태로 전환하지 않고 접수 실패·응답 유실·송장 누락 오류로 기록하며, 결제 상태와 배송대행지 접수 상태를 분리해 재조회 또는 멱등 재접수한다. 어느 경우에도 결제 성공만으로 배송대행지 접수 성공이나 송장 발급을 추정하지 않는다.

### 9-2. 직접전달

- 스마트스토어는 공식 발송 방식의 DIRECT_DELIVERY를 기준으로 구현한다.
- 쿠팡 DIRECT는 숫자 송장값과 배송추적 불가 제약이 있으므로 일반적인 직접전달 용도로 사용할 수 있는지 운영 승인을 받은 뒤 활성화한다.
- 11번가와 ESM은 공식 문서·실계정 검증 전까지 미지원으로 표시한다.
- 미지원 마켓에 임의 송장이나 거짓 배송정보를 전송하지 않는다.

### 9-3. 통관정보

- P와 12자리 숫자 형식만 확인한 상태는 “형식 유효”다.
- 성명·전화번호·개인통관고유부호의 실제 일치 확인이 끝난 경우에만 “본인 일치”로 표시한다.
- 검증 API를 확보하지 못하면 고객 제출과 운영자 확인 절차를 제공하되 자동 일치로 단정하지 않는다.

## 10. 경쟁 서비스 패리티 원칙

리펀디 기능은 `10_리펀디_벤치마킹/`에 전부 보존하고, 커머스라이프 구현 순서만 다음 기준으로 분류한다.

| 분류 | 기준 | 예시 |
|---|---|---|
| MVP-1 | 첫 실사용 주문 처리를 완결하는 기능 | 멀티마켓 수집, 주문현황, 매칭, 송장, 클레임, 알림 |
| MVP-2 | MVP-1 안정화 후 운영 자동화를 확장하는 기능 | 배대지 주문서, 대량 문자, 상품관리, 고급 장부 |
| 후보 | 사업·사용자 가치 검증 후 순서 결정 | 캐시백, 쿠폰, 고급 AI 자동화 |
| 의존성 검증 | 결제·외부업체·마켓 쓰기·개인정보 선행조건 필요 | 자동결제, 배대지 운영, 상품 변경 |

## 11. 출시 판정 회의의 필수 증거

출시 판정 시 다음 자료를 한 묶음으로 확인한다.

1. 요구사항 ID별 구현 파일과 테스트 연결표
2. 마켓별 자격증명·승인·API 버전·확인일
3. 정상·오류·부분성공 UAT 결과
4. 판매자센터와 내부 주문 대사 결과
5. 미지원 기능과 사용자 대체 절차
6. 보안·개인정보 점검 결과
7. 백업 복구와 장애 훈련 결과
8. 미해결 결함 목록과 우선순위

문서, 화면, 테스트가 존재한다는 사실만으로 요구사항 충족을 주장하지 않는다. 실제 외부 상태와 운영 복구 가능성까지 증명해야 한다.
