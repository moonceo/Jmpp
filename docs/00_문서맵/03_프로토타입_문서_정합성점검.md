# 프로토타입·문서 정합성 점검

## 1. 점검 범위

- 소싱하기, 배대지 선택, 결제대기, 결제완료
- 배송대행지 주문서 자동입력·접수·국내송장 반영
- 자동 배송중 처리 ON/OFF
- 발송대기와 배송중 처리
- 직접전달 예외

화면 캡처 연결을 사용할 수 없어 시각 디자인 감사는 제외했다. 현재 React 코드, 상태 전환 함수, mock 데이터와 활성 문서를 기준으로 기능 정합성을 점검했다.

## 2. 확정된 실서비스 흐름

1. 상품·옵션·수량과 저장된 배송대행지 수령 프로필을 선택한다.
2. 구매대행 신청 후 결제대기에서 채팅과 신청정보를 확인한다.
3. 결제완료 후 선택한 배송대행지 사이트를 연다.
4. 주문상품·수취·통관정보를 배송대행지 주문서에 자동입력한다.
5. `접수대기`와 `접수신청`을 동일한 접수 단계로 실행한다.
6. 연결 배송대행지는 접수 성공과 동시에 국내 택배사·송장번호를 발급한다.
7. 국내송장을 주문에 저장한다.
8. 자동 배송중 처리 OFF면 마켓 상태를 변경하지 않고 `READY_TO_SHIP`으로 이동한다.
9. ON이면 국내송장을 마켓에 전송하고 마켓 성공 확인 후 `SHIPPING`으로 이동한다.

## 3. 현재 일치하는 부분

| 항목 | 현재 프로토타입 | 판정 |
|---|---|---|
| 배대지 선택 | 결제 전 저장된 수령 프로필 선택 | 일치 |
| 결제대기 분리 | 구매대행 신청 후 별도 `결제하기` 제공 | 일치 |
| 통관부호 검증 | 유효 통관부호만 결제 진행 | 일치 |
| 국내송장 필수 | 송장 없이는 발송대기·배송중 정상 전환 불가 | 일치 |
| 자동 처리 OFF | 국내송장 저장 후 발송대기, 마켓 배송중 미처리 | 일치 |
| 자동 처리 ON | 국내송장 확보 후 배송중 결과 시연 | 최종 결과 일치, 외부 호출은 시뮬레이션 |
| 발송대기 처리 | `배송중 처리` 클릭 시 선택 모달 없이 송장 전송 | 일치 |
| 직접전달 | 마켓만 먼저 배송중 처리하고 구매·송장 완료 전 내부 상품준비 유지 | 일치 |

## 4. 프로토타입과 실서비스 문서의 차이

| ID | 차이 | 현재 프로토타입 근거 | 영향 | 분류 |
|---|---|---|---|---|
| GAP-01 | 배송대행지 사이트 열기·주문서 자동입력·접수 화면이 없음 | `handleCompleteSourcingPayment`가 외부 handoff 없이 바로 다음 상태를 생성 | 실제 사용자 중간 작업을 검증할 수 없음 | 의도된 프로토타입 생략 |
| GAP-02 | 결제완료 클릭 시 더미 국내송장을 즉시 생성 | `createDummyInvoice` 호출 | 실서비스의 접수 응답과 프로토타입 결과가 같은 화면 사건으로 합쳐짐 | 의도된 시뮬레이션 |
| GAP-03 | 자동 배송중 처리 ON에서 실제 마켓 API를 호출하지 않음 | mock 주문은 `uploadedToMarketAt`, `marketOrderStatus`를 로컬 갱신 | 실제 성공·실패·재시도·대사 검증 불가 | 실서비스 미구현 |
| GAP-04 | 실주문 소싱 결제완료 흐름이 비활성 | `dataSource === api`이면 안내 후 완료하지 않음 | API 주문으로 배대지 접수·송장 연동 검증 불가 | 실서비스 미구현 |
| GAP-05 | PAID·배송대행지 접수·INVOICE_RECEIVED를 개별 화면 상태로 관찰할 수 없음 | 결제완료 시 바로 `INVOICE_RECEIVED`와 `SOURCED` 생성 | 장애 지점과 재처리 대상 구분 불가 | 상태 모델 미구현 |
| GAP-06 | 접수 실패·응답 유실·송장 누락 더미가 없음 | 정상 결제완료 더미는 모두 국내송장 보유 | 실패 복구 UX와 운영 절차를 시연할 수 없음 | 더미/예외 시나리오 부족 |
| GAP-07 | 자동 배송중 처리 설정이 브라우저 localStorage 범위 | `jumunpangpang.autoShipping` | 다른 브라우저·기기·작업자와 설정이 공유되지 않음 | 실서비스 저장 범위 결정 필요 |
| GAP-08 | 결제완료 화면의 배송대행지 자동입력 완료 표시는 실제 실행 증거가 아님 | 프로토타입은 외부 사이트를 열지 않음 | 화면 문구를 실연동 성공으로 오해할 수 있음 | 프로토타입 표현 차이 |

## 5. 문서 상충 점검과 조치

| 기존 상충 | 조치 |
|---|---|
| 국내송장이 통관·국내인계 뒤 발급될 수 있다는 미확정 계약 | 접수 즉시 발급 배송대행지만 연결하는 정책으로 확정 |
| PAID 후 장기 국내송장 대기를 정상 흐름으로 설명 | 정상 접수는 즉시 발급, 미수신은 접수 실패·응답 유실·송장 누락 오류로 변경 |
| 결제완료와 국내송장 수신을 같은 사건으로 표현 | 서버 사건은 분리하되 정상 접수 트랜잭션에서 연속 처리하도록 명시 |
| `접수대기`와 `접수신청`을 별도 단계로 해석할 여지 | 동일한 접수 단계로 명시 |
| 발송대기에서 택배 발송·직접전달 방식을 다시 선택 | 선택 모달 제거, `배송중 처리`는 저장된 국내송장을 즉시 전송하도록 통일 |
| 내부정책의 목록 액션이 상세 액션과 구분되지 않음 | 목록 고빈도 액션과 상세 전체 액션을 분리해 갱신 |

## 6. 남은 결정·구현 항목

1. 자동 배송중 처리 설정의 실서비스 저장 단위를 회사, 스토어, 사용자 중 무엇으로 할지 확정한다.
2. 배송대행지 접수 요청 ID, 멱등키, 외부 주문서 ID, 접수시각, 응답 원문을 저장한다.
3. 접수 성공·응답 유실·송장 누락의 재조회와 안전 재시도 정책을 구현한다.
4. mock에 접수 실패와 자동 마켓 발송 실패 주문을 추가해 복구 흐름을 시연한다.
5. 실제 마켓 송장 전송은 provider 성공 대사 후에만 내부 `SHIPPING`으로 확정한다.
