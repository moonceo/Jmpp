# 소싱라이프 주문관리 문서맵

이 폴더의 문서는 소싱라이프 주문관리의 현재 프로토타입과 실서비스 구현 목표를 함께 관리한다. `_legacy` 폴더는 참고 자료이며 구현 기준으로 사용하지 않는다.

- `현재 프로토타입`: 현재 Next.js mock 화면의 실제 동작을 설명한다.
- `실서비스 목표`: 마켓 API·서버·DB·소싱라이프 연동을 포함한 구현 목표와 완료 증거를 정의한다.

새 기능 구현은 실서비스 목표를 기준으로 진행하고, 현재 동작 확인은 코드와 현재 프로토타입 문서를 기준으로 한다.

1. `02_실서비스_완성목표_및_로드맵.md`: 최종 목표, 단계, 출시 게이트

3. `01_주문처리_핵심규칙.md`: 현재 프로토타입 상태와 전환 조건
4. `03_프로토타입_문서_정합성점검.md`: 프로토타입과 실서비스 목표의 의도된 차이와 미구현 항목

7. 시스템/API: 생산 데이터 모델, 동기화, 마켓·소싱라이프 계약
8. UI/UX·운영·유저플로우: 화면과 실제 업무 절차
9. 프론트 구현기준, 내부정책, 와이어프레임: 현재 구현 보조 자료

## 기준 우선순위

현재 구현의 실제 동작이 충돌하면 다음 순서로 판단한다.

1. 현재 코드와 타입
2. `01_주문처리_핵심규칙.md`
3. 공통 모델/API 문서
4. 기능명세
5. 서비스기획과 UI/UX 명세
6. 운영 매뉴얼, 유저플로우, 와이어프레임

새 실서비스 기능의 구현 목표가 충돌하면 다음 순서로 판단한다.

1. 실서비스 완성목표와 승인된 P0 정책
2. 실서비스 PRD
3. 실서비스 상세기능명세/UAT
4. 생산 아키텍처·마켓 API·소싱라이프 계약
5. UI/UX·운영·유저플로우
6. 현재 프로토타입 코드

현재 프로토타입에 기능이 없다는 사실이 실서비스 목표를 취소하지 않는다. 반대로 공식 API와 실계정 검증이 끝나지 않은 목표를 현재 지원 기능으로 표시하지 않는다.

충돌을 발견하면 낮은 우선순위 문서를 방치하지 않고 같은 변경에서 함께 수정한다.

## 문서 관리 원칙

- 주문 흐름 변경 시 핵심규칙, 기능명세, 공통 모델/API, 운영 매뉴얼을 함께 확인한다.
- UI 라벨이나 액션 변경 시 UI/UX 명세와 와이어프레임을 함께 수정한다.
- 상태 조합 변경 시 더미데이터를 함께 검증한다.
- 변경 후 `99_변경이력.md`에 한 줄을 추가한다.
- 네이버·쿠팡 API의 실제 요청값은 공식 문서를 최종 근거로 확인한다.
- 11번가·ESM도 공식문서와 실계정 UAT를 최종 근거로 확인한다.
- 마켓과 소싱라이프 외부 쓰기 작업은 멱등키, 결과 대사, 감사로그를 함께 설계한다.
- 경쟁서비스 공개자료는 기능 후보로만 사용하며 완료 증거로 사용하지 않는다.
- 소싱라이프 직접 생성 주문, 타오바오 직접 결제, 내부 배대지·창고 관리는 현재 MVP 범위에 포함하지 않는다.
