# 프론트엔드 구현 기준

## 1. 현재 구현 전제

현재 MVP는 백엔드 없이 Next.js App Router, React, TypeScript, Tailwind CSS, shadcn/ui 조합으로 구현한다.
주문 데이터는 mock data와 클라이언트 상태를 기준으로 동작하며, 일부 소싱/송장 결과는 localStorage에 저장한다.
주문관리는 소싱라이프 내부 메뉴이며, 주문수집 원천은 마켓 주문으로 한정한다.
소싱라이프에서 직접 생성하거나 주문한 내역은 주문수집 데이터로 넣지 않는다.
소싱라이프의 구매, 검수, 입고, 물류 상세 처리는 소싱라이프 기존 기능에서 진행한다.

실제 패키지 기준:

- Next.js 16.1.4
- React 19.2.3
- TypeScript 5 strict mode
- Tailwind CSS 4
- shadcn/ui 스타일의 Radix 기반 UI primitive

경로 별칭은 `@/*`를 사용한다.
공유 타입은 `types/`, 도메인 상수는 `lib/constants/`, mock fixture는 `lib/mock-data/`, 공유 client state는 `lib/stores/` 기준으로 둔다.

현재 주문 MVP의 주요 데이터 흐름은 React state, mock data, localStorage 중심이다.
React Query는 의존성에 포함되어 있으나 주문관리 핵심 데이터 로딩에는 아직 사용하지 않는다.
Zustand는 현재 대시보드 store 중심으로 사용한다.

## 2. 실제 라우트

| 라우트 | 화면 |
|---|---|
| `/orders` | 주문관리 > 주문수집, 기본 신규주문 |
| `/orders?view=all` | 처리보류를 포함한 전체주문 |
| `/orders?view=new` | 신규주문 |
| `/orders?view=preparing` | 상품준비 |
| `/orders?view=waiting` | 발송대기 |
| `/orders?view=shipping` | 배송중 |
| `/orders?view=delivered` | 배송완료 |
| `/orders?view=claims` | 취소/반품/교환 |
| `/me/markets` | 주문관리 > 마켓연동 |

`all` view와 `ORDER_STATUSES.ALL`은 실제 전체주문 탭에 사용한다. `ON_HOLD` 주문은 이 화면과 `처리보류` 필터에서 조회하고 일반 처리 액션을 렌더링하지 않는다.

## 3. 주문관리 메뉴 구조

좌측 메뉴의 주문관리 하위 메뉴:

- 주문수집
- 취소/반품/교환
- 문의관리
- 마켓연동

주문수집 내부 상태는 본문 상단 탭으로 제공한다.

- 신규주문
- 상품준비
- 발송대기
- 배송중
- 배송완료

## 4. 검색/필터 구현

- 기간 버튼: `오늘`, `3일`, `7일`, `30일`, `직접 입력`.
- 검색 placeholder: `상품명, 주문번호, 주문자, 수령인 검색`.
- 마켓/스토어 필터는 하나의 아이콘 버튼으로 제공한다.
- 마켓과 스토어는 중복 선택 가능하다.
- 선택한 마켓과 관계없는 스토어는 비활성화한다.
- 마켓/스토어를 아무것도 선택하지 않으면 전체 주문을 표시한다.
- 마켓만 선택하면 선택한 마켓의 전체 스토어 주문을 표시한다.
- 스토어만 선택하면 해당 스토어 주문을 표시하고, 이때 스토어가 속한 마켓은 자동 포함된 것으로 본다.
- 마켓과 스토어를 함께 선택하면 선택한 마켓 안에서 선택한 스토어 주문만 표시한다.
- 단계별 상태 필터 옵션은 현재 주문 배열에서 추출하지 않고 주문 단계별 고정 허용 목록으로 관리한다.
- 판매처 드롭다운 옵션은 공통 `MARKET_ABBREVIATIONS`, `MARKET_BADGE_CLASSES`를 사용해 마켓별 네모 약자 아이콘과 스토어명을 표시한다.
- 해당 상태의 주문이 0건이어도 그 단계에서 조회 가능한 옵션은 드롭다운에 유지한다.
- 배송완료 주문은 모두 `배송완료` 상태값을 가지며, `marketOrderStatus === "PURCHASE_DECIDED"`이면 `구매확정` 필터 값을 추가한다.
- 상태 필터는 단일 파생값을 비교하지 않고 주문이 가진 상태값 목록에 선택값이 포함되는지 확인한다.
- 단계별 도구 영역은 `justify-between` 구조로 나누고 액션 버튼 그룹은 왼쪽, 필터와 설정 그룹은 오른쪽에 배치한다.
- 클레임 유형 필터는 액션 버튼 JSX와 분리해 오른쪽 필터 그룹에서 렌더링한다. 발송대기 송장 유무 필터는 제공하지 않는다.
- 필터는 주문 목록 조회 조건이며 주문수집 실행 범위 제한이 아니다.
- `주문수집` 버튼은 상단 우측 공통 액션으로 유지한다.

## 5. 주문 테이블 컬럼

주문수집 테이블 컬럼 순서:

1. 선택
2. 진행상태
3. 처리하기
4. 주문일시
5. 상품정보
6. 택배정보
7. 배송정보
8. 판매처

진행상태 컬럼은 소싱 진행 상태와 중국배송중·통관 중·국내 배송중·배송완료 배지를 표시한다. 마켓 보조 배지는 `마켓 취소요청`, `구매확정`만 생성하며, `마켓 배송중`, `마켓 배송완료`는 원천 상태와 관계없이 생성하지 않는다.
결제완료 이후의 조회 버튼은 상세 처리하기 영역에 구현하고 소싱상품 영역에는 중복 배치하지 않는다.
소싱 배지는 마켓 주문상태에서 계산하지 않고, 별도 소싱 진행 단계가 있으면 그 값을 우선 사용한다.
별도 단계가 없을 때만 소싱라이프 매칭/결제/송장 수신 상태로 보수적으로 추정한다.
배송완료 주문은 명시적으로 `배송완료` 소싱 단계를 가진 더미데이터를 사용해 `중국배송중`으로 잘못 보이지 않게 한다.
상태 projection은 실주문과 데모 주문에서 동일하게 `PAYMENT_READY → 결제대기`, `PAID/INVOICE_RECEIVED → 결제완료`, `EXTERNAL_PURCHASE → 결제완료`를 사용한다. `EXTERNAL_PURCHASE` 내부값은 유지하고 자세히 보기의 소싱상품에서 `외부구매`로 표시한다. 국내송장 수신만으로 중국배송중을 추정하지 않으며 취소·클레임 처리로 소싱 상태를 `HOLD`로 덮어쓰지 않는다.

전체 페이지에는 좌우 스크롤이 생기지 않게 한다.
필요 시 테이블 내부에서만 가로 스크롤을 허용한다.
컬럼 폭은 메뉴별로 최대한 동일하게 유지한다.

## 6. 행 확장 상세

주문 행을 클릭하면 자세히 보기 영역을 펼친다.
상세 섹션 순서:

1. 주문상품
2. 구매자
3. 배송정보
4. 택배정보
5. 처리하기
6. 소싱상품

상세의 구매자는 이름과 연락처만 표시한다.
상세의 배송정보는 수정 가능하다.
상세 하단은 `처리하기`와 `소싱상품`을 1:2 비율로 배치한다. 처리하기에는 상태별로 허용된 실행·조회 버튼을 모으고, 소싱상품은 썸네일, 상품명, 옵션명, 수량, 소싱금액, 소싱라이프 주문번호만 표시한다. 외부 구매는 소싱라이프 정보 대신 `외부구매` 배지와 외부 구매처 결제완료 안내를 표시한다.

행 상세와 체크 선택은 탭, 검색어, 필터, 데이터 변경 시 현재 화면 기준으로 초기화한다.
다른 탭에서 선택한 체크 상태가 현재 탭으로 이어져 보이면 안 된다.

## 7. 상태별 버튼

| 상태 | 처리하기 버튼 |
|---|---|
| `NEW` | `주문확인`, `소싱하기`, `주문취소` |
| `PREPARING` | 목록은 `소싱하기`, `주문취소`; 상세 처리하기는 `소싱하기`, `국내송장 등록`, `마켓 직접전달`, `주문취소` |
| `READY_TO_SHIP` | 목록은 `배송중 처리`; 상세 처리하기는 `배송중 처리`, `결제완료 보기`, `주문취소` |
| `SHIPPING` | 조회 전용 |
| `DELIVERED` | 조회 전용 |
| `CLAIM` | `취소처리`, `반품처리`, `교환처리` |

메인 화면 버튼 규칙:

- 아이콘 버튼은 아이콘만 표시한다.
- 텍스트 버튼은 텍스트만 표시한다.
- 메인 화면에서 아이콘과 텍스트를 한 버튼 안에 섞지 않는다.
- 사이드바 메뉴는 예외로 둔다.

## 8. 소싱하기 모달

신규주문의 `소싱하기`:

- match-only 모드로 동작한다.
- 후보/옵션 매칭 저장과 주문확인을 함께 처리한다.
- 처리 후 상품준비로 이동한다.
- 오른쪽 하단의 `주문확인` 바로 아래에 빨간 테두리 `주문취소` 버튼을 배치한다.
- 주문취소 클릭 시 소싱 대상 주문을 별도 상태로 보관하고 소싱 모달을 닫은 뒤 공통 `SellerCancelDialog`를 연다.

상품준비의 `소싱하기`:

- 추천 소싱 상품 목록을 표시한다.
- 추천 상품 그리드는 동일 높이 행과 `h-full` 카드 구조를 사용하며, 카드 상단의 기본 가격은 생략한다. 카드 하단에는 선택 옵션의 원화 가격과 재고만 표시하고 위안화 개당 가격은 표시하지 않는다.
- 후보는 썸네일, 한국어 상품명 값, 중국어 상품명 값, 판매처, 원화/위안 상품원가를 표시한다.
- 후보 카드에는 `한국어 상품명`, `중국어 상품명` 타이틀 라벨을 표시하지 않는다.
- 구매횟수, AI 매칭률, 별점, 배송일수는 표시하지 않는다.
- 추천 후보 카드마다 옵션 드롭다운을 제공하고 한국어 옵션명 아래 중국어 옵션명, 가격, 재고를 표시한다.
- 옵션이 품절이면 결제 버튼을 비활성화한다.
- 각 추천 후보 카드에 수량 증감을 제공하며 후보별 옵션 ID와 수량을 별도 상태로 유지한다. 옵션 또는 수량 변경 시 해당 후보를 현재 선택 상품으로 바꾸고 비용·마진을 다시 계산한다.
- `추천 소싱 상품` 영역에는 `키워드 또는 타오바오/소싱라이프 상품 URL 입력` 필드와 `찾기` 버튼을 배치한다.
- 기본 이미지 매칭 후보 20개를 먼저 표시한다.
- 키워드 찾기는 새 더미 후보 20개를 기존 후보 목록 상단에 추가한다.
- URL 찾기는 타오바오 또는 소싱라이프 URL만 허용하며, 허용 URL이면 해당 상품 1개를 기존 후보 목록 상단에 추가한다.
- 소싱 모달은 `후보/옵션 → 배대지 수령 프로필 → 결제대기/채팅 → 결제` 단계를 분리한다.
- 옵션 선택 카드의 상품 요약은 선택 후보 썸네일과 상품명, `MARKET_LABELS[order.marketType]`을 사용한다.
- 마진 계산은 주문의 `paymentPrice`를 시작값으로 하고 `platformFee`를 독립 차감한다. `platformFee`가 0이면서 `expectedSettlement`이 있으면 결제금액과 정산예정금액 차이를 판매 수수료로 보완한다.
- 소싱 비용은 상품가와 분리해 `sourcingServiceFee`, `currencyExchangeFee`, `estimatedForwarderShippingFee`로 계산한다. 더미 기본값은 상품가의 3%, 2.5%를 각각 원 단위 절사하고 예상 운임 4,750원을 사용하며, 실서비스에서는 소싱라이프 견적 응답값으로 교체한다.
- 마진율 분모는 마켓 결제금액 `paymentPrice`를 사용한다.
- 배대지 선택 단계는 `MarginAnalysis`를 왼쪽 상품 요약 아래에 `wide` 레이아웃으로 렌더링하고, 오른쪽 `PaymentSummary`는 `costOnly` 상태로 소싱 총비용만 노출한다. 실제 결제 단계에서는 전체 비용·마진 요약을 유지한다.
- 구매대행 신청 콜백은 주문을 `PAYMENT_WAITING`으로만 전환하고 결제 완료 콜백을 호출하지 않는다.
- 결제대기 주문은 처리하기에 `결제하기`를 표시하며 외부 구매·직접전달 버튼은 함께 노출하지 않는다.
- `결제하기`는 `status === PREPARING`이면서 투영 단계가 `PAYMENT_WAITING`일 때만 렌더링한다. 발송대기·배송중·배송완료의 미결제 조합은 `결제상태 불일치` 배지로 표시하고 송장 전송·배송중 전환을 차단한다.
- `SOURCED` 주문은 상세 처리하기에 `결제완료 보기`를 표시한다. `CHINA_SHIPPING`, `CUSTOMS_CLEARANCE`, `DOMESTIC_SHIPPING`은 진행상태 배지만 렌더링하고 조회 버튼이나 모달 메타데이터를 생성하지 않는다.
- 실서비스 결제완료 콜백은 선택 배송대행지 사이트 열기 → 주문서 자동입력 → 단일 접수 단계(`접수대기`=`접수신청`) → 국내송장 즉시 회수까지 오케스트레이션한다. 결제·접수·송장 사건은 분리 저장하고 접수 실패에도 결제 성공을 보존한다.
- 현재 프로토타입의 `handleCompleteSourcingPayment`는 외부 배송대행지 화면과 접수 API를 구현하지 않고 `createDummyInvoice`를 즉시 호출한다. 자동 배송중 처리 ON은 `uploadedToMarketAt`과 마켓 배송중 상태를 로컬에서 시뮬레이션하고, OFF는 국내송장을 저장한 `READY_TO_SHIP`으로 이동한다.
- 결제완료 조회 화면은 결제정보·주문번호·선택 배송대행지·주문서 접수 및 국내송장 반영 결과를 표시해야 한다.
- 더미 주문은 로딩 시 상태별 필수 필드를 정규화한다. 결제대기는 유효 통관부호·소싱상품·배대지·신청시각만, 소싱라이프 결제완료는 여기에 실제 결제정보·소싱라이프 주문번호·국내송장을 추가로 가져야 한다. 의도된 통관부호 불일치 더미는 결제 전 신규주문·상품준비에만 유지한다.
- 테이블 셀 재마운트로 모달이 닫히지 않도록 활성 소싱 주문 상태는 주문 페이지 수준에서 관리한다.

## 9. 택배정보/배송중 처리

발송대기:

- `자동 배송중 처리` 토글을 제공한다.
- 상품준비와 발송대기의 토글은 `jumunpangpang.autoShipping` 단일 localStorage 값을 공유한다.
- 일괄 `배송중 처리` 버튼은 송장번호가 있고 직접전달로 이미 처리되지 않은 주문만 대상으로 한다.
- 발송대기 전역 액션은 체크된 주문이 있으면 체크된 주문을 우선 대상으로 하고, 체크가 없으면 현재 필터에 보이는 주문을 대상으로 한다.
- 일괄 `배송중 처리`는 송장번호가 있고 직접전달로 이미 처리되지 않은 주문만 실제 처리 대상으로 처리한다.

행:

- 발송대기에서는 구매 완료 시 저장된 택배사와 송장번호를 표시한다.
- 송장 누락은 정상 목록 상태가 아니라 구매 완료 또는 연동 오류로 처리한다.
- 정상 발송대기 주문은 송장을 보유한다. `배송중 처리`는 모달 없이 `onSendInvoice`를 즉시 호출하며, 방어적으로 송장이 누락된 경우 상태를 변경하지 않고 오류 안내를 표시한다.
- 발송대기 목록 처리하기는 `배송중 처리`만 렌더링하고, 상세 처리하기는 `배송중 처리 → 결제완료 보기 → 주문취소` 순으로 렌더링한다.
- `마켓 직접전달`은 상품준비 상세의 처리하기에서만 제공하며 발송대기의 `배송중 처리`에는 방식 선택 모달을 렌더링하지 않는다.
- `marketDeliveryMethod === DIRECT_DELIVERY`이면 상태와 관계없이 판매자 `주문취소` 액션을 렌더링하지 않는다.

배송중:

- 송장 수정 버튼은 제공하지 않는다.
- 변경된 송장번호 항목은 표시하지 않는다.

## 10. 마켓연동 화면

`/me/markets` 화면 구성:

- 우측 상단 `마켓 추가` 버튼.
- 목록 컬럼: 마켓, 스토어명, 연동상태, 활성, 관리.
- 관리 영역의 `설정` 버튼은 마켓 추가와 동일한 계정 수정 모달을 연다.
- 삭제 버튼은 삭제 확인 모달 후 삭제한다.

마켓 추가/수정 모달:

- 마켓 선택 드롭다운: 스마트스토어, 쿠팡, 11번가, G마켓, 옥션.
- 공통 필수: 스토어명, 사업자번호.
- 스마트스토어: 연동용 판매자 ID, 클라이언트 아이디, 클라이언트 시크릿.
- 쿠팡: 쿠팡 업체코드, Access Key, Secret Key, 쿠팡 윙 로그인 ID.
- 11번가: API Key.
- G마켓/옥션: Master ID, Seller ID.

현재 MVP에서 제공하지 않는 항목:

- 플랫폼 수수료율
- 마지막 수집
- 결과
- 결제카드
- 별도 계정설정 페이지

## 13. 검증 기준

현재 저장소에는 테스트 러너가 없다.
의미 있는 프론트 또는 문서 기준 변경 후 검증은 다음 기준으로 한다.

- `npm run lint`
- `npm run build`

`npm test`는 현재 `package.json`에 정의되어 있지 않으므로 사용하지 않는다.
