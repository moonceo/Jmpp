# 프론트엔드 구현 기준

## 1. 현재 구현 전제

현재 MVP는 백엔드 없이 Next.js App Router, React, TypeScript, Tailwind CSS, shadcn/ui 조합으로 구현한다.
주문 데이터는 mock data와 클라이언트 상태를 기준으로 동작하며, 일부 소싱/송장 결과는 localStorage에 저장한다.
커머스라이프는 독립 주문관리 서비스이며, 주문수집 원천은 마켓 주문으로 한정한다.
소싱라이프에서 직접 생성하거나 주문한 내역은 주문수집 데이터로 넣지 않는다.
소싱라이프 연동으로 받은 구매, 검수, 입고, 물류 상태와 결과는 커머스라이프 내부 UI에서 조회한다. 소싱라이프 주문내역 이동 링크는 구현하지 않는다.

실제 패키지 기준:

- Next.js 16.1.4
- React 19.2.3
- TypeScript 5 strict mode
- Tailwind CSS 4
- shadcn/ui 스타일의 Radix 기반 UI primitive

경로 별칭은 `@/*`를 사용한다.
공유 타입은 `types/`, 도메인 상수는 `lib/constants/`, mock fixture는 `lib/mock-data/`, 공유 client state는 `lib/stores/` 기준으로 둔다.

현재 주문 MVP의 주요 데이터 흐름은 React state, mock data, localStorage 중심이다.
React Query는 의존성에 포함되어 있으나 주문관리 핵심 데이터 로딩에는 아직 사용하지 않는다.
Zustand는 현재 대시보드 store 중심으로 사용한다.

## 2. 실제 라우트

| 라우트 | 화면 |
|---|---|
| `/orders` | 주문관리 > 주문수집, 기본 신규주문 |
| `/orders?view=all` | 처리보류를 포함한 전체주문 |
| `/orders?view=new` | 신규주문 |
| `/orders?view=preparing` | 상품준비 |
| `/orders?view=waiting` | 발송대기 |
| `/orders?view=shipping` | 배송중 |
| `/orders?view=delivered` | 배송완료 |
| `/orders?view=claims` | 취소/반품/교환 |
| `/me/markets` | 주문관리 > 마켓연동 |

`all` view와 `ORDER_STATUSES.ALL`은 실제 전체주문 탭에 사용한다. `ON_HOLD` 주문은 이 화면과 `처리보류` 필터에서 조회하고 일반 처리 액션을 렌더링하지 않는다.

## 3. 주문관리 메뉴 구조

사이드바 상단 브랜드는 `커머스라이프`로 표시하고 주문관리 외 상위 서비스 메뉴와 타오바오/1688 전환은 렌더링하지 않는다. 아이템 검색, 찜 리스트, 장바구니, 주문 내역, 배송 조회, 통관고유부호도 메뉴 정의에 포함하지 않는다.

좌측 메뉴의 주문관리 하위 메뉴:

- 주문수집
- 취소/반품/교환
- 문의관리
- 마켓연동

주문수집 내부 상태는 본문 상단 탭으로 제공한다.

- 신규주문
- 상품준비
- 발송대기
- 배송중
- 배송완료

## 3-1. 모노크롬 디자인 시스템

- 모노크롬 전환은 기존 화면의 색상만 교체하는 작업이 아니다. 전체 라우트는 공통 shadcn/ui 대시보드 앱 셸과 기능별 페이지 템플릿으로 재구성한다.
- 공통 앱 셸은 `SidebarProvider` 기반의 접이식 사이드바, 그룹형 업무 내비게이션, 상단 헤더, 사이드바 트리거, 브레드크럼, 서비스 상태 표시, 본문 작업 영역으로 구성한다.
- 주문수집·클레임·문의·마켓연동·장부 화면은 공통 `PageHeader`를 사용하고, 검색·필터·탭·테이블 등 실제 작업 영역은 `Card` 기반 패널 안에 배치한다.
- 독립 페이지마다 사이드바나 상단 헤더를 복제하지 않는다. `components/application-shell.tsx`와 `components/app-sidebar.tsx`에서 앱 셸을 공유한다.
- CSS 변수 또는 컬러 utility만 변경하고 기존 독립형 레이아웃을 유지한 상태는 대시보드 전환 완료로 보지 않는다.
- `app/globals.css`의 shadcn/ui CSS 변수는 chroma가 없는 검정·흰색·무채색 값만 사용한다.
- 기능 화면은 `bg-background`, `bg-card`, `bg-muted`, `bg-primary`, `text-foreground`, `text-muted-foreground`, `text-primary-foreground`, `border-border`, `ring-ring` semantic utility를 사용한다.
- 마켓, 주문상태, 성공, 경고, 오류를 빨강·초록·파랑 등 유채색으로 구분하지 않는다. 채움, 테두리, 굵기, 명도 대비와 텍스트 라벨을 함께 사용한다.
- 기능 컴포넌트에서 raw `button`, `input`, `select`, `textarea`, `table`을 직접 사용하지 않고 `components/ui`의 shadcn/ui primitive를 사용한다. primitive 구현 파일은 이 규칙의 예외다.
- `components/ui` 기반 파일은 공식 shadcn 레지스트리 소스를 기준으로 관리한다. 공식 컴포넌트가 있는 기능을 별도 raw control이나 자체 primitive로 다시 만들지 않는다.
- 기능 화면의 상호작용은 `Button`, `Input`, `Select`, `Switch`, `Checkbox`, `Tabs`, `ToggleGroup`, `Popover`, `DropdownMenu`, `Dialog`, `Table`을 사용하고, 폼 구조는 `Field`, 상태 안내는 `Alert`, 빈 상태는 `Empty`, 반복 목록은 `Item`을 우선 사용한다.
- `form`, `main`, `section`, `header`와 일반 배치용 `div`처럼 shadcn에 대응 primitive가 없는 시맨틱 HTML은 유지할 수 있다. 다만 버튼·입력·선택처럼 사용자 조작을 받는 요소를 raw HTML로 구현하지 않는다.
- 일반 UI 텍스트는 `text-sm` 14px을 기본으로 하고, 캡션·시간·배지·보조 메타데이터에만 `text-xs` 12px을 사용한다. 12px 미만 글자는 허용하지 않는다.
- 본문은 사이드바 이후 왼쪽에서 시작해 `w-full min-w-0`으로 전체 가용 너비를 사용한다. 페이지 프레임에 `container`, `mx-auto`, 중앙 정렬 `max-w-*`를 기본 적용하지 않는다.
- 인라인 색상과 브랜드 hex 값은 사용하지 않는다. 데이터 시각화도 `--chart-1`부터 `--chart-5`까지의 무채색 토큰을 사용한다.

## 4. 검색/필터 구현

- 기간 버튼: `오늘`, `3일`, `7일`, `30일`, `직접 입력`.
- 검색 placeholder: `상품명, 주문번호, 주문자, 수령인 검색`.
- 마켓/스토어 필터는 하나의 아이콘 버튼으로 제공한다.
- 마켓과 스토어는 중복 선택 가능하다.
- 선택한 마켓과 관계없는 스토어는 비활성화한다.
- 마켓/스토어를 아무것도 선택하지 않으면 전체 주문을 표시한다.
- 마켓만 선택하면 선택한 마켓의 전체 스토어 주문을 표시한다.
- 스토어만 선택하면 해당 스토어 주문을 표시하고, 이때 스토어가 속한 마켓은 자동 포함된 것으로 본다.
- 마켓과 스토어를 함께 선택하면 선택한 마켓 안에서 선택한 스토어 주문만 표시한다.
- 단계별 상태 필터 옵션은 현재 주문 배열에서 추출하지 않고 주문 단계별 고정 허용 목록으로 관리한다.
- 판매처 드롭다운 옵션은 공통 `MARKET_ABBREVIATIONS`, `MARKET_BADGE_CLASSES`를 사용해 마켓별 네모 약자 아이콘과 스토어명을 표시한다.
- 해당 상태의 주문이 0건이어도 그 단계에서 조회 가능한 옵션은 드롭다운에 유지한다.
- 배송완료 주문은 모두 `배송완료` 상태값을 가지며, `marketOrderStatus === "PURCHASE_DECIDED"`이면 `구매확정` 필터 값을 추가한다.
- 상태 필터는 단일 파생값을 비교하지 않고 주문이 가진 상태값 목록에 선택값이 포함되는지 확인한다.
- 단계별 도구 영역은 `justify-between` 구조로 나누고 액션 버튼 그룹은 왼쪽, 필터와 설정 그룹은 오른쪽에 배치한다.
- 클레임 유형 필터는 액션 버튼 JSX와 분리해 오른쪽 필터 그룹에서 렌더링한다. 발송대기 송장 유무 필터는 제공하지 않는다.
- 필터는 주문 목록 조회 조건이며 주문수집 실행 범위 제한이 아니다.
- `주문수집` 버튼은 상단 우측 공통 액션으로 유지한다.

## 5. 주문 테이블 컬럼

주문수집 테이블 컬럼 순서:

1. 선택
2. 처리하기
3. 주문일시
4. 진행상태
5. 상품정보
6. 택배정보
7. 배송정보

`OrderDateCell`은 날짜와 시간 아래에 `MARKET_ABBREVIATIONS`의 `N`, `C`, `G`, `11`, `A` 아이콘과 `storeName`을 표시한다. 별도 `marketAccount` 컬럼은 생성하지 않는다.

진행상태 컬럼은 `getOrderProgressLabel()`이 계산한 대표 배지 하나만 표시한다. 우선순위는 `소싱환불·소싱반품 → 구매확정 → 기본 소싱 진행상태`이며 `MATCH_PENDING_REVIEW`는 `소싱필요`, 환불 `REQUESTED/PROVIDER_REVIEW`는 `소싱환불 승인대기`로 합친다. `CANCEL_REQUESTED`, `ON_HOLD`, 마켓 배송중·배송완료는 대표 상태로 생성하지 않는다.
결제완료부터 배송완료까지 `배송추적`은 행 자세히 보기의 처리하기에만 렌더링한다. 공통 모달의 단계·누적 이벤트 계산은 `lib/delivery-history.ts`에서 관리하고, `결제완료 → 중국배송 → 통관 → 국내배송 → 배송완료`와 후속 반품·교환을 누적한다.
결제완료 이후의 `소싱상품관리`는 행 자세히 보기의 처리하기에만 구현하고 소싱상품 영역에는 중복 배치하지 않는다.
소싱 배지는 마켓 주문상태에서 계산하지 않고, 별도 소싱 진행 단계가 있으면 그 값을 우선 사용한다.
별도 단계가 없을 때만 소싱라이프 매칭/결제/송장 수신 상태로 보수적으로 추정한다.
배송완료 주문은 명시적으로 `배송완료` 소싱 단계를 가진 더미데이터를 사용해 `중국배송중`으로 잘못 보이지 않게 한다.
상태 projection은 실주문과 데모 주문에서 동일하게 `PAYMENT_READY → 결제대기`, `PAID/INVOICE_RECEIVED → 결제완료`, `EXTERNAL_PURCHASE → 결제완료`를 사용한다. `EXTERNAL_PURCHASE` 내부값은 유지하되 `sourcingLifeMatch`가 없으므로 자세히 보기의 소싱상품 영역은 렌더링하지 않는다. 국내송장 수신만으로 중국배송중을 추정하지 않으며 취소·클레임 처리로 소싱 상태를 `HOLD`로 덮어쓰지 않는다.

전체 페이지에는 좌우 스크롤이 생기지 않게 한다.
필요 시 테이블 내부에서만 가로 스크롤을 허용한다.
컬럼 폭은 메뉴별로 최대한 동일하게 유지한다.

## 6. 행 확장 상세

주문 행을 클릭하면 자세히 보기 영역을 펼친다.
넓은 화면의 상세는 다음 3열로 나눈다.

1. 왼쪽 22%, 최소 320px: 구매자 · 배송정보, 택배정보
2. 가운데 가변 60%: 상품 비교, 마진계산
3. 오른쪽 18%, 최소 260px: 처리하기

상세의 구매자는 이름과 연락처만 표시한다.
상세의 배송정보는 신규주문·상품준비·발송대기 demo 주문에서 왼쪽 구매자·배송정보 카드의 수정 버튼으로 변경한다. 상세 `처리하기`에는 같은 버튼을 중복 렌더링하지 않으며, 실주문과 배송중 이후에는 왼쪽 수정 버튼도 숨긴다.
`Order.sourcingLifeMatch`가 있을 때만 상품 비교를 렌더링해 화면 크기와 관계없이 주문상품 아래에 소싱상품을 쌓는다. 매칭값이 없으면 소싱상품 카드와 빈 상태 안내를 생략하고 주문상품 카드만 렌더링한다.
`Order.sourcingLifeMatch`가 있을 때만 상세 `마진계산` 카드를 렌더링한다. 상품원가는 `sourcingLifeActualPayment.amount → sourcingLifeMatch.estimatedCost → expectedCost` 순으로 선택하고 기존 `calculateSourcingMargin`을 사용한다. 계산값은 매출·정산, 예상 소싱비용, 예상 순이익·마진율 3영역을 한 열에 세로로 표시하며 원가가 없으면 계산 대기 안내를 렌더링한다.
구매자와 수령 정보는 왼쪽 카드 내부에서 1열로 쌓고, 택배정보는 같은 왼쪽 영역의 다음 카드로 렌더링한다. 택배정보에는 국내 송장번호와 중국 송장번호를 각각 한 줄로 표시하고 없는 번호는 `-`로 렌더링한다. 직접전달 주문에만 두 번호 사이에 `직접전달` 배지를 렌더링한다.
`OrderDetailPanel`의 바깥 영역은 `xl` 이상에서 `minmax(320px, 22%) minmax(0, 1fr) minmax(260px, 18%)` 3열로 렌더링한다. 가운데는 남은 약 60%를 사용해 상품 영역의 우선순위를 유지하면서도 왼쪽 주소와 오른쪽 버튼이 지나치게 좁아지지 않게 한다. `xl` 미만에서는 상품 영역, 구매자·배송정보와 택배정보, 처리하기 순서의 한 열로 전환한다.

행 상세와 체크 선택은 탭, 검색어, 필터, 데이터 변경 시 현재 화면 기준으로 초기화한다.
다른 탭에서 선택한 체크 상태가 현재 탭으로 이어져 보이면 안 된다.

## 7. 상태별 버튼

| 상태 | 처리하기 버튼 |
|---|---|
| `NEW` | 목록·상세 처리하기는 `주문확인`, `매칭하기`, `주문취소` |
| `PREPARING` | 목록은 `소싱하기`, `주문취소`만 표시; 상세 처리하기는 진행단계별 결제, `외부구매 배송처리`, 조건부 `마켓 직접전달` 추가 |
| `READY_TO_SHIP` | 외부 구매 등 호환 흐름에서 목록·상세 `배송중 처리`; 상세는 `운송장 수정/등록` 등 허용 기능 추가 |
| `SHIPPING` | 목록 처리하기는 비움; 상세에 `소싱상품관리`, `배송추적`, 조건부 `배송중 처리`, 처리 시작 전 `운송장 수정` 제공 |
| `DELIVERED` | 목록 처리하기는 비움; 상세에서 `소싱상품관리`, `배송추적` 제공. 기존 환불 조회는 `소싱상품관리` 안에서 제공 |
| `CLAIM` | 진행 중 `취소처리`, `반품처리`, `교환처리`; 소싱 결제정보·물류·환불 원장이 있으면 `소싱상품관리`, `배송추적`을 함께 제공하고 환불 조회는 `소싱상품관리` 안에서 제공 |

메인 화면 버튼 규칙:

- 아이콘 버튼은 아이콘만 표시한다.
- 텍스트 버튼은 텍스트만 표시한다.
- 메인 화면에서 아이콘과 텍스트를 한 버튼 안에 섞지 않는다.
- 사이드바 메뉴는 예외로 둔다.

## 8. 매칭하기/소싱하기 모달

신규주문의 `매칭하기`:

- match-only 모드로 동작한다.
- 후보/옵션 매칭 저장과 주문확인을 함께 처리한다.
- 처리 후 상품준비로 이동한다.
- 오른쪽 하단의 검정 채움 `주문확인` 바로 아래에 테두리형 `주문취소` 버튼을 배치한다.
- 주문취소 클릭 시 소싱 대상 주문을 별도 상태로 보관하고 소싱 모달을 닫은 뒤 공통 `SellerCancelDialog`를 연다.

상품준비의 `소싱하기`:

- 추천 소싱 상품 목록을 표시한다.
- 추천 상품 그리드는 동일 높이 행과 `h-full` 카드 구조를 사용하며, 카드 상단의 기본 가격은 생략한다. 카드 하단에는 선택 옵션의 원화 가격과 재고만 표시하고 위안화 개당 가격은 표시하지 않는다.
- 후보는 썸네일, 한국어 상품명 값, 중국어 상품명 값, 판매처, 원화/위안 상품원가를 표시한다.
- 후보 카드에는 `한국어 상품명`, `중국어 상품명` 타이틀 라벨을 표시하지 않는다.
- 구매횟수, AI 매칭률, 별점, 배송일수는 표시하지 않는다.
- 추천 후보 카드마다 옵션 드롭다운을 제공하고 한국어 옵션명 아래 중국어 옵션명, 가격, 재고를 표시한다.
- 옵션이 품절이면 결제 버튼을 비활성화한다.
- 각 추천 후보 카드에 수량 증감을 제공하며 후보별 옵션 ID와 수량을 별도 상태로 유지한다. 옵션 또는 수량 변경 시 해당 후보를 현재 선택 상품으로 바꾸고 비용·마진을 다시 계산한다.
- `추천 소싱 상품` 영역에는 `키워드 또는 타오바오/소싱라이프 상품 URL 입력` 필드와 `찾기` 버튼을 배치한다.
- 기본 이미지 매칭 후보 20개를 먼저 표시한다.
- 키워드 찾기는 새 더미 후보 20개를 기존 후보 목록 상단에 추가한다.
- URL 찾기는 타오바오 또는 소싱라이프 URL만 허용하며, 허용 URL이면 해당 상품 1개를 기존 후보 목록 상단에 추가한다.
- 소싱 모달은 `후보/옵션 → 배대지 수령 프로필 → 결제대기/중국 판매자 채팅 → 결제` 단계를 분리한다.
- 옵션 선택 카드의 상품 요약은 선택 후보 썸네일과 상품명, `MARKET_LABELS[order.marketType]`을 사용한다.
- 마진 계산은 주문의 `paymentPrice`를 시작값으로 하고 `platformFee`를 독립 차감한다. `platformFee`가 0이면서 `expectedSettlement`이 있으면 결제금액과 정산예정금액 차이를 판매 수수료로 보완한다.
- 소싱 비용은 상품가와 분리해 `sourcingServiceFee`, `currencyExchangeFee`, `estimatedForwarderShippingFee`로 계산한다. 더미 기본값은 상품가의 3%, 2.5%를 각각 원 단위 절사하고 예상 운임 4,750원을 사용하며, 실서비스에서는 소싱라이프 견적 응답값으로 교체한다.
- 마진율 분모는 마켓 결제금액 `paymentPrice`를 사용한다.
- 배대지 선택 단계는 왼쪽에 주문상품, 소싱상품, `MarginAnalysis`, 배송대행지 선택 섹션을 이 순서로 렌더링한다. 주문상품과 소싱상품은 별도 카드로 구분하고 `MarginAnalysis`는 `wide` 레이아웃을 사용한다. 오른쪽 `PaymentSummary`는 `costOnly` 상태로 소싱 총비용·실행 버튼·결제대기 전환 안내를 노출하며, 안내는 카드 최하단에 배치한다. 실제 결제 단계에서는 전체 비용·마진 요약을 유지한다.
- 구매대행 신청 콜백은 주문을 `PAYMENT_WAITING`으로만 전환하고 결제 완료 콜백을 호출하지 않는다.
- 결제대기 주문은 처리하기에 `결제하기`를 표시하며 외부 구매·직접전달 버튼은 함께 노출하지 않는다.
- 결제대기와 결제완료는 `SourcingProgressView`의 공통 `결제·채팅` 작업공간을 사용한다. 데스크톱은 왼쪽 상태별 업무정보와 오른쪽 400px 중국 판매자 채팅 패널을 독립 스크롤 영역으로 구성하고, 모바일은 두 영역을 세로로 쌓는다. 채팅 패널은 두 상태 모두 메시지 내역·입력·전송을 유지한다. 결제대기에만 shadcn `ButtonGroup`으로 `깎아줘`, `깎아줘 취소`를 표시하고 `PriceNegotiationStatus`로 중복 요청과 무효 취소를 막는다. `canProceedToPayment()`가 요청 중 결제 진입을 차단하고 취소 후 허용한다.
- 결제대기 상세에서는 상단 구매대행 접수 안내 카드와 `판매자 채팅` 배지를 렌더링하지 않는다. `PaymentWaitingProductComparison`은 원주문 `order.product`와 저장된 소싱 매칭 상품을 2열로 비교하고, `PaymentWaitingCostSummary`는 `calculateSourcingMargin(order, amount)` 결과로 상품원가·이용료·환전 수수료·예상 배송비·예상 총비용·예상 순이익·마진율을 표시한다. 상태는 색상만으로 구분하지 않고 `수익 예상` 또는 `역마진 예상` 배지를 함께 표시한다. 하단 고정 작업 영역에는 `주문 취소하기`와 금액을 포함하지 않은 `상품 결제하기`를 같은 행으로 배치한다. `주문 취소하기`는 `onRequestCancel`을 통해 기존 `SellerCancelDialog`를 열고, `상품 결제하기`는 기존 가격 협상 상태 가드를 유지한다.
- `결제하기`는 `status === PREPARING`이면서 투영 단계가 `PAYMENT_WAITING`일 때만 렌더링한다. 발송대기·배송중·배송완료의 미결제 조합은 `결제상태 불일치` 배지로 표시하고 송장 전송·배송중 전환을 차단한다.
- 소싱 결제완료부터 배송완료까지 `SOURCED`, `CHINA_SHIPPING`, `CUSTOMS_CLEARANCE`, `DOMESTIC_SHIPPING`, `DELIVERED` 전 단계에 `소싱상품관리` 메타데이터를 생성한다. 행 자세히 보기 버튼만 `SourcingWorkflowDialog`를 열고 결제상품·결제정보와 중국 판매자 채팅을 유지한다.
- 소싱 환불 진입점은 `OrderProcessActions`에 별도 배치하지 않는다. `SourcingWorkflowDialog`의 구매대행 신청 상품 영역에서 상태에 따라 `반품·환불 신청`, `환불 진행`, `환불 내역`을 표시하고 환불 처리 뒤 열린 결제상품 화면의 주문 상태를 즉시 갱신한다.
- 실서비스 결제완료 콜백은 선택 배송대행지 사이트 열기 → 주문서 자동입력 → 단일 접수 단계(`접수대기`=`접수신청`) → 국내송장 즉시 회수까지 오케스트레이션한다. 결제·접수·송장 사건은 분리 저장하고 접수 실패에도 결제 성공을 보존한다.
- 현재 프로토타입의 `handleCompleteSourcingPayment`는 외부 배송대행지 화면과 접수 API를 구현하지 않고 `createDummyInvoice`를 즉시 호출한다. 결제완료 후에는 항상 내부 `SHIPPING`으로 이동한다. 자동 배송중 처리 ON은 `uploadedToMarketAt`과 마켓 배송중 상태를 로컬에서 추가 시뮬레이션하고, OFF는 마켓 상태만 결제완료로 유지한다.
- 결제완료 조회 화면은 신청 상품·결제정보·주문번호·선택 배송대행지·주문서 접수 및 국내송장 반영 결과를 왼쪽에 표시하고, 오른쪽 중국 판매자 채팅 패널에서 결제대기부터 이어진 대화를 조회·작성할 수 있어야 한다. 결제 CTA는 렌더링하지 않는다.
- 더미 주문은 로딩 시 상태별 필수 필드를 정규화한다. 결제대기는 유효 통관부호·소싱상품·배대지·신청시각만, 소싱라이프 결제완료는 여기에 실제 결제정보·소싱라이프 주문번호·국내송장을 추가로 가져야 한다. 중국배송 이후 단계의 소싱라이프 더미 주문은 중국 택배사·송장번호도 가진다. 의도된 통관부호 불일치 더미는 결제 전 신규주문·상품준비에만 유지한다.
- 테이블 셀 재마운트로 모달이 닫히지 않도록 활성 소싱 주문 상태는 주문 페이지 수준에서 관리한다.

## 9. 택배정보/배송중 처리

발송대기:

- `자동 배송중 처리` 토글을 제공한다.
- 상품준비와 발송대기의 토글은 `jumunpangpang.autoShipping` 단일 localStorage 값을 공유한다.
- 일괄 버튼 명칭은 `배송중 처리`이며 행·상세와 동일한 흐름을 사용한다.
- 발송대기 전역 액션은 체크된 주문이 있으면 체크된 주문을 우선 대상으로 하고, 체크가 없으면 현재 필터에 보이는 주문을 대상으로 한다.
- 일괄 `배송중 처리`는 조건에 맞는 주문을 모아 계정별 기본 발송 방식 건수를 확인창에 표시하고, 백엔드가 계정 설정에 따라 자동 분리한다. 이미 마켓 발송된 대상은 재전송하지 않는다.

행:

- 목록 택배정보는 국내 송장번호와 중국 송장번호를 고정 순서로 표시한다. 직접전달 주문은 두 번호 사이에 `직접전달` 배지를 추가한다.
- `marketDeliveryMethod === DIRECT_DELIVERY`일 때만 `직접전달`을 표시하며, 그 외 주문에는 직접전달 행과 문구를 렌더링하지 않는다.
- 중국 송장번호는 `chinaInvoice.trackingNumber`를 사용하고 값이 없으면 `-`로 표시한다.
- 발송대기에서는 구매 완료 시 저장된 국내 택배사와 송장번호를 표시한다.
- 송장 누락은 정상 목록 상태가 아니라 구매 완료 또는 연동 오류로 처리한다.
- 정상 발송대기 주문은 송장을 보유한다. `배송중 처리`는 하나의 handler로 연결하고, 미발송 주문에서 스토어 기본 발송 방식을 읽기 전용으로 확인한다.
- 소싱라이프 결제완료부터 배송완료까지 상세 처리하기에는 같은 `소싱상품관리` 명칭을 항상 사용하고 목록에는 렌더링하지 않는다.
- 상품준비 상세의 `배송중 처리`는 기본값이 직접전달인 스마트스토어·11번가에서만 활성화한다. 기본값이 송장전송이면 결제·국내송장 확보 전에는 숨긴다.
- 마켓 발송이 이미 완료된 발송대기 주문도 버튼명은 `배송중 처리`로 유지하되 모달을 생략한다. API 주문은 `SHIPPING_PROCESS` 하나를 보내며 백엔드 대사 결과로 내부 상태만 완료한다.
- `marketOrderStatus === DELIVERING`이면 판매자 `주문취소` 액션을 렌더링하지 않는다.

배송중:

- `shippingProcessStarted`가 거짓인 마켓 미제출 주문에만 상세 `운송장 수정`을 제공한다. 배송중 처리 명령 접수 직후 값을 참으로 반영하고, 주문 재조회에서도 진행 중·성공 명령을 기준으로 복원한다.
- 국내송장 저장 API도 진행 중·성공한 `SHIPPING_PROCESS`, `INVOICE_SUBMIT`, `DIRECT_DELIVERY` 명령이 있으면 수정을 거부한다.
- 마켓 제출 후에는 내부 수정 버튼, 판매자센터 이동 버튼, 주문별 수정내역 재수집 버튼을 모두 렌더링하지 않는다.
- 변경된 송장번호 항목은 표시하지 않는다.

## 10. 마켓연동 화면

`/me/markets` 화면 구성:

- 우측 상단 `마켓 추가` 버튼.
- 목록 컬럼: 마켓, 스토어명, 기본 발송방식, 연동상태, 활성, 관리.
- 관리 영역의 `설정` 버튼은 마켓 추가와 동일한 계정 수정 모달을 연다.
- 삭제 버튼은 삭제 확인 모달 후 삭제한다.

마켓 추가/수정 모달:

- 마켓 선택 드롭다운: 스마트스토어, 쿠팡, 11번가, G마켓, 옥션.
- 공통 필수: 스토어명, 사업자번호.
- 스마트스토어·11번가 공통 필수: 배송중 처리 기본값(`송장전송`, `직접전달`).
- 쿠팡·G마켓·옥션: 기본 발송방식을 `송장전송`으로 고정한다.
- 스마트스토어: 연동용 판매자 ID, 클라이언트 아이디, 클라이언트 시크릿.
- 쿠팡: 쿠팡 업체코드, Access Key, Secret Key, 쿠팡 윙 로그인 ID.
- 11번가: API Key.
- G마켓/옥션: Master ID, Seller ID.

현재 MVP에서 제공하지 않는 항목:

- 플랫폼 수수료율
- 마지막 수집
- 결과
- 결제카드
- 별도 계정설정 페이지

## 12. 와이어프레임 문서 기준

현재는 별도 정적 와이어프레임을 먼저 만든 것이 아니라 실제 프론트 프로토타입을 먼저 구현했다.
따라서 `docs/09_와이어프레임`의 HTML은 현재 화면을 페이지별/모달별로 확인하기 위한 정적 참조 파일로 유지한다.

- 페이지 HTML: 주문수집 5개 상태, 취소/반품/교환, 마켓연동
- 모달/팝오버 HTML: 주문상세, 소싱하기, 외부구매 배송처리, 배송정보 수정, 주문취소 확인, 마켓 추가/수정, 마켓 삭제 확인, 클레임 처리, 이미지 크게보기, 직접 기간 선택, 마켓/스토어 필터

## 13. 검증 기준

현재 저장소는 Vitest 테스트 러너를 사용한다. 의미 있는 변경 후 다음 순서로 검증한다.

- `npm run lint`
- `npm run test`
- `npm run build`

단일 파일은 `npm run test:single -- path/to/file.test.ts`로 검증한다.

## 14. 현재 프론트 미연결 기능

현재 프론트 프로토타입에는 다음 기능이 아직 연결되지 않았다. 기능 자체는 `10_리펀디_벤치마킹/`에 유지하며 MVP 선정 후 화면·상태·API를 추가한다.

- 타오바오 직접 결제
- 내부 배대지/창고 관리
- 배송중 송장 변경 API 전송
- 플랫폼 수수료율 설정 화면
- 처리이력 전용 화면

## 15. 리펀디 재검증 반영 구조

| 경로·모듈 | 역할 |
|---|---|
| `/dashboard` | 월간 운영 지표와 처리할 작업의 시작 화면 |
| `/journey` | 주문 상태 투영, 그룹·타일 집계, 이슈 작업함 |
| `/me/notifications` | 고객·셀러 알림 정책 데모와 메시지 미리보기 |
| `lib/order-journey.ts` | 상태 그룹, 라벨, 투영·이슈 판정의 순수 함수 |
| `lib/inquiry-ai-draft.ts` | 외부 호출 없이 안전한 문의 답변 초안을 만드는 순수 함수 |

주문현황의 이슈 제외·미루기와 알림 설정은 현재 컴포넌트 로컬 상태다. 실서비스 전환 시 tenant·사용자 범위를 포함한 서버 정책, 감사로그, 멱등 저장으로 교체한다. 상태 투영과 AI 초안 규칙은 각각 단위 테스트를 유지한다.
