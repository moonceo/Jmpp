# 주문팡팡 내부정책

## 1. 문서 목적

이 문서는 주문팡팡의 주문수집, 마켓 계정 관리, 주문상태, 소싱라이프 연동, 국내송장 처리, 장부 연계에 대한 내부 운영 기준을 정의한다.

내부정책은 서비스 기획, UI/UX 명세, 기능명세, API/아키텍처, 운영 매뉴얼이 서로 충돌하지 않도록 하는 기준 문서다.

## 2. 마켓 연동 정책

최종 연동 대상은 네이버 스마트스토어, 쿠팡, 11번가, 지마켓, 옥션이다.
초기 활성 연동은 네이버 스마트스토어와 쿠팡으로 한다.
11번가, 지마켓, 옥션은 확장 예정 마켓으로 관리하고 순차적으로 활성화한다.

주문팡팡은 마켓별 다중 계정 등록을 지원한다.
사용자는 동일 마켓 안에서도 여러 개의 스토어 또는 판매자 계정을 등록할 수 있다.
등록 가능한 계정 수에는 제한을 두지 않는다.

## 3. 주문수집 대상 정책

주문수집은 활성화된 모든 연동 계정을 대상으로 실행한다.

초기 범위에서는 다음 기능을 제공하지 않는다.

- 특정 판매처만 주문수집
- 특정 계정만 주문수집

마켓 필터와 계정 필터는 주문 목록 조회용 필터다.
필터를 변경해도 주문수집 대상 계정은 바뀌지 않는다.

계정 하나의 인증이 실패해도 다른 계정의 주문수집은 계속 진행한다.
실패는 연동 계정 단위로 기록하고 표시한다.

## 4. 주문 식별 정책

주문은 마켓과 연동 계정을 함께 기준으로 식별한다.

| 단위 | 식별 기준 |
|---|---|
| 주문 단위 | 마켓 + 연동 계정 + 마켓 주문번호 |
| 주문상품 단위 | 마켓 + 연동 계정 + 상품주문번호 |

동일한 마켓 주문번호라도 연동 계정이 다르면 별도 주문으로 관리한다.
주문 목록에는 마켓과 연동 계정을 별도 정보로 표시한다.

## 5. 주문상태 정책

주문팡팡은 내부 주문상태를 기준으로 화면과 기능을 동작시킨다.

| 코드 | 라벨 | 정책 |
|---|---|---|
| `NEW` | 신규주문 | 마켓 결제완료 주문 수집 후 주문확인 전 |
| `PREPARING` | 상품준비 | 주문확인 완료 후 소싱라이프 구매 진행 |
| `READY_TO_SHIP` | 발송대기 | 소싱라이프 결제 완료 후 국내송장 또는 송장전송 대기 |
| `SHIPPING` | 배송중 | 마켓 송장전송 성공 후 |
| `DELIVERED` | 배송완료 | 마켓 배송완료 또는 구매확정 |
| `CLAIM` | 취소/반품/교환 | 취소, 반품, 교환 처리 대상 |

마켓 원문 상태는 내부 상태로 변환해 사용한다.
화면에는 마켓별 원문 상태 차이를 직접 노출하지 않는다.

## 6. 주문확인 정책

신규주문에서 다음 단계로 이동하는 사용자-facing 액션명은 `주문확인`으로 한다.

`주문확인`이 성공하면 주문상태는 `PREPARING`으로 변경된다.
일괄 주문확인은 `NEW` 상태 주문에만 적용한다.
실패한 주문은 `NEW` 상태에 남기고 실패 사유를 표시한다.

`주문취소`는 신규주문 테이블 행 액션으로 제공한다.
주문상세 모달 하단의 다음 단계 버튼에는 포함하지 않는다.

## 7. 소싱라이프 연동 정책

소싱라이프는 주문팡팡 내부 기능이 아니라 외부 소싱/구매 서비스다.

주문팡팡은 다음 결과만 주문 단위로 관리한다.

- 소싱 후보 조회 여부
- 매칭 상품과 옵션
- 소싱라이프 주문번호
- 소싱라이프 결제 완료 여부
- 실제결제금액
- 국내송장 확보 여부

소싱라이프 내부의 구매, 검수, 입고, 물류 상세 처리는 주문팡팡 범위가 아니다.

## 8. 소싱하기 정책

`소싱하기`는 주문상태에 따라 동작 범위가 다르다.

| 상태 | 정책 |
|---|---|
| `NEW` | 소싱 후보 확인, 매칭 저장, 주문확인을 함께 처리 |
| `PREPARING` | 소싱 후보 확인, 옵션 선택, 매칭 저장, 소싱라이프 결제 화면 이동 |

상품준비 단계의 소싱라이프 결제 화면 이동은 `소싱하기` 흐름 안에서 처리한다.
별도 독립 액션으로 분리하지 않는다.

소싱 후보가 없거나 적합하지 않으면 `후보 없음, 소싱라이프에서 찾기` 버튼을 제공한다.
이 버튼은 운영자가 소싱라이프로 이동해 직접 검색 또는 이미지 검색으로 상품을 찾는 흐름이다.

## 9. 소싱상태 정책

소싱상태는 주문상태를 대체하지 않는다.
소싱상태는 소싱라이프 연동 진행도를 보조적으로 표시한다.

| 코드 | 라벨 |
|---|---|
| `NOT_LINKED` | 소싱 전 |
| `MATCHING` | 이미지 매칭 중 |
| `MATCH_SAVED` | 매칭 저장 |
| `PAYMENT_READY` | 결제 가능 |
| `PAID` | 소싱라이프 결제완료 |
| `INVOICE_RECEIVED` | 국내송장 수신 |
| `HOLD` | 처리 보류 |

`PAID`가 반영되면 주문상태는 `READY_TO_SHIP`으로 변경한다.
필수정보 누락, 매칭 실패, 결제 실패, 송장전송 실패는 소싱상태를 `HOLD`로 표시할 수 있다.

## 10. 국내송장 정책

국내송장은 `READY_TO_SHIP` 상태에서만 입력 또는 수집할 수 있다.

국내송장 입력 경로는 다음과 같다.

- 소싱라이프 자동수집
- 소싱라이프 송장 수동수집
- 운영자 수동 입력

어떤 경로로 입력되어도 국내송장은 즉시 자동저장한다.
별도 저장 버튼이나 중간 저장 단계는 두지 않는다.

국내송장 컬럼은 국내 택배사와 국내 송장번호를 함께 표시한다.
이는 같은 업무 목적의 정보이므로 하나의 컬럼에 함께 표시할 수 있다.

## 11. 자동수집과 자동 송장전송 정책

자동수집과 자동 송장전송은 서로 다른 기능이다.

| 기능 | 정책 |
|---|---|
| 자동수집 | 발송대기 주문의 국내송장을 소싱라이프에서 자동으로 가져오는 기능 |
| 송장 수동수집 | 운영자가 버튼을 눌러 소싱라이프 국내송장을 조회하는 기능 |
| 자동 송장전송 | 국내송장이 입력된 뒤 마켓에 자동으로 전송하는 기능 |

자동 송장전송은 국내송장이 자동수집, 송장 수동수집, 수동 입력 중 어떤 방식으로 입력되었는지와 관계없이 동작한다.

자동 송장전송 ON이면 국내송장 자동저장 직후 마켓 송장전송을 실행한다.
자동 송장전송 OFF이면 운영자가 `송장전송` 버튼을 눌러야 마켓으로 전송한다.

송장전송 성공 시 주문상태는 `SHIPPING`으로 변경한다.
송장전송 실패 시 주문상태는 `READY_TO_SHIP`으로 유지하고 실패 사유를 표시한다.

## 12. 주문 테이블 정책

초기버전 주문 테이블은 행 확장 구조를 사용하지 않는다.
주문 처리에 필요한 주요 정보는 테이블 컬럼으로 직접 노출한다.

컬럼 정책은 다음과 같다.

- 하나의 컬럼은 하나의 업무 목적 또는 하나의 기능 단위를 담당한다.
- 같은 업무 목적의 값과 상태 표시는 한 컬럼에 함께 표시할 수 있다.
- 서로 다른 업무 목적의 상품정보, 구매자정보, 수령인정보, 소싱정보, 송장정보, 처리버튼은 한 컬럼에 섞지 않는다.
- 개인통관부호 컬럼에는 부호 값과 일치/불일치/확인필요 상태를 함께 표시한다.
- 후보 일치율은 소싱 후보 리스트에서만 표시하고 주문 테이블에는 표시하지 않는다.
- 국내송장 수신 시각과 처리이력은 초기버전 주문 테이블에서 제외한다.

## 13. 주문상세 모달 정책

마켓 주문번호를 클릭하면 주문상세 모달을 연다.

주문상세 모달은 주문별 공통 정보를 표시하고, 하단에는 현재 주문 상태에서 가능한 다음 단계 버튼만 표시한다.

| 주문상태 | 하단 버튼 |
|---|---|
| `NEW` | `주문확인`, `소싱하기` |
| `PREPARING` | `소싱하기` |
| `READY_TO_SHIP` | `송장전송` |
| `SHIPPING` | 조회 전용 |
| `DELIVERED` | 조회 전용 |
| `CLAIM` | `클레임확인` |

## 14. 마켓수수료율 정책

마켓수수료율은 `내정보 > 마켓연동`에서 관리한다.
수수료율은 마켓 또는 연동 계정 단위로 설정할 수 있다.

마켓수수료율은 다음 계산에 사용한다.

- 정산예정금액
- 예상마진
- 실제마진
- 장부 기능

주문수집 화면에는 수수료율 상세값을 기본 컬럼으로 표시하지 않는다.
주문수집 화면에서는 운영 판단에 필요한 정산예정금액과 마진 결과값을 우선 표시한다.

## 15. 개인정보와 통관정보 정책

구매자 연락처, 수령인 연락처, 배송지 주소, 개인통관부호는 주문 처리에 필요한 정보로 관리한다.

개인통관부호는 단일 컬럼으로 표시한다.
컬럼 안에는 부호 값과 일치/불일치/확인필요 상태를 함께 표시한다.

개인정보는 주문 처리 목적 외 화면과 로그에 불필요하게 노출하지 않는다.

## 16. 실패 처리 정책

실패 사유는 정상 처리가 되지 않은 주문에만 표시한다.

| 실패 구분 | 정책 |
|---|---|
| 주문수집 실패 | 계정 단위 실패로 기록 |
| 주문확인 실패 | `NEW` 유지 |
| 소싱라이프 연동 실패 | 주문상태 유지, 소싱상태 `HOLD` |
| 결제 실패 | `PREPARING` 유지, 소싱상태 `HOLD` |
| 송장전송 실패 | `READY_TO_SHIP` 유지, 소싱상태 `HOLD` |
| 클레임 처리 실패 | `CLAIM` 유지 |

초기버전에서는 처리이력을 주문관리 화면에 제공하지 않는다.
상태 변경 로그는 내부 진단 또는 추후 확장 기능으로 분리한다.

## 17. 확장 정책

초기에는 네이버 스마트스토어와 쿠팡을 우선 구현한다.
11번가, 지마켓, 옥션은 동일한 공통 주문 모델과 내부 상태 기준을 사용해 확장한다.

새 마켓을 추가할 때도 다음 정책은 유지한다.

- 마켓별 원문 상태를 내부 상태로 변환한다.
- 주문 식별 기준에 연동 계정을 포함한다.
- 활성화된 모든 연동 계정을 수집 대상으로 한다.
- 주문확인, 소싱하기, 국내송장 자동저장, 송장전송의 기본 흐름을 유지한다.
- 마켓별 차이는 API 매핑 계층에서 처리하고 화면 정책은 공통으로 유지한다.
