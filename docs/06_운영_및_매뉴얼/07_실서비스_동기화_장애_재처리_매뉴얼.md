# 실서비스 동기화·장애·재처리 매뉴얼

## 1. 운영 원칙

- 외부 결과가 확인되지 않은 작업을 성공으로 마감하지 않는다.
- 재시도 전에 같은 작업이 이미 마켓에 반영됐는지 확인한다.
- 실패를 숨기기 위해 내부 상태만 다음 단계로 변경하지 않는다.
- 마켓과 소싱라이프 중 한쪽만 성공하면 별도 복구 작업을 유지한다.
- 비밀키·개인통관고유부호·결제정보를 티켓과 채팅에 붙여 넣지 않는다.
- 운영자 수동 보정도 원인, 근거, 작업자, 전후상태를 감사로그에 남긴다.

## 2. 일일 점검

### 업무 시작

1. 동기화센터에서 모든 활성 계정의 마지막 성공시각을 확인한다.
2. 인증 만료·권한·IP 오류 계정을 확인한다.
3. NEEDS_ATTENTION과 DEAD 작업을 확인한다.
4. 전날 야간 대사 불일치를 확인한다.
5. 오늘 출고·클레임 마감 임박 작업을 확인한다.

### 업무 중

- 주문수집 지연 10분 초과 계정
- 일괄 주문확인·발송 부분 실패
- 가격·재고 변경으로 중단된 구매
- 결제 결과 확인 중
- 송장대기 지연
- 취소와 구매·발송의 경합
- 반품·교환 처리기한 임박

### 업무 종료

1. 당일 UNKNOWN 명령을 0건으로 만든다.
2. 마켓 성공·소싱 실패 saga에 담당자와 다음 시각을 지정한다.
3. 클레임 기한 초과 위험을 인계한다.
4. 대량 수동 보정이 있었으면 원인과 재발방지를 기록한다.

## 3. 계정 장애

### 3-1. 인증 만료

증상:

- 401
- 토큰 발급 실패
- 키 만료 표시

처리:

1. 해당 계정의 새 쓰기 명령을 일시 중지한다.
2. 마지막 성공 cursor를 보존한다.
3. 키 만료일과 마켓 공지를 확인한다.
4. OWNER/ADMIN에게 재인증을 요청한다.
5. 새 키를 Secret Manager에 새 version으로 저장한다.
6. 읽기 API로 계정·판매자 식별을 검증한다.
7. 짧은 overlap 범위를 재수집한다.
8. 정상 대사 후 쓰기 명령을 재개한다.

금지:

- 기존 Secret을 로그로 출력
- 만료된 쓰기 명령을 무조건 일괄 재호출

### 3-2. 권한·IP 오류

증상:

- 403
- ESM/11번가 허용 IP 오류
- 쿠팡 연동업체 불일치

처리:

1. 자동 재시도를 중단한다.
2. 마켓연동 화면에 계정 확인 필요를 표시한다.
3. 등록 IP, 연동업체, API 그룹, 판매자 ID를 확인한다.
4. 설정 변경 후 공식 반영 대기시간을 지킨다.
5. 읽기 테스트 후 수집을 재개한다.

## 4. 주문수집 장애

### 4-1. 일부 페이지 실패

1. sync_run을 PARTIAL로 유지한다.
2. 성공 페이지와 마지막 안전 cursor를 확인한다.
3. 실패 원인이 429/5xx면 backoff 후 재개한다.
4. 같은 조회 구간을 다시 읽되 외부 ID로 중복 제거한다.
5. 생성·수정 건수와 판매자센터를 대사한다.

### 4-2. cursor 불일치

1. 계정 수집을 일시 중지한다.
2. 마지막 성공 cursor와 raw snapshot을 확인한다.
3. 안전한 과거 시점부터 overlap 재수집한다.
4. 오래된 event가 상태를 역행하지 않았는지 확인한다.
5. 야간 대사를 즉시 실행한다.

cursor를 임의의 현재시각으로 건너뛰지 않는다.

### 4-3. 수집 주문 누락

확인:

- 대상 마켓 상태가 수집 범위에 포함되는가.
- 계정·스토어가 활성인가.
- 조회 기간·페이지·클레임 별도 API가 처리됐는가.
- 외부 주문 ID가 다른 주문과 충돌했는가.
- adapter가 알 수 없는 enum을 버렸는가.

처리:

1. 단건 또는 기간 재수집.
2. raw snapshot과 normalization 오류 확인.
3. 누락 주문을 수동 생성하지 말고 adapter를 수정해 replay.
4. 같은 패턴 주문을 전체 검색.

### 4-4. 네이버 자동 예약 중단·지연

1. scheduler는 전용 `WORKER_DATABASE_URL` 역할 검증을 통과한 `scripts/worker.ts` 프로세스 안에서 inbound·outbound loop와 함께 실행되는지 확인한다.
2. 계정이 활성이고 연결 상태인지, 마지막 terminal sync 종료 후 `NAVER_ORDER_SYNC_INTERVAL_MS`가 지났는지 확인한다.
3. 같은 계정·`ORDERS` stream에 `PENDING`, `RUNNING`, `RETRY` 실행이 남아 있으면 새 실행을 수동 삽입하지 말고 기존 실행의 lease·재시도 상태를 먼저 해소한다.
4. `SYNC_RUN_SCHEDULED` SYSTEM 감사로그와 실행의 고정 `window_end`, `cursor_before`, `window_start`를 대조한다.
5. scheduler polling·batch 설정을 확인하되 cursor나 마지막 종료시각을 현재시각으로 강제 변경하지 않는다.

현재 자동 예약은 네이버에만 구현되어 있고 실제 판매자 계정 장시간 운전 UAT는 완료되지 않았다. 쿠팡·11번가·ESM 계정에는 이 절차를 적용해 자동 수집이 된다고 판단하지 않는다.

## 5. 외부 명령 장애

### 5-1. 명확한 실패

- provider 오류코드와 retryable을 확인한다.
- 잘못된 필드·상태는 사용자가 수정한 뒤 새 revision으로 실행한다.
- 인증·권한은 계정 runbook으로 이동한다.
- 영구 미지원은 MANUAL_FALLBACK으로 전환한다.

### 5-2. timeout·UNKNOWN

1. 같은 명령을 즉시 재실행하지 않는다.
2. 마켓 단건 주문·클레임 상태를 조회한다.
3. 목표 상태가 반영됐으면 SUCCEEDED로 대사한다.
4. 반영되지 않았고 재실행 가능 상태면 같은 idempotency intent로 재시도한다.
5. 상태를 판정할 수 없으면 NEEDS_ATTENTION으로 올린다.

판매자 취소 `SELLER_CANCEL`은 위 일반 재시도 절차의 예외다. 네이버 쓰기 API가 멱등키를 받지 않고 현재 구현에 명령 전 claim 인과 기준선이 없으므로, `UNKNOWN`은 항상 `NEEDS_ATTENTION`과 수동 대사로 유지하며 자동 재호출하지 않는다. 최종 상품주문 상태가 `CANCELED`일 때만 적용 완료로 판정하고, 현재·deprecated·완료 `CANCEL/ADMIN_CANCEL` 또는 `CANCEL_REJECT` 흔적은 명령과의 인과가 증명될 때까지 미적용 근거로 사용하지 않는다.

### 5-3. 부분 성공

1. 성공 item만 내부 상태를 변경한다.
2. 실패 item과 마켓 오류를 화면에 표시한다.
3. 실패 item만 새 command 대상으로 만든다.
4. batch 전체를 재호출하지 않는다.

## 6. 주문확인·발송 경합

### 취소가 주문확인보다 먼저 확정

- 주문확인을 실행하지 않는다.
- 클레임 작업함으로 이동한다.
- 자동 구매 예약을 취소한다.

### 주문확인이 먼저 확정

- 취소 API가 허용되면 클레임 흐름을 실행한다.
- 소싱 구매가 시작됐는지 확인한다.

### 취소가 발송보다 먼저 확정

- 발송 command를 취소하거나 실행 전 차단한다.

### 발송이 먼저 확정

- 취소 버튼을 그대로 재시도하지 않는다.
- 마켓 규칙에 따라 반품 또는 출고중지 흐름으로 전환한다.

모든 경우에 마켓 상태와 내부 command 시각을 감사로그로 연결한다.

## 7. 소싱 구매 장애

### 7-1. 가격·재고 변경

- 구매를 중단한다.
- 이전·현재 가격과 재고를 표시한다.
- tenant 가격 허용한도 안이어도 자동 구매 설정이 없으면 사용자 확인을 요구한다.
- SKU 품절이면 대체 SKU 또는 재매칭.

### 7-2. 결제 redirect 유실

1. paymentSessionId로 결제 상태를 조회한다.
2. PAID면 중복 결제 없이 상태를 반영한다.
3. PENDING이면 만료까지 확인한다.
4. FAILED/EXPIRED면 새 session을 만든다.

### 7-3. 일부 item 구매 실패

- purchase를 PARTIAL로 표시한다.
- 성공 item을 다시 구매하지 않는다.
- 실패 item의 가격·재고·통관정보를 수정해 재신청한다.

### 7-4. 구매와 취소 동시

- order_item과 purchase를 잠근다.
- 구매 요청 전이면 취소.
- 이미 PAID/PURCHASED면 소싱 환불 saga.
- 마켓 취소 성공만으로 소싱 환불을 완료 처리하지 않는다.

## 8. 국내송장 장애

### 8-1. 송장 미수신

- 결제·구매·배송대행지 접수·국내송장 상태를 분리해 확인한다.
- 연결 배송대행지는 접수와 동시에 송장을 발급하므로 장기 미수신을 정상 대기로 보지 않는다.
- 접수 요청 ID로 성공 여부와 응답 유실을 대사하고, 미접수면 동일 멱등키로 안전하게 재시도한다.
- 현재 정책상 발송 가능 상태로 이동하지 않는다.
- 출고기한 임박 시 운영 경고.

### 8-2. 잘못된 택배사·송장

- market invoice는 REJECTED.
- 실제 shipment 값이 잘못됐는지 마켓 코드 변환만 잘못됐는지 구분한다.
- 수정 후 새 revision으로 전송한다.

### 8-3. 이미 등록된 송장

- 같은 수취인·합배송인지 확인한다.
- 마켓 현재 발송 상태를 조회한다.
- 이미 정상 반영이면 성공으로 대사한다.
- 다른 주문의 잘못된 중복이면 운영자 확인.

### 8-4. 직접전달

- 마켓 capability와 공식 필수값을 확인한다.
- 쿠팡 DIRECT의 숫자값과 실제 국내송장을 구분한다.
- 직접전달 성공 후에도 구매·실제 국내송장 미완료면 상품준비를 유지한다.
- 추적 불가 사실을 화면에 표시한다.

## 9. 클레임 장애

### 9-1. 마켓 성공·소싱 실패

- 마켓 claim 상태를 보존한다.
- 소싱 환불 작업을 NEEDS_ATTENTION으로 유지한다.
- 예상 손실·환불 가능단계·담당자를 표시한다.

### 9-2. 마켓 실패·소싱 성공

- 소싱 중단/환불 결과를 되돌리지 않는다.
- 마켓 판매자센터 수동 복구 또는 기술지원 작업을 만든다.

### 9-3. 반품 회수 누락

- 회수방식·회수지·택배사·송장을 확인한다.
- 자동회수/Goodsflow와 판매자 직접 회수를 구분한다.
- 재요청 전 기존 회수 접수 여부를 조회한다.

### 9-4. 교환 재배송 실패

- 교환품 확보와 재배송 shipment를 보존한다.
- 마켓에 송장이 반영되지 않았으면 재배송 완료로 표시하지 않는다.
- 직접전달/일반 송장 capability를 다시 확인한다.

## 10. 대사

### 자동 대사 항목

- 주문·상품주문 존재 여부
- 주문확인 상태
- 클레임 유형·수량·상태
- 마켓 발송 상태와 송장
- 구매확정
- 소싱 application·purchase
- 실제 국내송장과 배송완료

### 차이 분류

| 분류 | 예 |
|---|---|
| AUTO_FIX | 늦게 수집된 구매확정 |
| VERIFY_THEN_FIX | timeout 송장 결과 |
| USER_ACTION | 잘못된 송장·클레임 사유 |
| MARKET_MANUAL | API 미지원 |
| ENGINEERING | schema·mapping 오류 |

대사 수정도 raw 근거와 감사로그를 남긴다.

## 11. 장애 등급

| 등급 | 조건 | 초기 대응 |
|---|---|---|
| SEV-1 | 다수 계정 중복 구매·잘못된 취소·개인정보 유출 | 자동화 중지, 보안/운영 즉시 소집 |
| SEV-2 | 한 마켓 전체 수집·쓰기 중단, 광범위 누락 | 해당 adapter 중지, 대사·공지 |
| SEV-3 | 일부 계정·작업 실패, 수동 대체 가능 | 실패 작업함과 담당자 |
| SEV-4 | 표시·리포트 오류, 업무 영향 낮음 | 일반 결함 |

SEV-1·2는 원인과 복구 후 재발방지 문서를 작성한다.

## 12. 개인정보 사고

1. 노출 경로와 범위를 즉시 차단한다.
2. 관련 token·secret을 회전한다.
3. 로그·snapshot·export 접근 이력을 보존한다.
4. 영향 tenant·필드·기간을 확인한다.
5. 법무·개인정보 담당 절차에 따라 신고·통지를 판단한다.
6. 임의로 증거 로그를 삭제하지 않는다.
7. 운영 복구 후 마스킹·권한·보존정책 회귀 테스트를 실행한다.

## 13. 백업·복구

- PostgreSQL 시점복구를 사용한다.
- Secret은 별도 비밀 저장소 정책으로 백업한다.
- raw snapshot과 감사로그의 복구 가능성을 확인한다.
- 최소 분기 1회 복구 훈련을 한다.
- 복구 후 마켓 cursor를 현재로 점프하지 않고 overlap 대사를 수행한다.

목표:

- RPO 15분
- 핵심 주문조회 RTO 4시간

실제 목표 달성은 복구훈련 결과로만 판정한다.

## 14. 운영 인계 필수정보

- 영향 tenant·마켓·계정
- sync_run 또는 command ID
- 외부 주문·상품주문·claim ID
- 발생·감지·마지막 성공시각
- raw snapshot ID
- 이미 실행된 외부 효과
- 재시도 가능 여부
- 개인정보 포함 여부
- 담당자와 다음 점검시각

비밀키와 개인정보 원문은 인계문에 넣지 않는다.
