# 기획문서 작성 스킬

## 적용 범위

- 이 스킬은 소싱라이프 내부 주문관리 기획문서를 작성하거나 수정할 때 적용한다.
- `00_문서맵`부터 `09_와이어프레임`까지가 현재 활성 문서 체계다.
- 현재 MVP 문서는 프론트 구현, mock data, localStorage 동작을 최신 기준으로 본다.
- 사용자의 기능 추가, 제외, 용어 변경, 상태 변경 요청에 따라 영향을 받는 현재 기준 문서를 함께 수정한다.
- `_legacy` 폴더는 과거 보관용 문서이며 현재 기준 문서로 보지 않는다.

## 작업 전 확인

- 수정 전 관련 문서에서 같은 개념이 이미 작성되어 있는지 먼저 확인한다.
- 이미 작성되어 있으면 사용자에게 어디에 있는지 알려주고 중복 작성하지 않는다.
- 일부만 작성되어 있으면 누락된 부분만 보강한다.
- 새 기능이면 영향을 받는 문서 전체에 반영한다.
- 사용자가 "추가"라고 말해도 기존 문서에 같은 기능이 있으면 새 항목을 중복 생성하지 않는다.

## 문서별 역할

- `01_서비스기획`: 서비스 목적, 범위, 정책, 운영 원칙, 비즈니스 규칙을 작성한다.
- `02_UI_UX_명세서`: 화면, 메뉴, 탭, 필터, 컬럼, 라벨, 버튼, 모달, 사용자 흐름을 작성한다.
- `03_기능명세서`: 기능 동작, 조건, 상태 변경, 성공 처리, 실패 처리, 예외 처리를 작성한다.
- `04_시스템_아키텍처_및_API`: 공통 데이터 모델, 상태 모델, API 처리 기준, 마켓 API 매핑, 소싱라이프 연동 기준, 공식 API 링크 인덱스와 구현용 API 연동 기준을 작성한다.
- `05_프론트엔드_개발가이드`: 프론트엔드 구현 기준, 화면 구성, 컴포넌트 동작, 상태별 UI 표시 기준을 작성한다.
- `06_운영_및_매뉴얼`: 운영자가 실제 업무에서 따라야 하는 처리 절차와 주의사항을 작성한다.
- `07_주문팡팡개별`: 소싱라이프 주문관리 내부 정책, 유지해야 할 판단 기준, 확장 원칙을 작성한다.
- `08_유저플로우`: 현재 구현 기준의 사용자 흐름과 보조 흐름을 작성한다.
- `09_와이어프레임`: 현재 프로토타입 화면을 페이지별, 모달별로 확인할 수 있는 문서와 HTML 기준을 작성한다.

## 동시 반영 기준

- 기능을 추가하거나 변경할 때는 영향을 받는 문서를 같은 작업 안에서 함께 수정한다.
- 정책, 화면, 동작이 모두 바뀌면 `01`, `02`, `03`을 함께 수정한다.
- 용어만 바뀌어도 해당 용어가 등장하는 모든 현재 기준 문서를 수정한다.
- 기능을 제외하거나 삭제할 때도 관련 문서 전체에서 같은 기준으로 제거하거나 제외 기준을 명시한다.
- 한 문서에는 있고 다른 문서에는 없는 상태, 버튼, 컬럼, 정책이 생기지 않도록 확인한다.

## 용어 규칙

- 사용자 화면 액션명은 `주문확인`을 사용하고 `발주확인`은 사용하지 않는다.
- 마켓명은 `스마트스토어`, `쿠팡`, `11번가`, `G마켓`, `옥션`을 기준으로 작성한다.
- 판매처 또는 스토어 연결 단위는 사용자 화면에서 `스토어명`으로 작성한다.
- `마켓`과 `스토어명`은 서로 다른 정보로 분리한다.
- `주문확인` 이후 단계는 `상품준비`로 작성한다.
- 소싱라이프 결제 완료 후 배송중 처리 전 단계는 `발송대기`로 작성한다.
- 신규주문에서 소싱 후보/옵션을 저장하고 주문확인까지 처리하는 액션명은 `매칭하기`로 작성한다.
- 상품준비에서 구매대행 신청/결제까지 진행하는 액션명은 `소싱하기`로 작성한다.
- 상품준비 단계에서 소싱라이프 결제 화면으로 이동하는 동작은 `소싱하기` 흐름 안에 포함한다.
- 별도 사용자-facing 액션으로 `결제하기`를 만들지 않는다.
- 배송정보 수정 버튼명은 목록에서는 `수정`으로 작성한다.
- 날짜 빠른 필터는 `오늘`, `3일`, `7일`, `30일`, `직접 입력` 기준으로 작성한다.
- 버튼은 메인 화면에서 아이콘 버튼이면 아이콘만, 텍스트 버튼이면 텍스트만 사용한다.

## 주문수집 범위와 필터

- 주문수집 대상은 활성화된 모든 마켓 계정과 스토어다.
- 마켓/스토어 필터는 주문 목록 조회용 필터다.
- 마켓/스토어 필터를 주문수집 실행 범위 제어 기능으로 작성하지 않는다.
- 아무것도 선택하지 않으면 전체 주문을 표시한다.
- 마켓만 선택하면 선택한 마켓의 전체 스토어 주문을 표시한다.
- 스토어만 선택하면 해당 스토어 주문을 표시한다.
- 마켓과 스토어를 함께 선택하면 선택한 마켓 안에서 선택한 스토어 주문만 표시한다.
- 선택한 마켓과 관계없는 스토어는 숨기지 않고 비활성화한다.
- 특정 판매처만 주문수집하는 기능과 특정 스토어만 주문수집하는 기능은 초기 범위에서 제외한다.
- 동일 마켓 안에서도 여러 스토어 또는 판매자 계정을 개수 제한 없이 등록할 수 있다는 기준을 유지한다.
- 체크박스 선택 상태와 행 자세히보기 상태는 주문수집 탭, 검색어, 필터, 데이터 초기화가 바뀌면 초기화하는 기준으로 작성한다.

## 테이블 컬럼 규칙

- 하나의 컬럼은 하나의 업무 목적 또는 하나의 기능 단위를 담당한다.
- 같은 업무 목적의 값과 상태 표시는 한 컬럼에 함께 표시할 수 있다.
- 서로 다른 업무 목적의 정보를 한 컬럼에 섞지 않는다.
- 상품명, 옵션명, 수량, 마켓 주문번호는 `상품정보` 컬럼에 함께 표시할 수 있다.
- 수령인명, 수령인 연락처, 배송지 주소, 개인통관부호는 `배송정보` 컬럼에 함께 표시할 수 있다.
- `택배정보` 컬럼에는 국내 택배사와 국내 송장번호를 함께 표시한다.
- 개인통관부호는 `통관부호 일치` 또는 `통관부호 불일치`로 표시한다.
- 송장 입력 경로, 처리 결과, 처리이력은 초기 주문 테이블의 별도 컬럼으로 두지 않는다.
- 주문 목록 기본 컬럼은 `선택`, `처리하기`, `주문일시`, `상품정보`, `택배정보`, `배송정보`, `판매처`, `소싱` 순서를 기준으로 작성한다.
- `소싱` 컬럼은 처리 버튼을 넣지 않고 현재 상태 또는 결과만 표시한다.
- 소싱 전은 `-`, 매칭 후 결제 전은 `매칭완료`, 결제 후 주문서가 있으면 주문내역 아이콘 링크를 표시한다.
- 컬럼을 추가, 삭제, 이름 변경할 때는 전체 컬럼 리스트를 다시 작성하고 번호를 재정렬한다.

## 상태와 액션 규칙

- `NEW`는 마켓 결제완료 주문이 수집되었고 주문확인 전인 상태다.
- `PREPARING`은 주문확인 완료 후 소싱라이프 결제 완료 전 상태다.
- `READY_TO_SHIP`은 소싱라이프 결제 완료 후 국내송장 입력, 확인, 배송중 처리 전 상태다.
- `SHIPPING`은 배송중 처리 완료 후 상태다.
- `DELIVERED`는 마켓 배송완료 또는 구매확정 상태다.
- `CLAIM`은 취소, 반품, 교환 처리 대상 상태다.
- `CANCELED`는 판매자가 직접 주문취소 처리한 종료 상태다.
- 판매자 직접 주문취소는 구매자 요청 클레임인 `CLAIM` 목록과 분리한다.
- 새 버튼을 추가할 때는 표시 위치, 활성 조건, 성공 결과, 실패 결과를 함께 정의한다.
- 자동화 기능을 추가할 때는 ON/OFF 동작, 대상 주문, 성공 결과, 실패 결과를 함께 정의한다.
- 주문 행 클릭 시 자세히 보기 영역을 펼치는 구조를 기본으로 작성한다.
- 마켓 주문번호 클릭으로 주문상세 모달을 여는 구조는 현재 기준으로 작성하지 않는다.
- 신규주문의 주문취소는 개별 처리와 다수건 일괄 처리 모두 확인 모달을 거친다.
- 상품준비의 `직접 구매 처리` 흐름은 `발송대기 처리`와 `배송중 처리` 두 액션 기준으로 작성한다.
- 발송대기 필터는 `전체`, `송장 있음`, `송장 없음` 드롭다운 기준으로 작성한다.

## 주문 자세히보기 규칙

- 주문 행 자세히보기는 목록 컬럼에 없는 주문 관련 정보를 확인하는 보조 영역이다.
- 자세히보기 섹션 순서는 `주문상품`, `구매자`, `배송정보`, `택배정보`, `소싱상품` 기준으로 작성한다.
- 구매자는 이름과 연락처만 표시한다.
- 배송정보는 수취인 이름, 연락처, 주소, 개인통관부호, 통관부호 확인 상태를 표시하고 자세히보기 안에서도 수정할 수 있게 작성한다.
- 택배정보는 제목 없이 `택배사 송장번호` 한 줄 표시를 기준으로 작성한다.
- 소싱상품은 썸네일, 상품명, 옵션명, 수량, 소싱금액, 소싱라이프 주문번호만 표시한다.
- 소싱상품의 옵션명과 수량은 같은 줄에 붙여 표시한다.
- 주문일시와 마켓/스토어명은 보조 정보로 표시하고 상품주문번호는 자세히보기에서 표시하지 않는다.

## 국내송장 규칙

- 국내송장은 `READY_TO_SHIP` 상태에서 운영자가 직접 입력할 수 있다.
- 국내송장은 운영자 수동 입력 시 즉시 자동저장한다.
- 별도의 국내송장 저장 버튼이나 중간 저장 단계를 만들지 않는다.
- 별도 `소싱라이프 송장 수집` 버튼은 제공하지 않는다.
- `자동 배송중 처리`는 국내송장이 입력된 뒤 배송중 처리를 자동 실행하는 기능이다.
- 자동 배송중 처리는 국내송장이 입력된 경로와 관계없이 동작한다.
- 배송중 처리 성공 시 주문상태는 `SHIPPING`으로 변경한다.
- 배송중 처리 실패 시 주문상태는 `READY_TO_SHIP`으로 유지하고 실패 사유를 표시한다.
- 배송중 상태에서는 송장 변경을 마켓에 전송하는 버튼을 제공하지 않는다.
- 변경된 송장번호 항목은 표시하지 않는다.

## 소싱라이프 규칙

- 주문관리는 소싱라이프 내부 기능이다.
- 주문관리는 마켓에서 수집된 주문을 기준으로 소싱라이프 주문번호, 결제 완료 여부, 실제결제금액, 국내송장 확보 여부를 주문 단위로 관리한다.
- 소싱라이프에서 직접 생성하거나 주문한 내역은 주문관리의 주문수집 목록에 포함하지 않는다.
- 소싱라이프의 구매, 검수, 입고, 물류 상세 처리는 소싱라이프 기존 기능에서 진행한다.
- `NEW` 상태의 `매칭하기`는 매칭 저장과 주문확인을 함께 처리한다.
- `PREPARING` 상태의 `소싱하기`는 후보 확인, 옵션 선택, 매칭 저장, 소싱라이프 결제 화면 이동을 포함한다.
- 추천 소싱 상품 영역에는 `키워드 또는 타오바오/소싱라이프 상품 URL 입력` 필드와 `찾기` 버튼을 배치한다.
- 기본 이미지 매칭 후보 20개를 먼저 표시하고, 키워드 찾기는 20개 후보를 상단에 추가하며, URL 찾기는 해당 상품 1개를 상단에 추가한다.
- 후보 목록 카드에는 한국어 상품명, 중국어 상품명, 판매처, 원화/위안 상품원가를 표시한다.
- 구매 1회, AI 매칭률, 별점, 배송일수, 배송비, 예상마진은 표시하지 않는다.
- 옵션 드롭다운은 한국어 옵션명 아래 중국어 옵션명을 표시한다.
- 옵션 드롭다운은 항상 아래로 열린다.
- 품절 옵션은 선택 상태로 보여줄 수 있으나 소싱라이프 결제 진행 버튼은 비활성화한다.
- 주문내역 아이콘 링크는 새 탭으로 소싱라이프 주문상세내역 임시 페이지를 연다.

## 마켓연동 규칙

- 마켓연동 화면의 마켓 추가 버튼은 우측 상단에 배치한다.
- 마켓 추가와 관리는 같은 구조의 추가/수정 모달을 사용한다.
- 삭제는 삭제 확인 모달을 거친 뒤 처리한다.
- 마켓 선택은 드롭다운으로 작성하고 선택지는 `스마트스토어`, `쿠팡`, `11번가`, `G마켓`, `옥션`이다.
- 목록 컬럼은 `마켓`, `스토어명`, `연동상태`, `활성`, `관리` 기준으로 작성한다.
- 별도 `계정설정` 페이지, 플랫폼 수수료율, 마지막 수집, 결과 컬럼은 현재 MVP 기준으로 작성하지 않는다.
- 스토어명은 사용자가 구분하기 위한 값이며 필수 식별자는 마켓별 인증정보에 둔다.
- 스마트스토어 인증정보는 `연동용 판매자ID`, `클라이언트 아이디`, `클라이언트 시크릿` 기준으로 작성한다.
- 쿠팡은 `쿠팡윙 ID`를 표기할 수 있고, 11번가는 별도 ID 표시를 하지 않는다.

## 공식 API 문서 작성 규칙

- 공식 API 문서는 원문 전체 복사본으로 작성하지 않는다.
- 공식 URL, 확인일, 공식 문서 버전, 기능별 확인 위치, 내부 매핑 기준을 기록한 개발 참조 문서로 작성한다.
- 공식 API 링크 인덱스는 `04_시스템_아키텍처_및_API/{마켓명}API_공식링크/` 하위에 작성한다.
- 네이버 커머스API 공식 링크 인덱스는 `네이버커머스API_공식링크/00_공식문서_전체링크_인덱스.md`를 기준으로 관리한다.
- 네이버 커머스API 구현 기준은 `04_네이버커머스API_연동기준.md`에 작성한다.
- API 구현 기준 문서에는 기능별로 어떤 공식 문서를 확인해야 하는지 먼저 적는다.
- API 구현 기준 문서에는 인증, 주문수집, 주문확인, 배송중 처리, 취소/반품/교환, 계정/채널 검증, 오류/재시도 기준을 분리해서 작성한다.
- 주문관리 내부 버튼명은 사용자 화면 기준인 `주문확인`, `배송중 처리`, `주문취소`를 사용하고, 공식 API 용어인 발주확인/발송처리는 API 설명 또는 매핑표에서만 사용한다.
- 공식 API 상태값은 내부 `OrderStatus`와 직접 동일하게 쓰지 않고 별도 매핑표로 작성한다.
- 공식 API 문서를 추가하거나 이름을 바꾸면 `00_문서맵/00_문서맵_주문팡팡_소싱라이프.md`와 `00_문서맵/99_변경이력.md`를 함께 수정한다.

## 와이어프레임 작성 규칙

- 와이어프레임 HTML은 과거 정적 목업이 아니라 현재 프로토타입을 페이지별, 모달별로 확인하는 파일로 작성한다.
- HTML 파일명은 실제 확인 화면명과 일치해야 한다.
- 독립 페이지가 있는 화면은 페이지 HTML로, 모달/팝오버는 별도 단독 HTML로 작성한다.
- 문서 인덱스에는 MD 문서와 HTML 확인 파일을 구분해서 작성한다.

## 작성 톤

- 개발자에게 전달할 실제 기획문서처럼 작성한다.
- 문서에는 대화 히스토리, 수정 요청 히스토리, 작업 경위를 작성하지 않는다.
- `사용자가 요청했다`, `이번에 수정`, `현재 논의 중` 같은 표현을 쓰지 않는다.
- 구현 과정에 대한 해설이나 작업자 메모를 기획문서 본문에 쓰지 않는다.
- 기존 내용과 충돌되는 내용은 뒤에 덧붙이지 말고 기존 문장을 교체한다.
- 문장은 간결하고 판단 기준이 분명한 제품 기획 문체로 작성한다.

## 검증 규칙

- 수정 후 현재 기준 문서 전체에서 충돌 표현이 남아있는지 검색한다.
- 기본 충돌 검색어는 `송장전송`, `송장수정`, `선택 주문확인`, `선택 배송중`, `마켓수수료`, `계정설정`, `주문상세 모달`, `배송대행`, `배대지`, `타오월드`, `네이버 스마트스토어`, `최종기획`, `최종 기획`이다.
- `발주확인`, `발송처리`는 공식 API 문서 또는 API 매핑표 안에서는 허용하고, 사용자 화면 문구로 쓰였는지만 확인한다.
- 상태 코드, 버튼명, 컬럼명, 모달 버튼이 문서 간 서로 충돌하지 않는지 확인한다.
- `주문확인`, `매칭하기`, `소싱하기`, `국내송장 자동저장`, `배송중 처리`, `자동 배송중 처리`, `활성화된 모든 연동 계정` 기준이 필요한 문서에 반영되어 있는지 확인한다.
- 문서가 UTF-8 기준으로 정상 읽히는지 확인한다.

## 완료 보고

- 수정이 끝나면 실제로 수정한 문서만 보고한다.
- 요청 내용이 이미 문서에 있으면 수정하지 않고 어느 문서에 있는지 알려준다.
- 검증한 항목이 있으면 충돌 표현 검색 결과와 주요 정합성 확인 내용을 함께 요약한다.
