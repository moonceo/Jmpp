# [기획] 주문수집 + 소싱라이프 연동 최종 모델 서비스 기획서

본 문서는 주문수집 프로그램(주문팡팡)의 **최종 모델** 기준 서비스 정의 문서이다.
MVP 범위 문서가 아니며, 기능은 단계적으로 추가하되 모든 문서는 본 최종 모델을 기준으로 작성·갱신한다.

## 1. 서비스 정의

### 1.1 서비스 목적
- 여러 판매처(오픈마켓)의 주문을 **한 화면에서 통합 조회·처리**한다. (플레이오토형 통합 주문관리 모델)
- 주문 처리 과정에서 **소싱라이프**를 통해 상품 구매(소싱)와 국내송장 확보를 연결한다.
- 마켓 주문 수집 → 발주확인 → 소싱라이프 결제/주문 → 국내송장 수집 → 마켓 송장전송 → 배송 추적까지 전체 주문 생애주기를 관리한다.

### 1.2 소싱라이프와의 관계 (핵심 원칙)
- 소싱라이프는 주문수집 프로그램의 **내부 기능이 아니라, 주문 처리 중 연결되는 외부/별도 서비스**다.
- 주문수집 프로그램이 관리하는 것은 소싱라이프 자체가 아니라 **소싱라이프 연동 상태**다.
  - 소싱 주문 생성 여부, 소싱 결제 여부, 국내송장 발급 여부를 주문 단위로 추적한다.
- 소싱라이프 연동의 목적은 두 가지로 한정한다.
  1. 주문 상품의 구매/소싱 처리
  2. 국내송장(국내 택배 송장번호) 확보
- 국내송장이 없으면 마켓 송장전송을 할 수 없다. 이것이 소싱라이프 연동이 주문 흐름의 필수 경유지가 되는 이유다.

### 1.3 사용자 정의
| 사용자 | 설명 | 주요 행동 |
|---|---|---|
| 셀러(운영자) | 오픈마켓에서 해외소싱 상품을 판매하는 판매자 | 주문 확인, 발주확인, 소싱 결제, 송장전송, 클레임 대응 |
| 마스터 계정 | 셀러 계정의 소유자 | 마켓 연동 설정, 플랜/결제 관리 |
| 서브 계정(확장) | 주문 처리 전담 직원 | 주문 처리 메뉴 한정 접근 |

## 2. 연동 마켓 범위와 우선순위

| 우선순위 | 마켓 | API | 비고 |
|---|---|---|---|
| 1 | 네이버 스마트스토어 | 커머스API (OAuth 2.0) | 1차 연동 |
| 2 | 쿠팡 | Open API (HMAC 서명) | 1차 연동 |
| 3 | 11번가 | 오픈API | 2차 확장 |
| 4 | 지마켓/옥션 | ESM PLUS API | 2차 확장 |

확장 원칙:
- 모든 마켓 주문은 **공통 주문 모델**로 정규화한 뒤 처리한다.
- 마켓별 API 차이는 **마켓 어댑터** 계층에서 흡수한다. (상세: `04_시스템_아키텍처_및_API/공통_주문모델_및_마켓어댑터.md`)
- 신규 마켓 추가 시 공통 모델·내부 상태는 변경하지 않고, 어댑터와 상태 매핑표만 추가한다.

## 3. 전체 주문 흐름 (최종 모델)

```text
[마켓]            [주문수집 프로그램]                  [소싱라이프(외부)]
결제완료 주문  →  ① 주문수집 (신규주문)
              →  ② 발주확인 (마켓 API 호출)
              →  ③ 상품준비
                    - 소싱 상품 매칭/검토         →  소싱 주문 생성
                    - 소싱라이프 결제             →  결제/구매 진행
                    - 국내송장 대기               ←  국내송장 발급
              →  ④ 발송대기 (국내송장 확보, 마켓 송장전송 대기)
              →  ⑤ 마켓 송장전송 (마켓 API 호출)
송장 등록됨   ←
              →  ⑥ 배송중 (송장전송 성공 시 자동 전환)
              →  ⑦ 배송완료
```

상태 전환의 기준 (요약 — 상세 정의는 `07_주문팡팡개별/02_주문팡팡_내부주문상태_정의.md`):
- 마켓 주문 상태와 내부 주문 상태는 **분리**한다. 내부 상태가 화면·메뉴·처리 기준의 단일 기준(Single Source of Truth)이다.
- 마켓별 API 상태는 내부 상태로 **매핑**한다. 매핑표는 마켓별로 문서화한다.
- 송장전송 성공 후에만 내부 상태가 `배송중`으로 변경된다. 전송 실패 시 `송장전송 실패` 상태로 남아 재시도 대상이 된다.

## 4. 메뉴 구조 (최종 모델 IA)

| Level 1 | Level 2 | 역할 | URL |
|---|---|---|---|
| 대시보드 | - | 처리 필요 주문 요약, 마켓별 수집 현황 | `/` |
| 주문관리 | 전체 | 모든 마켓·모든 상태 통합 조회 | `/orders` |
| | 신규주문 | 수집된 결제완료 주문 확인, 발주확인 처리 | `/orders/new` |
| | 상품준비 | 소싱 매칭, 마진 검토, 소싱라이프 결제, 국내송장 대기 | `/orders/preparing` |
| | 발송대기 | 국내송장 확보 후 마켓 송장전송 대기/실패 관리 | `/orders/waiting` |
| | 배송중 | 마켓 송장 등록 완료 주문의 배송 추적 | `/orders/shipping` |
| | 배송완료 | 배송 완료·구매확정 주문 | `/orders/delivered` |
| | 취소/반품/교환 | 클레임 주문 통합 관리 | `/orders/claims` |
| 문의관리 | - | 마켓 문의 수집/답변 (확장) | `/inquiries` |
| 내정보 | 마켓 연동 | 마켓별 API 인증 정보 등록/상태 확인 | `/me/markets` |
| | 프로필/설정/플랜/장부 | 계정·결제·정산 부가 기능 | `/me/*` |

기존 IA(`기획_IA_메뉴구조도.md`)와의 차이:
- **상품준비**, **배송완료** 메뉴가 추가된다. 소싱라이프 결제와 국내송장 확보가 명시적인 작업 단계이기 때문이다.
- 클레임 주문은 진행 단계 메뉴와 별도로 항상 `취소/반품/교환`에서 조회 가능해야 한다.

## 5. 기능 범위 정의

### 5.1 주문수집 프로그램이 관리하는 것
1. 마켓 주문 수집 (자동 주기 수집 + 수동 수집)
2. 내부 주문 상태 관리 (공통 상태 체계)
3. 발주확인 (마켓 API 호출)
4. 소싱라이프 연동 상태 관리 (소싱 주문/결제/국내송장 추적)
5. 국내송장 처리 (수집/수동입력/검증)
6. 마켓 송장 업로드 (송장전송, 실패 재시도)
7. 클레임(취소/반품/교환) 수집 및 처리
8. 주문 이력(히스토리) 기록

### 5.2 주문수집 프로그램이 관리하지 않는 것
- 소싱라이프 내부의 구매 대행 프로세스 자체 (소싱라이프 서비스 영역)
- 배대지(배송대행지) 내부 운영 (입고 검수 등)
- 마켓 상품 등록/관리 (주문관리 범위 외)
