# 공통 주문 모델 및 마켓 어댑터 설계 기준

## 1. 문서 목적

여러 마켓(네이버, 쿠팡, 11번가, 지마켓, 옥션)의 주문을 하나의 화면에서 처리하기 위한 **공통 주문 모델**과 **마켓 어댑터** 구조, 그리고 마켓별 API 상태 → 내부 상태 매핑 기준을 정의한다.

- 내부 상태의 원본 정의: `../07_주문팡팡개별/02_주문팡팡_내부주문상태_정의.md`
- 1차 수집 필수 필드: `../07_주문팡팡개별/01_주문팡팡_주문1차수집_필수컬럼.md`
- 마켓별 API 기준 문서: `./외부_마켓_API/naver-commerce-api.md`, `./외부_마켓_API/coupang-open-api.md`

## 2. 아키텍처 개요

```text
[네이버 어댑터]  [쿠팡 어댑터]  [11번가 어댑터(확장)]  [ESM 어댑터(확장)]
       │              │                │                    │
       └──────────────┴───── 정규화 ───┴────────────────────┘
                              │
                      [공통 주문 모델]
                              │
        ┌─────────────────────┼──────────────────────┐
   [내부 상태 엔진]      [주문관리 화면]        [소싱라이프 연동]
   (매핑/전환 규칙)      (메뉴/필터/액션)       (소싱 주문/결제/국내송장)
```

원칙:
- 화면과 비즈니스 로직은 **공통 주문 모델과 내부 상태만** 바라본다. 마켓별 분기는 어댑터 내부에만 존재한다.
- 신규 마켓 추가 시 작업 범위는 (1) 어댑터 구현 (2) 상태 매핑표 작성 (3) 인증 설정 화면 추가, 세 가지로 한정된다. 공통 모델·내부 상태·화면은 변경하지 않는다.

## 3. 공통 주문 모델

주문은 **주문(Order)** 과 **주문상품(OrderItem, 라인)** 2계층으로 관리한다. 상태·소싱·송장은 주문상품 단위다.

### 3.1 Order (주문 헤더)

| 필드 | 타입 | 필수 | 설명 |
|---|---|---|---|
| `orderId` | string | ✔ | 내부 주문 식별값 |
| `marketCode` | enum | ✔ | `NAVER` / `COUPANG` / `ST11` / `GMARKET` / `AUCTION` |
| `sellerAccountId` | string | ✔ | 셀러 계정(연동 채널) 식별값 |
| `marketOrderNo` | string | ✔ | 마켓 주문번호 |
| `storeName` | string | ✔ | 스토어명 (연동 설정 기반) |
| `orderedAt` | datetime | ✔ | 주문 접수 일시 |
| `buyerName` / `buyerPhone` | string | ✔ | 구매자 정보 |
| `receiverName` / `receiverPhone` | string | ✔ | 수령인 정보 |
| `zipCode` / `address1` / `address2` | string | ✔ | 수령지 주소 |
| `pccc` | string | - | 개인통관고유부호 (해외직구 주문 필수, 미수집 시 별도 수집 플로우) |
| `deliveryMemo` | string | - | 배송 요청사항 |
| `currency` | string | ✔ | 통화 (기본 KRW) |
| `totalPaymentAmount` | number | ✔ | 주문 총 결제금액 |
| `collectedAt` / `updatedAt` | datetime | ✔ | 수집/갱신 시각 |
| `rawPayload` | json | ✔ | 마켓 응답 원문 (원문 보관 정책) |

### 3.2 OrderItem (주문상품 라인)

| 필드 | 타입 | 필수 | 설명 |
|---|---|---|---|
| `orderItemId` | string | ✔ | 내부 주문상품 식별값 |
| `marketOrderItemNo` | string | ✔ | 마켓 주문상품(라인) 식별값. 네이버 `productOrderId`, 쿠팡 `orderItems` 라인 기준 |
| `productId` / `productName` / `optionName` | string | ✔ | 상품 식별값/상품명/옵션명 |
| `quantity` | number | ✔ | 수량 |
| `unitPrice` | number | ✔ | 단가 |
| `itemPaymentAmount` | number | ✔ | 라인 결제금액 |
| `thumbnailUrl` / `productUrl` | string | - | 썸네일/원문 링크 |
| `marketStatus` | string | ✔ | 마켓 원본 상태 (원문 그대로) |
| `internalStatus` | enum | ✔ | 내부 상태 코드 (07 문서 정의) |
| `previousStatus` | enum | - | 클레임 인입 직전 정상 상태 |
| `marketFee` | number | - | 플랫폼 수수료 (미제공 시 0) |
| `expectedSettlement` | number | - | 예상 정산금액 (미제공 시 내부 계산) |

### 3.3 SourcingLink (소싱라이프 연동 상태)

소싱라이프는 외부 서비스이므로 주문수집 프로그램은 **연동 상태만** 보관한다.

| 필드 | 타입 | 설명 |
|---|---|---|
| `orderItemId` | string | 대상 주문상품 |
| `sourcingOrderId` | string | 소싱라이프 측 주문 식별값 |
| `sourcingStatus` | enum | `NONE` / `MATCHED`(매칭완료) / `ORDERED`(소싱주문 생성) / `PAID`(결제완료) / `ARRIVED`(배대지 입고) / `FAILED` |
| `sourcingCost` | number | 소싱 원가 (외화) |
| `sourcingCurrency` | string | 소싱 통화 (CNY 등) |
| `exchangeRate` | number | 적용 환율 |
| `forwarderType` | enum | `INSTANT`(즉시송장형) / `AFTER_ARRIVAL`(입고후송장형) |
| `linkedAt` / `paidAt` | datetime | 연동/결제 시각 |

### 3.4 DomesticInvoice (국내송장)

| 필드 | 타입 | 설명 |
|---|---|---|
| `orderItemId` | string | 대상 주문상품 |
| `courierCode` / `courierName` | string | 택배사 코드/명칭 (마켓 전송 시 마켓별 택배사 코드로 변환) |
| `trackingNo` | string | 국내송장번호 |
| `source` | enum | `SOURCING_SYNC`(소싱라이프 연동 수집) / `MANUAL`(운영자 수동입력) |
| `collectedAt` | datetime | 확보 시각 |

### 3.5 InvoiceUploadLog (마켓 송장전송 이력)

| 필드 | 타입 | 설명 |
|---|---|---|
| `orderItemId` | string | 대상 주문상품 |
| `attemptNo` | number | 시도 회차 |
| `result` | enum | `SUCCESS` / `FAILED` |
| `errorCode` / `errorMessage` | string | 마켓 응답 오류 (실패 시) |
| `requestPayload` / `responsePayload` | json | 요청/응답 원문 |
| `attemptedAt` | datetime | 시도 시각 |

## 4. 마켓 어댑터 인터페이스

모든 마켓 어댑터는 다음 5개 오퍼레이션을 구현한다. 마켓이 미지원하는 오퍼레이션은 `UNSUPPORTED`를 명시적으로 반환한다.

| 오퍼레이션 | 입력 | 출력 | 설명 |
|---|---|---|---|
| `fetchOrders` | 수집 기간, 페이징 커서 | 공통 주문 모델 목록 + 원문 | 주문 목록/상세 수집 및 정규화 |
| `confirmOrder` (발주확인) | `marketOrderItemNo` 목록 | 성공/실패 (라인 단위 부분 실패 포함) | 네이버 발주확인 / 쿠팡 상품준비중 처리 |
| `uploadInvoice` (송장전송) | `marketOrderItemNo`, 택배사 코드, 송장번호 | 성공/실패 + 오류 코드 | 마켓 송장 등록 |
| `fetchClaims` | 수집 기간 | 클레임 목록 (취소/반품/교환) | 클레임 수집 |
| `syncStatus` | `marketOrderItemNo` 목록 | 마켓 원본 상태 | 배송중 이후 상태 추적용 |

공통 요구사항:
- **멱등성**: 같은 라인에 발주확인/송장전송을 중복 호출해도 내부 데이터가 중복 생성되지 않아야 한다. 마켓이 "이미 처리됨" 오류를 반환하면 성공으로 간주한다.
- **부분 실패**: 일괄 처리 시 라인 단위로 성공/실패를 분리 기록한다.
- **레이트리밋**: 마켓별 호출 제한을 어댑터 내부에서 준수한다(대기/분할).
- **원문 보관**: 모든 요청/응답 원문을 로그로 남긴다.

## 5. 중복 수집 방지 기준

- 주문 단위 유니크 키: `marketCode + sellerAccountId + marketOrderNo`
- 주문상품 단위 유니크 키: `marketCode + sellerAccountId + marketOrderItemNo`
- 같은 기간을 여러 번 수집해도 주문이 중복 생성되지 않아야 하며, 기존 주문은 **갱신**(마켓 상태, 주소 변경 반영)으로 처리한다.
- 갱신 시 내부 상태 후퇴 금지 규칙(07 문서 5장)을 따른다.

## 6. 네이버 스마트스토어 매핑 (1순위)

기준: 커머스API (`./외부_마켓_API/naver-commerce-api.md`, 확인일 2026-06-10)

### 6.1 오퍼레이션 매핑

| 어댑터 오퍼레이션 | 네이버 API |
|---|---|
| `fetchOrders` | 변경 상품 주문 내역 조회(변경분) + 상품 주문 상세 내역 조회(배치) |
| `confirmOrder` | 발주 확인 처리 (`placeOrder`) |
| `uploadInvoice` | 발송 처리 (`dispatch`) — 택배사 코드 + 송장번호 필수 |
| `fetchClaims` | 취소/반품/교환 조회 API |
| `syncStatus` | 상품 주문 상세 내역 조회 |

### 6.2 상태 매핑표 (네이버 → 내부 상태)

| 네이버 상태 | 내부 상태 | 조건 |
|---|---|---|
| `PAYMENT_WAITING` | 수집 제외 | 결제완료 전 주문은 수집하지 않는다 |
| `PAYED` + 발주확인 전 | `NEW` | 최초 수집 |
| `PAYED` + 내부 처리 진행 중 | 내부 진행 상태 유지 | **네이버는 발주확인 후에도 `PAYED`가 유지될 수 있으므로 마켓 상태로 내부 상태를 되돌리지 않는다** |
| `DELIVERING` | `SHIPPING` | 진행 방향 갱신만 허용 |
| `DELIVERED` | `DELIVERED` | |
| `PURCHASE_DECIDED` | `PURCHASE_CONFIRMED` | |
| `CANCELED` / `CANCELED_BY_NOPAYMENT` | `CANCELED` | |
| claimType=`CANCEL` + 진행중 | `CANCEL_REQUESTED` | claimStatus 기준 세분화 |
| claimType=`RETURN` + 진행중/완료 | `RETURN_REQUESTED` / `RETURN_IN_PROGRESS` / `RETURN_COMPLETED` | claimStatus 기준 |
| claimType=`EXCHANGE` + 진행중/완료 | `EXCHANGE_REQUESTED` / `EXCHANGE_IN_PROGRESS` / `EXCHANGE_COMPLETED` | claimStatus 기준 |
| 매핑 불가 | `UNKNOWN` | 실패 로그 기록 후 운영자 확인 |

### 6.3 연동 주의사항

- 인증: OAuth 2.0 Client Credentials. 토큰 만료 전 재발급 로직 필요.
- 발주확인(`placeOrder`)은 송장전송(`dispatch`)의 전제조건이다.
- 상세 조회는 상품주문번호 수 제한이 있으므로 배치 분할 처리한다.
- 발송 지연 처리, 배송 희망일 변경은 2차 범위.

## 7. 쿠팡 매핑 (2순위)

기준: Open API (`./외부_마켓_API/coupang-open-api.md`, 확인일 2026-06-10)

### 7.1 오퍼레이션 매핑

| 어댑터 오퍼레이션 | 쿠팡 API |
|---|---|
| `fetchOrders` | 발주서 목록 조회(일단위 페이징) + 발주서 단건 조회(보완) |
| `confirmOrder` | 상품준비중 처리 (acknowledgement) |
| `uploadInvoice` | 송장 업로드 — **`INSTRUCT` 상태에서만 가능** |
| `fetchClaims` | 취소/반품/교환 API |
| `syncStatus` | 발주서 단건 조회 |

### 7.2 상태 매핑표 (쿠팡 → 내부 상태)

| 쿠팡 상태 | 내부 상태 | 조건 |
|---|---|---|
| `ACCEPT` | `NEW` | 결제완료, 상품준비중 처리 전 |
| `INSTRUCT` + 내부 처리 진행 중 | `ORDER_CONFIRMED` ~ `MARKET_INVOICE_FAILED` | 내부 소싱/송장 진행 상태가 기준 |
| `DEPARTURE` | `SHIPPING` | 출고 |
| `DELIVERING` / `NONE_TRACKING` | `SHIPPING` | |
| `FINAL_DELIVERY` | `DELIVERED` | |
| 취소/반품/교환 API 응답 | 클레임 상태군 | 클레임 유형/단계 기준 |
| 매핑 불가 | `UNKNOWN` | |

### 7.3 연동 주의사항

- 인증: Access key + Secret key, HMAC 서명. 허용 IP 등록 필요 여부 확인.
- 송장 업로드는 `INSTRUCT` 상태에서만 가능하므로 발주확인(상품준비중 처리)이 선행돼야 한다.
- **`ACCEPT` 상태에서 고객이 배송지를 변경할 수 있다.** 상품준비중 처리 후 발주서 단건 조회로 배송지를 재확인하고, 변경 시 내부 주문 정보를 갱신 + 운영자 알림.
- 주문 생성 직후 목록 조회 반영 지연이 있을 수 있으므로 단건 조회로 보완한다.

## 8. 확장 마켓 어댑터 추가 절차 (11번가, 지마켓/옥션)

신규 마켓 추가 시 다음 산출물을 작성한 뒤 구현한다.

1. `./외부_마켓_API/{마켓}-api.md` — 공식 문서 링크, 확인일, 인증 방식, 호출 제한
2. 본 문서에 매핑 섹션 추가 — 오퍼레이션 매핑표 + 상태 매핑표 (6장/7장과 동일 형식)
3. 어댑터 5개 오퍼레이션 구현 명세 — 미지원 오퍼레이션은 `UNSUPPORTED` 명시
4. 인증 설정 화면 항목 정의 (`02_UI_UX_명세서` 마켓 연동 섹션)

| 마켓 | 사전 확인 포인트 |
|---|---|
| 11번가 | 오픈API 키 발급 절차, 주문 상태 코드 체계, 송장 등록 API 제약 |
| 지마켓/옥션 | ESM PLUS 통합 계정 구조(한 계정 두 마켓), 마켓 구분값 처리 |

## 9. 소싱라이프 연동 인터페이스 (외부 서비스)

소싱라이프는 마켓 어댑터가 아니라 **별도 외부 서비스 연동**으로 취급한다.

| 오퍼레이션 | 방향 | 설명 |
|---|---|---|
| 소싱 주문 생성 | 주문팡팡 → 소싱라이프 | 주문상품 정보(상품/옵션/수량/수령지)를 전달해 소싱 주문 생성. `sourcingOrderId` 수신 |
| 결제 상태 확인 | 소싱라이프 → 주문팡팡 (콜백) 또는 주기 조회 | `PAID` 확인 시 내부 상태 `SOURCING_PAYMENT_COMPLETED` 전환 |
| 국내송장 수신 | 소싱라이프 → 주문팡팡 (콜백) 또는 주기 조회 | 택배사+송장번호 수신 시 `DomesticInvoice` 생성, `MARKET_INVOICE_PENDING` 전환 |
| 소싱 주문 취소 | 주문팡팡 → 소싱라이프 | 클레임 처리 시 소싱 주문 취소/환불 요청 |

- 소싱라이프 API 명세는 확정 시 본 문서에 요청/응답 스키마를 추가한다. (현재 인터페이스 계약 단계)
- 연동 실패 시 `sourcingStatus = FAILED`로 기록하고 운영자 재처리 대상으로 노출한다.

## 10. 검증 기준

- 같은 기간 반복 수집 시 주문 중복 생성 0건
- 마켓 상태 변경(배송완료, 클레임)이 다음 수집 주기 내 내부 주문에 반영
- 발주확인/송장전송 부분 실패 시 라인 단위 성공/실패가 구분 기록
- `UNKNOWN` 발생 시 원문 포함 실패 로그 생성
- 내부 상태가 마켓 수집에 의해 후퇴하는 케이스 0건
